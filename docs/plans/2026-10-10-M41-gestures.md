# M41: moving and adding stops takes one gesture wherever you are — build plan

Gate: `docs/milestones/M41-planning-without-friction.md`, § *Exit gate*. The decisions are
numbered there and cited here as D1–D11. ADR-068 records D9 and D11. Delete this file when M41's
gate closes (`docs/plans/README.md`).

## The stack

Each part has its own branch (a worktree each), based on the part below. Each opens as a draft
and is merged in order with a merge commit (`docs/guidelines/stacked-prs.md`). **Nothing merges
without Mitchell.** Parts are built back to back. Each is self-reviewed, including ADR-068's
duplicate check, then marked ready, and CodeRabbit is triggered in the next free hourly slot. A
part under review takes no push; fixes go to the lowest part and merge forward.

**What a person clicks on the preview to see each part:**
- **Part 1:** open a stop on Day 2, change Day to Day 3, and save. It moves, keeps its time, and
  History shows one entry. Undo puts it back. Open a parked stop and pick a day; it leaves the
  rack. *Remove* in the editor removes the stop.
- **Part 2:** on desktop the header has no *Add stop*. Double-click the drawer's empty space; the
  editor opens set to *Unscheduled*. Save, and the card is in the drawer with no buttons on it.
  Tap it to open it. An empty day reads *"Double-click or drag to add a stop"*.
- **Part 3:** drag a stop from Day 2 to the rack. Its card reads *"from Day 2"*. A stop parked
  before this deploy reads nothing.
- **Part 4:** in Calendar, drag Day 3's Kyoto card onto Day 4. Every stop on that card moves, as
  one History entry. Drag a card past the last day; the trip grows to that date. Drag Day 1's only
  card to Day 2; Day 1 is empty and the start date is unchanged. Drag a rack card onto a day.
- **Part 5:** in Plan, drag Day 2's header onto Day 4; its stops move. Option-drag a stop; a copy
  lands. Drag a stop's top edge; its start changes. Focus a stop and press Delete; it goes, with
  the undo toast.
- **Part 6:** copy a Google Maps place link, focus Day 2 and press ⌘V. The editor opens on Day 2
  with the place filled in. Paste *"Ramen at Ichiran"* and the title is filled in.
- **Part 7:** press ⌘K and type *cal*, then Enter: Calendar. ⌘K *new*: the editor opens on the
  focused day. ⌘K *ask*: the assistant opens. ⌘K and a trip's name: that trip. Then do the whole
  walk with the keyboard only.

## Part 1 — move from the editor (D3)

1. **One move function.** `board/moveStops.ts`:
   `moveStopsCommands(trip, activityIds, toDayId | null, { newDays? })` returns the
   `BatchableCommand[]` for a move: `AddDay` for each new day, then `MoveActivity` per stop,
   appended at the end of the target day's order. It also returns the `UpdateActivity` that
   today's `assignFromRack` adds. `moveActivity`, `assignFromRack`, `unscheduleActivity` and
   `resolveDrop`'s callers are re-pointed onto it, with no behaviour change. Its unit tests come
   from `@tc/factories`.
2. **Editor.** The Day select is enabled in edit mode. On save, a changed day sends
   `dispatchBatch([UpdateActivity?, ...moveStopsCommands(...)])`. An unchanged day stays one
   `UpdateActivity`. A timed stop keeps its time window.
3. **Remove in the editor footer.** It sends `RemoveActivity` with the existing undo toast. The
   rack card's Remove goes in Part 2.
4. **Tests.** A sheet test asserts that a day change dispatches one batch whose `MoveActivity`
   equals what a drag of the same stop builds. Seen red with the select still disabled, and with
   the move left out of the batch. Remove has a component test.

## Part 2 — the drawer is just cards (D1, D4, D5)

1. **Rack cards.** Edit, Remove and *Add to day…* go. A tap (or Enter) on the card opens its
   editor, and the card stays draggable. The *"Parked by"* line stays.
2. **Create.** Double-click the drawer's empty space to call `openCreate()` (parked). On touch,
   a hold does the same, matching the river. Suggest mode keeps its Day 1 default.
3. **Header.** *Add stop* is removed from the desktop cluster (`TripHeader.tsx:542`); the phone
   `⋯` item stays.
4. **Empty day.** `DayRiver` draws one line of muted text when it has no stops, worded by pointer
   type. It is not a control and takes no pointer events, so double-click still reaches the
   river.
5. **e2e.** Every spec in *Header* above moves from the header button to a river double-click
   (for a day) or a drawer double-click (for a parked stop), through one helper in
   `e2e/helpers/`. Run `grep -rn '"Add stop"' apps/web/e2e/` before and after. The capability test
   asserts a parked stop can be made on desktop with no header button.

## Part 3 — a parked stop shows the day it left (D6)

1. **Contract.** `MoveActivity` and `ActivityMovedV1` gain `fromDayId: uuid | null`, with
   `.nullable().default(null)`. `decide` fills it from state, not from the client, so it cannot
   lie. Revert and clone leave it `null`. CHANGELOG entry. Run `pnpm` openapi/fingerprint if the
   public shape moves.
2. **Read.** The rack's view model takes, per parked stop, the `fromDayId` of its last
   `ActivityMoved` whose `toDayId` is `null`, mapped to *"from Day N"* (by the day's current
   ordinal, or nothing if the day has been removed). It is read client-side, where the trip's
   events are already replayed (check), or exposed on the detail read if they are not.
3. **Tests.** Domain: `decide` stamps `fromDayId`, and an old event parses with `null`. Rack: an
   origin shows; a pre-change stop shows none; a stop parked by a revert shows none. Each seen red.

## Part 4 — Calendar drag (D2)

1. **Cards carry ids.** `calendarCityCards` adds `activityIds` per card.
2. **Drag sources and targets.** Each city card is `draggable({ kind: "city-card", activityIds,
   fromOrdinal })`, and the `DayGrip` gets `cursor: grab`. In-trip cells, and out-of-trip cells
   **after** the end, are drop targets. Cells before the start are not.
3. **Drop.** One `dispatchBatch(moveStopsCommands(...))`. A drop past the end adds
   `daysBetween(end, date)` `AddDay`s, with ids minted client-side, then the moves. Day 1 moved
   away stays as an empty day.
4. **The rack in Calendar.** `lensAcceptsDrops` admits Calendar, its doc comment updated (it
   says not to make it a list). A rack card dropped on a cell is the same move.
5. **Tests.** A unit test of the batch for a past-end drop: N `AddDay`, then the moves. Component
   tests for the drop wiring. The e2e drags a card to another day and past the end, and checks
   History has one entry. Seen red.

## Part 5 — Plan gestures (D7)

1. **Day drag.** `Column.tsx`'s header becomes a drag source `{ kind: "day", dayId }`. A drop on
   another day moves all its stops through `moveStopsCommands`. The header's title button keeps
   its click to focus the day.
2. **Option/Alt-drag copies.** On drop, `altKey` builds `AddActivity` with a new id and the
   copied fields, placed where the drop lands, instead of the move. The cursor shows copy while
   Alt is held.
3. **Top edge.** A second grip on `RiverBlock`, plus `resizeStart` in `riverGestures.ts`
   mirroring `resizeEnd`. It shares `follow`, the threshold and `RIVER_MIN_MINUTES`, and commits
   through `onRetime`.
4. **Delete/Backspace** on a focused river block sends `RemoveActivity` with the undo toast,
   guarded by `isTypingTarget`.
5. **Tests.** `riverGestures` units for `resizeStart`. Component tests for each gesture, each
   seen red.

## Part 6 — paste to add (D8)

1. **Parser.** `lib/pasteToStop.ts` is pure. A `google.com/maps/place/<name>/@lat,lng` URL
   becomes a title plus a location. A `maps.app.goo.gl` short link needs a server redirect lookup:
   if it is cheap and quota-safe it goes through a small route, otherwise it opens the editor
   with the link in notes and goes to candidates. Plain text becomes the title. Unit-tested over
   its examples, each seen red.
2. **Where.** A `paste` listener on Plan, when a day is focused and the target is not a text
   input, calls `openCreate({ dayId, prefill })`. A drop of a link or text onto a day's river does
   the same. Prefill goes through the editor, so the place is reviewed before saving.

## Part 7 — ⌘K (D9, D11)

1. **Lift the actions** that are inline today into named functions or context values that the
   page control and the palette both call:
   - the lens switch (`useLens().setView`);
   - `openCreate`;
   - the assistant's `show` (lifted into a context);
   - undo and redo;
   - opening Share (Settings with its Share section);
   - navigation to `/`, `/playbooks`, `/account` and a trip.
2. **Palette.** It is built on `components/ui/dialog` with a list. There is no new dependency
   unless a combobox primitive is clearly cheaper. Its commands live in
   `components/palette/commands.ts`, which only imports and lists the actions (ADR-068 §1).
   Matching is loose; Enter runs the top match; *No match* goes nowhere.
3. **Focus.** Closing returns focus to where it was. The editor opened from it hands focus back
   too (KI-2026-10-09-b, at least for this path).
4. **Tests.** An identity test: for each command, the mocked action is the same reference the
   page control receives (ADR-068 §2). Seen red with one command re-implemented inline. The e2e
   is keyboard-only: ⌘K → Calendar → ⌘K *new* → save → ⌘K *ask*.
5. **The gate.** The full ci-like e2e on merged `main`; the mouse and keyboard-only walk on the
   top part's preview; the duplication log closed out.
