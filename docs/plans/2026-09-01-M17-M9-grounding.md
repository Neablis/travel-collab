# M17 + M9 (grounding link) build plan — 2026-09-01

Write-once scaffolding (`docs/plans/README.md`): deleted at M17's gate close and
again at M9's, with anything durable promoted to an ADR, a milestone file or a
known-issue entry first.

**Decisions this plan rests on**, all Mitchell's, 2026-09-01:

1. **M17 exit-gate box 3 (home time on hover) is amended out of the gate** and
   becomes its own placed item. The app has no timezone infrastructure of any
   kind — no `tz` on a trip, `Intl` pinned to `timeZone: "UTC"` in both
   formatters (`apps/web/src/lib/dates.ts:72`,
   `packages/pages/src/format.ts:11`), no airport dataset and no date/tz
   dependency in any `package.json`. Box 3 as written pulls in all three plus a
   `packages/contracts` change for `trip.tz`. The home airport is still stored
   and displayed by this milestone; it just does not yet drive a tz reference
   line. Recorded in `M17-account-customization.md` as an amendment, per
   `docs/milestones/README.md`'s rule that a gate definition changes only by
   Mitchell's explicit decision.
2. **M9's grounding takes the contract route:** `placeRef` is added to
   `AddActivity`/`UpdateActivity` in `packages/contracts` as its own reviewed
   PR, then `search_places` is built on it. Chosen over a cache-validated
   string because the write tools are *derived* from `BatchableCommand`
   (`planningTools.ts:77`), so the tool schema **is** the contract schema —
   a wrapper that added `placeRef` outside the contract would break the
   "derived, never hand-listed" property ADR-015 bought.
3. **Conversation durability is out of scope, and the gate does not cover it.**
   Mitchell, asked directly: *"Im really ok with a conversation getting lost
   today on a page refresh. What i originally meant was having a back and forth
   conversation rather than 1 prompt, then losing all context with the next
   prompt."* That back-and-forth **already ships** — the client holds the
   thread and re-posts it each turn (`TripBoardScreen.tsx:394-397`, "Ruling
   R1"), capped at 40 messages (`lib/askLimits.ts`). So M9 gate box 2 needs a
   **walk, not a build**, exactly as its own annotation says, and no
   conversations table is built. This is written into the milestone file so a
   later session does not re-derive durability as missing work.
4. **Session scope is M17 complete + M9's grounding link only.** M9's remaining
   boxes (replay harness/KI-11, KI-94 step-quota admission, the live-model
   record) are a follow-on session. **M17's gate can close this session; M9's
   cannot**, and nothing in this plan should be read as closing it.

# M17 — account preferences

## Three facts the milestone file gets wrong, corrected here

**1. Gate box 2's call-site list is stale.** Of the four surfaces it names:
`MapFocusCard.tsx:24` is correct; `MapRail.tsx` is at **:361**, not :358;
`mapRailData.ts` is at **:72**, not :68, and holds no unit string at all (it is
the `totalKm` *source*); and **Timeline's day summary no longer renders a
distance** — `TimelineLens.tsx:167-171` and `:192-195` record that M10 Phase 8
removed it deliberately. The box also names a **"longest-hop"** surface that
does not exist (grep: no such thing). Meanwhile it misses one that does:
**`MapDayStrip.tsx:144`**, same `· X km` shape as `MapFocusCard`.

So the real work is **three** call sites — `MapFocusCard.tsx:24`,
`MapRail.tsx:361`, `MapDayStrip.tsx:144` — and the box text is corrected in the
milestone file in the same commit rather than silently reinterpreted.

**2. `packages/domain/src/trip/conflicts.ts:211` stays in kilometres.** It emits
a user-visible string (`~N km apart on the same day`) but lives in the pure
domain, which the UI may not import and which takes no I/O. Plumbing an account
preference into it would cross the architecture wall for one conflict
description. Left as-is and noted in the milestone file, not silently skipped.

**3. `users.name` cannot be the user-set name.** `upsertUser`
(`server/users.ts:69-81`) is an `onConflictDoUpdate` that rewrites `name` from
the provider on **every sign-in**, so a name typed into the settings Sheet
would be silently clobbered the next time the person signs in with Google. This
plan therefore adds a **separate `display_name` column** for the user-set value
and leaves the provider's `name` untouched. `displayNameFor` gains one term at
the front of its existing chain.

> **This is a design decision the milestone file did not anticipate** and is
> flagged to Mitchell rather than absorbed. The alternative — a
> `name_set_by_user` boolean guarding the upsert — needs `upsertUser` to become
> conditional, which is a change to the Identity module's whole documented
> write surface (`users.ts:12-18`) for no gain.

## Link 1 — contracts (PR 1)

`packages/contracts/src/identity.ts`, new file, following `access.ts`'s shape
and its header-comment convention:

```ts
export const DistanceUnit = z.enum(["km", "mi"]);

export const UserPreferences = z.object({
  displayName: z.string().min(1).max(80).nullable(),
  homeAirport: z.string().regex(/^[A-Z]{3}$/).nullable(),
  distanceUnit: DistanceUnit,
});

export const UpdateUserPreferences = UserPreferences.partial();
```

- `homeAirport` is a **3-letter IATA code**, uppercase, or null. Validated but
  not resolved against any dataset — that is exactly the line decision 1 draws.
  A regex is honest about what is stored and stays forward-compatible with a tz
  lookup later.
- `distanceUnit` is **required and defaults to `km` at the storage layer**, so
  a reader never has to interpret an absent unit.
- Changelog entry in `docs/contracts/CHANGELOG.md`, same PR.
- No consumers yet — PR 1 is schema + changelog only, which is what makes it
  reviewable on its own.

## Link 2 — storage (PR 2)

Migration **`0015`** (next after `0014_futuristic_night_thrasher.sql`), adding to
`users`:

- `display_name text` — nullable, user-set, never written by `upsertUser`.
- `home_airport text` — nullable.
- `distance_unit text not null default 'km'`.

**The migration needs a production dispatch** — `gh workflow run
migrate-production.yml -f confirm=migrate` from `main`. Merging does not apply
it. Stated in PR 2's body, per `AGENTS.md` and gate box 4.

Timestamps on `users` are `mode: "string"` (the older convention, KI-53 note at
`schema.ts:193-202`); the new columns carry no timestamps, so nothing here
touches that.

## Link 3 — Identity module (PR 2)

`apps/web/src/server/users.ts` gains two functions beside the existing write
surface, following `savedDays.ts`'s row→DTO boundary:

- `readPreferences(userId): Promise<UserPreferences>` — returns storage
  defaults for a user with no row rather than throwing, since a session can
  outlive a row.
- `writePreferences(userId, patch: UpdateUserPreferences): Promise<UserPreferences>`.

**`upsertUser` is not touched.** Its `onConflictDoUpdate` set list is
enumerated by hand, so the new columns are simply absent from it — which is
precisely the property that keeps a user-set name safe. A test asserts it:
write a `display_name`, run `recordSignIn`, assert it survived.

New route `apps/web/src/app/api/account/preferences/route.ts` — `GET` and
`PATCH`, both `auth()`-gated inline (there is no `requireUser()` helper and
account scope resolves no resource, so the two `require*` helpers do not fit).
Contract-validated against `UpdateUserPreferences` on the way in.

## Link 4 — `kmLabel` (PR 2)

`apps/web/src/lib/units.ts`, one exported helper owning every distance:

```ts
kmLabel(km: number, unit: DistanceUnit): string
```

Rules from SPEC §12 / gate box 2: **miles below 0.19 → feet; km below 1 →
metres.** A property test over the boundaries, with a measured `witness` floor
per `AGENTS.md`'s testing model — not a guessed one.

Applied at the three real call sites above. `mapRailData.ts` keeps computing
`totalKm`; only the rendering changes, so the map data shape is untouched.

## Link 5 — reaching the client (PR 2)

Preferences are read in the trip page's **server component** and passed down as
props, then held in a small `PreferencesProvider` context for the map
components that need them. This follows ADR-019's established rule — server-only
values reach UI as props from a server component, never by a client component
importing `src/server`.

Not the JWT: the session is JWT-only (`authConfig.ts:124-138`), so a preference
in the token would go stale until the next sign-in, which is the wrong
behaviour for a setting the person just changed.

## Link 7 — the `displayNameFor` seam (PR 2)

## Link 1 — contracts (PR 3)

`placeRef` on `AddActivity` and `UpdateActivity`
(`packages/contracts/src/activity.ts:98,115`):

```ts
placeRef: z.number().int().nonnegative().optional(),
```

Optional, because a user-typed location still arrives as free text and the
blind-enrichment path stays as its fallback (which is what closes KI-15's
remaining half rather than deleting it).

**Consumers updated in the same PR**, per invariant 5: the derived write tools
pick the field up for free (`planningTools.ts:77`), but `parseApprovedCommands`
(`writeTools.ts:395-412`) and the proposal renderer
(`describeProposedChange`, `writeTools.ts:106`) both enumerate fields by hand.
`AGENTS.md`'s own warning applies — *"adding a field means grepping for every
place fields are enumerated by hand"*, which M18 hit three times.

Changelog entry, and **`@tc/fixtures` exercises the new field** per the
Definition of Done, followed by `pnpm seed:verify`.

## Link 2 — the LocationIQ adapter learns `bounded` (PR 4)

`locationiq.ts:57-61` deliberately omits `bounded=1` ("biases ranking rather
than filtering"), and `GeocodeOptions` (`geocoder.ts:32`) has no such field.
M9's scope requires `viewbox` **+ `bounded=1`** for search. So the port gains an
optional `bounded?: boolean`, default false — **the existing enrichment path's
behaviour is unchanged**, and only the new search tool passes it.

Endpoint is already right: `locationiq.ts:3` is `/v1/search`. The Nearby/POI
endpoint stays unused, per the milestone's explicit instruction.

## Link 3 — `search_places` (PR 4)

A **fourth read tool**, added to `READ_TOOL_NAMES` (`readTools.ts:40`) under
ADR-022's rule, alongside `read_trip`/`read_day`/`find_free_time`:

- One call, an **array** of queries, each region-biased from `tripRegionOf`
  (`geocodeRegion.ts`) — so a turn costs one extra step, not one per place.
  `meta.steps` should read 2–3, not 18; it is the cost driver and is already
  measured.
- **Throttled at 2 req/s** through the existing `mapRateLimited`
  (`ai/rateLimit.ts:14`). Never `Promise.all` — this is what actually broke the
  2026-08-02 dogfood run.
- Returns **numbered** candidates with name, address and coordinates.
- Candidates are held in a **per-turn server-side cache**, keyed to that
  request. The model never sees or supplies a coordinate.

`MAX_ASK_STEPS` is 8 (`handleAskRequest.ts:59`); search-then-act fits without
raising it, and the plan does not raise it.

## Link 4 — resolving the ref (PR 4)

Server-side, in `buildProposal` (`writeTools.ts:234`): a command carrying
`placeRef: N` has its `location` **and coordinates** filled from that turn's
cache entry N. A `placeRef` with no matching entry is a hard rejection, not a
fallback to the model's text — that rejection is the guarantee, and it is the
same shape `idFields.ts` already provides for UUIDs.

`enrichCommandLocations` (`geocodeEnrichment.ts:202`) is demoted to what the
milestone says: a fallback for **user-typed text only**. It still runs for
commands with no `placeRef`, unchanged.

This is what closes **KI-81** and the architectural half of **KI-15**.

## Link 5 — KI-93, the second unmetered door (PR 4, gate box 8)

`geocodeQuota()` (`quota.ts:217`) has exactly one caller — the proxy route
(`api/geocode/route.ts:17`). The AI path geocodes in bulk through
`enrichCommandLocations` (called from `handleAiRequest.ts:448` and
`writeTools.ts:337`) with **no quota consult at all**, which `quota.ts:206-215`
admits in prose.

Grounding is about to send far more traffic through that same vendor, so the
door closes with it. Fix per the KI's own recommended path: **post-hoc
settlement** from the existing `LocationEnrichmentReport`, reusing the
`settleAiSteps` shape (`quota.ts:326`) rather than inventing a second
mechanism. Search-tool lookups settle the same way.

> The KI notes a product call on mid-batch behaviour — what happens when a
> batch exhausts the quota halfway. **Proposal: settle after, never refuse
> mid-batch**, matching `settleAiSteps`, which never refuses and never throws.
> A half-geocoded batch is worse than an over-quota one. Flagged for Mitchell,
> not silently chosen.

## Link 6 — KI-12 (gate box 7), and its stale premise

**KI-12's stated cause is false and must not be planned against.** Its file says
*"There is no `SetTripName` command anywhere in the contract"*. There is:
`SetTripName` (`contracts/src/trip.ts:98`) and `SetTripDates` (`:116`) are both
`BatchableCommand` members (`:254-255`) and both are already exposed as derived
tools with written descriptions (`planningTools.ts:27-28`).

What remains is **behavioural**: nothing makes the model call them on a "plan me
a trip" turn, and the system instruction (`instructionsFor`,
`handleAskRequest.ts:719`) says nothing about naming or dating a trip. So the
fix is an instruction change plus a test, not a contract change. **The KI file
is corrected in the same PR** — a known issue whose premise is stale is worse
than one that is open.

## A finding neither the milestone nor any KI records

**`/ask` never charges `aiStepQuotas` at all.** `handleAskRequest.ts:306`
consumes only `aiQuotas()`, and `settleAiSteps` is never called on that path —
only `/ai` charges the step layer (`handleAiRequest.ts:292`). So the
assistant's 8-step turns are unmetered by the step quota entirely, which is a
larger hole than KI-94's admission-charge overshoot and is not the same bug.

**Filed as a new known issue, not fixed here** — it is not a gate box, and
inventing one mid-session is exactly the gate-regrowth this milestone was cut
down to avoid. It belongs with KI-94 in the follow-on session.
