## The stack

Each part has its own branch, opens as a draft, and is merged in order with a merge commit
(`docs/guidelines/stacked-prs.md`). **Nothing merges without Mitchell.** Parts are built one after
another. As each is finished it is self-reviewed, marked ready, and CodeRabbit is triggered on it
in the next free hourly slot, while the next part is built. A part under review takes no push
until its review finishes; fixes then go to the lowest part and merge forward.

- Part 2: History → *Save snapshot*, make changes, preview the snapshot, *Restore*. One History
  entry; Undo returns to before the restore.

## Part 1 — *Accept all* is one batch (D1–D3)

1. **Contract.** `AcceptSuggestionChanges { changeIds: uuid[] (1–200) }` request and a response of
   the resolved `SuggestionChange[]`. A new `Origin` kind
   `suggestions { changes: { suggestionId, changeId }[], authorIds: string[] }` (D3); the existing
   `suggestion` kind stays, for single accepts and every stored envelope. Domain treats it as
   `user` for undo. Changelog entry in `docs/contracts/CHANGELOG.md`.
2. **Server.** `acceptSuggestionChanges(tripId, changeIds, reviewer)` in
   `apps/web/src/server/suggestions/`: editor+, every id pending, unexpired and on this trip;
   every pending parent is either already accepted or in the set; order parents first; concatenate
   commands; one `executeTripCommandBatch` with a hook that marks every change accepted
   (conditional on `pending`, else roll back). Any refusal lands nothing and names the change
   (D1). All-no-op is accepted with nothing appended (W52's rule, for the set). Route:
   `POST /api/trips/:tripId/suggestions/changes/accept`.
3. **History.** The description for a `suggestions` batch reads *"Accepted N suggestions from Sam
   and Ana"*. Undo of it is the ordinary undo; the rows stay `accepted` (D2).
4. **Client.** *Accept all* calls the new action once, with `acceptAllOrder`'s ids. The progress
   label becomes a single pending state; a refusal shows the named change and says nothing landed.
5. **Tests.** Integration test against real Postgres: accept ten → one History entry, one undo
   restores all, rows stay accepted — **seen red** against today's per-change loop. A refused
   change lands nothing. A unit test for the History sentence. The chip's component test.
6. **Spec.** Amend W77 in `docs/specs/2026-10-03-suggester-role-design.md` (it rejected a batch
   endpoint), citing D1.

## Part 2 — named snapshots (D4, D5)

1. **Migration `0045_trip_snapshots`**: `trip_snapshots(id uuid pk, trip_id fk cascade, seq int,
   name text 1–80, created_by, created_at)`, index on `(trip_id, created_at)`. Not on the stream.
2. **Contract.** `TripSnapshot { id, tripId, seq, name, createdBy, createdAt }`; create, rename,
   delete inputs. Changelog entry.
3. **Server** (`apps/web/src/server/snapshots/`): save at the current head `seq`, rename, hard
   delete, list newest first. Editor+ (D5); cap 20 per trip, refused with the reason. Restore is
   `RevertToState { toSeq: snapshot.seq }` through the ordinary pipeline — refuse `no-op` when the
   trip already matches. Routes under `/api/trips/:tripId/snapshots`.
4. **Client.** In the History panel, a *Snapshots* list above the scroll: *Save snapshot*, rename,
   delete (confirm), *Preview* (the existing `history/:seq` read), *Restore*. Viewers and
   suggesters see no controls.
5. **Tests.** Integration: save → change → restore lands one batch, undone in one step; a snapshot
   whose `seq` predates a deleted day restores that day; cap and role refusals. Each seen red.

## Part 3 — the assistant suggests (D6, D7)

1. **Migration `0046`**: `trip_suggestions.via text null` (`'assistant'`).
2. **Create.** Editors may create (`create.ts` role check); `via: assistant` rows are exempt from
   the 50-per-author cap, not the 200-per-trip cap. Spec W25 amended.
3. **Assistant.** In the ask route, after `buildProposal`: a proposal with more than one command
   and no inserts saves a snapshot (Part 2's action; skipped with a note at the cap) and stores
   one suggestion `via: assistant` authored by the asking editor. The stream's final chunk gains
   a `suggested { suggestionId, changeCount, snapshotId? }` shape. One-command and insert turns
   keep the card.
4. **Client.** The chat renders a short *"N suggestions are on the board"* note with a link that
   opens the chip; the chip and ghosts already draw them. *"via the assistant"* on the by-line.
5. **Tests.** Integration: an editor's multi-change turn (mocked model) stores a suggestion a
   second editor lists after a fresh read. Eval cases updated and re-run, numbers pasted in the
   gate. The e2e (`e2e/m40-big-change.spec.ts`): ask for a day → suggestions on the board →
   *Accept all* → one History entry → restore the snapshot, on `test:e2e:ci-like`.
6. **Docs.** `SYSTEM-DESIGN.md` as-built paragraph for suggestions and snapshots.
