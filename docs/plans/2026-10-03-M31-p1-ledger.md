# M31 Phase 1 — the ledger, on the current stack: build plan

Decision record: **ADR-062** §5 and its *Phase 0 findings (c)*. Gate:
`docs/milestones/M31-assistant-on-eve.md` § *Exit gate*, "Phase 1 — the ledger". Delete this
file at M31's gate close (`docs/plans/README.md`).

**This phase ships value even if the port stops here.** Nothing in it imports, mentions or
waits for `eve`. It closes two open known issues on the way:

- `KI-2026-09-14-b`: `ai_usage` is best-effort on abort.
- `KI-2026-09-17-c`: escalated turns bill the wrong model.

It also gives `ai-usage` its first database answers.

**It starts when M31 is current.** M19 is current until its gate closes, so this plan waits
for that unless Mitchell reorders.

## What is true today

Surveyed 2026-10-03. Cite these, and re-check them before trusting the line numbers.

- **One writer.** `createAskRecorder` (`server/assistant/askAnalytics.ts`) sees each step
  through `ToolLoopAgent`'s `onStepEnd`. Its `AskStepLike` type keeps only `toolCalls`,
  `text`, `finishReason` and `usage { inputTokens, outputTokens, totalTokens }`, so **cached
  tokens are dropped** even though `providerOptions.gateway.caching` is `"auto"`. Its
  single-writer latch builds the `TurnLedger` (`server/assistant/ledger.ts`). The sink in
  `server/ai/handleAskRequest.ts` then writes the `ai.ask` log line, the Sentry metrics,
  `recordAiUsage` and `settleAiSteps`.
- **No server-side turn id exists.** `ai_usage.id` is a fresh `randomUUID()` in
  `server/entitlements/usage.ts`.
- **Per-tool timings are measured but not kept.** `TurnMeter.toolCall(name, ms, ok)` is called
  from `registry.ts`'s `measured()`. Its output reaches only Sentry's `ai.tool.duration`. It
  has no `callId`, no sizes, and no notion of repaired, refused or reached-a-proposal.
- **Repair is unrecorded.** `repairToolCall` → `repairToolInput` in `handleAskRequest.ts`
  leaves no trace.
- **The escalation step is unknown.** `prepareStep` swaps to `grant.escalation.model`, but the
  escalation buffer stores no step; `pivotsOf` writes `step: -1`. `ai_usage.turn_model` is the
  admitted model for the whole turn, which is KI-2026-09-17-c.
- **The abort and error paths do not await the `ai_usage` insert** (KI-2026-09-14-b).
- **The money rule.** `server/entitlements/usage.noMoney.test.ts` (the schema comment calls
  it `aiUsage.noMoney.test.ts`; fix that comment) and `server/assistant/ledger.test.ts` forbid
  money anywhere on this path. Price is a downstream join against `modelRates.ts`, which has
  **no cached-input rate**.
- **The latest migration** is `0034_public_library_sweep_index`.

## Part 1 — the rows

1. **A turn has an id.** `handleAskRequest` mints `turnId = randomUUID()` once, before
   admission's last stage. It is passed to the recorder, the meter and the ledger
   (`TurnCost.turnId`), and the `ai.ask` record gains `turnId`, so a log line joins to its
   rows. **`ai_usage.id` becomes the `turnId`**, and the insert is
   `ON CONFLICT (id) DO NOTHING`. No new column is added: old rows keep their random ids and
   simply have no child rows.
2. **Migration `0035_ai_usage_steps_and_tool_calls`**, generated with drizzle-kit and never
   hand-written:
   - `ai_usage_steps`:
     - `turn_id uuid`, `step_index int`, **primary key `(turn_id, step_index)`**;
     - `model text not null` (the RESOLVED id that ran this step);
     - `tier text` (nullable);
     - `tokens_in`, `cache_read_tokens`, `cache_write_tokens`, `tokens_out` as nullable
       ints: null means unreported, never zero;
     - `finish_reason text`;
     - `escalated boolean not null`, true when this step ran on the escalation model;
     - `pivoted boolean not null`;
     - `created_at`.
   - `ai_usage_tool_calls`:
     - `turn_id uuid`, `call_id text`, **primary key `(turn_id, call_id)`**;
     - `step_index int`;
     - `tool text not null`;
     - `outcome text not null`: `ok | failed | repaired | refused-by-grant`;
     - `duration_ms int` (null for `refused-by-grant`, which never ran);
     - `input_bytes int`, `output_bytes int`;
     - `reached_proposal boolean`: null for tools that cannot produce one;
     - `created_at`.
   - An index on `created_at` for each table.
   - **No foreign key**, on the same terms as `ai_usage.user_id`. **No user text**: no input
     or output content, only sizes.
   - A schema comment states both rules, in the style of `aiUsage`'s.
3. **The recorder reads per step.** Widen `AskStepLike` to the AI SDK 7 shape it already
   receives: `usage.inputTokenDetails { cacheReadTokens, cacheWriteTokens }`, `finishReason`,
   and each tool call's `toolCallId`.
   - **The step's model is the one `prepareStep` chose.** `prepareStep` records
     `{ model, tier, escalated, pivoted }` per `stepNumber` in a per-turn map that the
     recorder reads. This is our id, which the rate record prices, never
     `step.response.modelId`, because the Gateway's echo is not guaranteed to match it.
   - A step with no `prepareStep` override records the admitted model and tier.
   - Unit tests cover: a cached-token step, an escalated step after a question-tier step, and
     a pivot. Each one is seen to fail.
4. **The meter learns a call's identity and size.**
   - `toolCall` takes `{ callId, name, ms, ok, inputBytes, outputBytes }`. `measured()` reads
     `toolCallId` from the AI SDK's `ToolExecutionOptions`. It takes byte sizes with
     `Buffer.byteLength(JSON.stringify(…))`, guarded so a size fault records null and never
     throws (the meter's existing totality rule).
   - A tool that *returns* a refusal stays `ok`: the outcome describes execution, and refusal
     values are already visible in the `ai.ask` line.
   - `step_index` comes from joining the meter's `callId` to the step's observed `toolCalls`
     at the latch.
5. **`repaired` and `refused-by-grant`.** `repairToolCall` gains a `meter.repair(callId, name,
   kind)` call:
   - `kind = "refused-by-grant"` when the name is a registered tool absent from this step's
     active set;
   - `kind = "repaired"` when `repairToolInput` returned a fixed call.

   **Before relying on it**, pin with an integration test what the AI SDK does with a call to
   an inactive tool on 7.0.84: whether `repairToolCall` sees it at all, and what the model
   receives. If the SDK never routes it there, detect it where it does surface, and say so in
   the PR. A refused call that is later repaired is recorded once, as `repaired`.
6. **`reached_proposal`.**
   - Write tools are collect-only, so a call reached the proposal if and only if a command it
     collected is in `ProposalBuffer.collected()` at the latch and not in `droppedCalls`. That
     needs the buffer to tag what it collects with the `callId`.
   - Read tools record null.
   - Confirm that the buffer at the latch is exactly what `buildProposal` consumes. The
     proposal is built in `messageMetadata` *after* `onEnd`
     (`handleAskRequest.ts`, the "`onEnd` just runs first" comment). If anything is added
     between the two, this definition is wrong and the PR stops to say so.
7. **One write.** `recordAiUsage(ledger)` becomes `recordTurnLedger(ledger)`.
   - It writes the `ai_usage` row, its steps and its tool calls in **one transaction**.
   - Steps and tool calls upsert on their primary keys, so a replayed write leaves one row.
     That is the property the eve instrumentation will need (ADR-062 §5).
   - It still never throws, and it logs `"ai_usage row was not written"` on failure.
   - Integration test (`usage.int.test.ts`): write the same ledger twice and count one turn,
     its N steps and its M calls.
8. **All three end paths (KI-2026-09-14-b).** Move the sink's writes (`recordTurnLedger` and
   `settleAiSteps`) under Next's `after()` at the **route-handler boundary**, as the KI
   proposes.
   - `handleAskRequest` returns the work, and the route registers it, because `after()`
     throws outside a request scope and the integration tests call `handleAskRequest`
     directly.
   - `route.int.test.ts`'s abort test drops its `vi.waitFor` and asserts synchronously.
   - Move the KI to `resolved/` in the same PR.
9. **The money guard covers the new tables.** `usage.noMoney.test.ts` asserts the same
   column-name pattern over `aiUsageSteps` and `aiUsageToolCalls`, and the same SQL pattern
   over migration `0035`. **Seen red** by adding a `cost_micro_usd` column locally.
10. **Sentry stays as it is**, except `ai.tool.duration` gains an `outcome` attribute from the
    new field. No new metric names.

## Part 2 — the readers

1. **Cached reads have a rate.** `ModelRate` gains an optional
   `cacheReadInputMicroUsdPerMTok`. Absent means cached reads are priced at the input rate,
   which overstates rather than understates.
   - Append **new dated entries**, effective the day the PR merges, for each model in use,
     with the Gateway's current cached-read price. **Never edit the frozen ones**: the record
     is append-only.
   - `handleAskRequest.ts` cites $0.028/MTok for deepseek cached reads. Verify that against
     the Gateway's model page on the day; do not copy it.
   - `microUsdFor` gains the cached-read argument. Its safe-integer tests extend to the new
     field.
2. **A turn is priced from its steps (KI-2026-09-17-c).**
   - One pure function, `microUsdForTurn(steps, classifier, at)`, sums `microUsdFor` per step
     at that step's model.
   - A turn with no step rows (anything before part 1) falls back to the existing
     `turn_model` pricing.
   - `ai_usage.turn_model` **keeps its meaning**: the admitted model. The KI's open question
     is answered as *"one value, and the per-step rows carry the truth"*.
   - `server/billing/revenue.ts` and the admin overview's margin read through the new
     function.
   - An integration test escalates a turn, deepseek then the edit-tier model, and sees the
     priced total move. It is seen red against the old single-model pricing.
   - Move the KI to `resolved/`.
3. **The `ai-usage` skill answers from the database.**
   - Add `.claude/skills/ai-usage/ledger.sql`: named, read-only queries over a `since`
     window, excluding simulated turns.
     - Tool failure rate per tool, where failed = `failed + repaired`, with
       `refused-by-grant` as its own column.
     - p50 and p75 `duration_ms` per tool.
     - Calls per turn per tool, and the tools that never ran.
     - Tokens per turn at p50 and p75, with the cached-read share.
     - Proposal-reached rate over change-intent turns, from `task_class`.
     - Escalation rate, and the tokens spent after escalation.
     - p75 turn latency. **This needs a column part 1 does not add.** Either add
       `ai_usage.latency_ms` in part 1's migration (preferred, since the recorder already
       computes `latencyMs`) or keep latency log-only. Decide in part 1 and say which.
   - Update `SKILL.md`:
     - a *From the database* section that runs these through the Neon MCP `run_sql` on the
       production branch, read-only, or through `psql` against a local database;
     - fix line 15's path to `apps/web/src/server/assistant/askAnalytics.ts`;
     - remove the *"no table, no migration"* claim.

     The log-line analyses stay; they carry the question text that the tables deliberately do
     not.
4. **The live set is a file.** Add `apps/web/src/server/ai/eval/live-set.json` with the
   fifteen prompts M31's gate proposes:
   - the five replay transcripts' openers;
   - five change-intent prompts;
   - five question-only prompts.

   Each entry has an `intent` label and a target trip from the seed. Add
   `scripts/assistant-live-set.mjs <url>`, which:
   - runs each prompt three times as one dedicated account, against any deployment;
   - tags nothing new: the account and the time window identify the run;
   - prints the SQL window for the skill's queries.

   It spends real model calls. It refuses to run unless `--confirm` is passed, and refuses
   against production.
5. **Fix the stale schema comment** that names `aiUsage.noMoney.test.ts`.

Verification for part 2: as for part 1, plus `ledger.sql` run against the test database after
`usage.int.test.ts`'s fixtures. Each query returns rows, and a query that divides is seen to
handle zero calls.

## Out of scope, on purpose

- `ask.apply` usage rows. The route makes no model call, and Phase 3 turns apply into a tool
  whose call is a row in `ai_usage_tool_calls`.
- Any `eve` code, `agent/` directory or dependency.
- Agent Runs, and changes to the OpenTelemetry pipeline.
- Retention or deletion policy for these tables. They hold no user text, so they follow
  `ai_usage`'s existing account-deletion path; the PR confirms that path covers them.
