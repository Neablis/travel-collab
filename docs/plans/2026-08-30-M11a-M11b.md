# M11a — the invite gate

## The three facts that shape it

**1. `recordSignIn` is wired by direct reference**, not through a wrapper —
`server/auth.ts:16-19` is `signIn: recordSignIn`. The admission call therefore
lands *inside* `recordSignIn`, which is also where the milestone puts it.

**2. Returning `false` cannot say why.** `@auth/core@0.41.3`'s
`handleAuthorized` (`lib/actions/callback/index.js:393-409`) collapses every
falsy return to `AccessDenied`, one code for all three refusals — but a
**string** return is passed to the `redirect` callback and honoured
(`init.js:13-19` allows any path starting `/`). Link 6's three distinct
messages are reachable only that way.

> **This changes a documented interface.** ADR-025 §Decision 4 specifies
> `recordSignIn` as fail-closed boolean. It becomes
> `Promise<boolean | string>`, and ADR-025 gets an amendment in the same PR —
> not a silent widening. The fail-closed property is *preserved*: the no-id
> path still returns `false`, and a database failure still propagates.

**3. `upsertUser` cannot tell us whether the row was new.** It is a bare
`onConflictDoUpdate` (`users.ts:55-73`) with no `RETURNING`. Admission is
defined as "has no `users` row", so the check needs a read *before* the upsert.
Do not try to infer it from the upsert.

## The shared contract between the parallel units

Fixed here so two agents cannot disagree about it.

- **Cookie:** name `pending_admission`; `httpOnly: true`, `sameSite: "lax"`,
  `path: "/"`, `maxAge: 600`, `secure` when not localhost. Written by
  `proxy.ts` (token) and by the `/signup` form (code). Read **and cleared** in
  `recordSignIn` on both success and refusal.
- **Refusal redirect targets**, the exact strings `recordSignIn` returns:
  - `/signin?error=InviteRequired` — no code and no token presented
  - `/signin?error=InviteInvalid` — presented, not recognised
  - `/signin?error=InviteSpent` — a single-use code already redeemed
- **`ERROR_MESSAGES` keys** in `authCopy.ts` gain exactly those three.
  `errorMessage()` already falls back rather than throwing, so a missing key
  degrades to `FALLBACK` instead of breaking.

## Unit A — server (own worktree)

Files: `server/admission.ts` (new), `server/users.ts`, `server/db/schema.ts`,
`drizzle/0011_*.sql` + `meta/`, `server/admission.int.test.ts` (new),
`server/users.int.test.ts`.

- `invite_codes` table: `code` (text, PK or unique-indexed), `createdAt`,
  `createdBy`, `redeemedBy` (nullable), `redeemedAt` (nullable). Follow
  `savedDays`' `mode: "date"` rule (KI-53), and `0009`'s `IF NOT EXISTS` +
  `--> statement-breakpoint` style. Migration is `0011_<tag>.sql` and needs a
  `meta/0011_snapshot.json` and a `_journal.json` entry — generate it with
  `pnpm --filter web db:generate`, never by hand.
- Redemption mirrors `acceptInvite`'s proven construction
  (`access/invites.ts:287-296`): `UPDATE … SET redeemed WHERE code = ? AND
  redeemed_by IS NULL RETURNING`, then `claimed[0] === undefined` ⇒ lost the
  race ⇒ re-read to tell "spent" from "never existed". **Do not invent a
  second pattern**; this one already survived review.
- Trip-invite admission (Link 2) is `status = 'pending'` on `trip_invites` —
  revocation writes `status = 'revoked'`, so pending alone already implies
  unrevoked (`invites.ts:290` is the precedent).
- The super code (Link 3) is one env var, compared in **constant time**, and
  **absent-means-closed**: an unset variable must never admit everyone.

## Unit B — front door (own worktree, disjoint from A)

## Unit C — proxy + e2e (after A and B)

Files: `src/proxy.ts`, `e2e/auth.setup.ts`, `e2e/smoke.spec.ts`,
`e2e/m11-invites.spec.ts`, `e2e/helpers.ts`, `playwright.config.ts`.

- `proxy.ts` sets the cookie on the redirect it *already builds*
  (`proxy.ts:54-64`); `NextResponse` is already imported. **It must not import
  `server/admission.ts`** — it runs in the Edge runtime with no database
  (ADR-024), and the lint wall does not exempt it. It stores; it never
  validates.
- `playwright.config.ts`'s `webServer.env` needs the super code, or every spec
  fails at `auth.setup.ts`.
- **`m11-invites.spec.ts` is the prize.** It signs in bob/carol/dan as brand-new
  dev users with no `users` row — exactly the population the gate refuses. Point
  its `signedInAs` at the real flow instead: click `/invite/<token>`, let the
  proxy store the token, sign in, be admitted by Link 2. That converts the "M11
  invite→accept→edit still works for someone who has never signed in" box from
  a manual walk into a CI assertion.

## What M11a's gate cannot prove here

The three "walked in a browser" boxes need a real Google round trip, and KI-50
blocks that from any preview host not hand-registered. Flagged to Mitchell;
`AUTH_REDIRECT_PROXY_URL` on the Preview environment is KI-50's own fix path and
covers every future branch. Everything else — refusal, single-use under
concurrency, existing users unaffected, cookie lifecycle — is provable here.

saved days — for **two** owners, or the profile/Discover agreement is vacuous.

`packages/domain/src/trip/cities.ts:34`, with the decisions link 1 needs already

`SavedStop[]` — **factor the shared core, do not write a second rule.** A
divergence here is precisely how Discover and a profile come to disagree.

Also: `expectations.ts:55` already tracks a `cities` baseline, and
`JapanTripExpectations` is typed, so a new report field forces the baseline
