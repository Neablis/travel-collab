### KI-2026-09-05-i — widget-layer debt: an unreachable `count{of}`, five dead vocabulary items, a property test speaking a retired vocabulary, a hand-listed prompt line, and an undocumented refresh model

- **Severity:** cleanup — five LOW findings, all CONFIRMED, none with a user-visible defect today. Bundled as one entry; strike a line as it lands and close when all five are struck.
- **Area:** `packages/pages/src/macros/primitives/single.ts:78-82`, `presets.ts:73-88`, `presets.test.ts:49-54`, `registry-types.ts:156,167,323`, `result.ts:22`, `registry.ts:54-64`, `registry.property.test.ts:83-104`, `packages/contracts/src/pages.ts:241-242`, `apps/web/src/server/ai/handleAskRequest.ts:1013`, `apps/web/src/components/pages/PageScreen.tsx:118-143`
- **Symptom / What happens:**
  1. **[F-B05](../../reviews/2026-09-05-overnight-review/findings/F-B05-count-of-day-city-has-no-preset.md) — `count{of: "day" | "city"}` has no preset**, so "how many days / how many cities" is code only the AI can reach (through `primitiveCatalog()` and the prompt line). Two preset rows fix it; the guard is generalising `presets.test.ts:49` so every enum value of every `nonFilterParams` entry must appear in some preset. Same shape as KI-2026-09-02-d.
  2. **[F-B06](../../reviews/2026-09-05-overnight-review/findings/F-B06-dead-widget-vocabulary-reads-as-seams.md) — five dead vocabulary items read as seams:** the `days`/`trip` input types no dimension maps to, `UnboundNeeds.days` (so `MacroView.tsx:133-134`'s "no days set" branch is unreachable), `ItemScope` (`resolve` is never called with `item`), `resolveMacro` (test-only callers) and `MacroKind` (one comment). Each is a decision the next contributor has to make; `resolveMacro` and `MacroKind` can go now, the other three depend on whether the repeat-template row is the next ADR.
  3. **[F-B07](../../reviews/2026-09-05-overnight-review/findings/F-B07-resolver-property-test-uses-retired-vocabulary.md) — the resolver property test's generator speaks the retired v1 vocabulary** (`dayRef`/`dayId`/`dayNumber`), and every schema is `filterParams(...).strip()`, so every case parses to `{}` and the `unbound` path its comment claims to exercise is never reached. False since 2026-09-04. Totality still holds. The `witness` floor cannot see this, because the assertion count is unchanged — generate from `FILTER_VALUE_SCHEMAS` and assert an `unbound` outcome is observed.
  4. **[F-B08](../../reviews/2026-09-05-overnight-review/findings/F-B08-prompt-hand-lists-non-filter-params.md) — the assistant prompt hand-enumerates the non-filter params** that `primitiveCatalog()` already derives, beside the derived catalogue, with the `compose_page` precedent (the same hand-list going stale) recorded ten lines above it.
  5. **[F-B04](../../reviews/2026-09-05-overnight-review/findings/F-B04-notebook-never-refreshes-trip-detail.md) — an open notebook fetches trip detail once and never refreshes it**, so a day deleted in another tab keeps rendering until reload (after reload the path is correct: `narrow` → `unbound("day")` → "that day was removed"). **This is not a notebook bug** — `TripProvider` fetches on mount only too, there is no `visibilitychange`, `EventSource`, `setInterval` or `useSyncExternalStore` anywhere in `apps/web/src`, and the one asymmetry is that `usePreferences`'s `user` *does* refresh. So a fix scoped to `PageScreen` would **create** the asymmetry the finding first described. Either put a focus/`visibilitychange` refetch in the shared trip source that both board and notebook consume — the notebook then inherits it through `MacroEditorContext`, which is already reactive and currently has nothing feeding it — or record the model ("trip detail is fetched on navigation") in ADR-012 so the next reader does not rediscover it.
