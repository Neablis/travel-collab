### KI-2026-09-15-a — the quota refund path has no direct SQL test and no property coverage, so its two guards are proven only indirectly

- **Severity:** reliability of verification (no known defect — the guards are correct today; what is missing is the test that would catch them regressing)
- **Area:** `apps/web/src/server/quota.ts` (`pgCounters.release`), `apps/web/src/server/quota.int.test.ts`, `apps/web/src/server/quota.property.test.ts`
- **Symptom / What happens:** `release` is the only path in the quota module that can *decrease* a counter, and it carries two guards that exist to stop specific holes — an exact-window match (`eq`, not `gte`) so a refund cannot subtract from a window it never charged, and a `greatest(hits - by, 0)` floor computed server-side so concurrent releases cannot drive a counter negative. Neither guard has a test that exercises the real SQL:
  - `quota.int.test.ts` (the only suite that reaches Postgres) has no test that calls `pgCounters().release` directly. The SQL is exercised only *transitively*, through `route.int.test.ts`'s refund assertions.
  - `quota.property.test.ts`'s `fakeCounters().release` is `async () => {}` — a no-op. That is honest today, because nothing the property suite drives invokes `release`; but it means the refund invariant has no property coverage at all, while `bump`'s monotonicity does.
- **Why it matters more than "a missing test":** the in-memory fake and the SQL implementation currently agree on every guard, and that agreement is what makes the unit tests meaningful. Nothing enforces it. If the SQL's `eq` were widened to `gte`, or the floor moved from SQL into JS, every unit test would still pass — only the indirect route-level assertion would notice, and only if it happened to straddle a window boundary.
- **How it was found:** the scoped re-review of the KI-94 fix wave (2026-09-15) listed both as deferred, out-of-scope observations. Neither is a regression from that work; both predate it by one commit — they arrived with `release` itself.
- **Why it was not fixed with the change that found it:** the fix wave was dispatched against five named review findings, and adding coverage for a sixth would have widened a security-sensitive diff that was already on its second review. A property test over reserve/release interleavings is also its own design question — it is the shape KI-2026-09-05-p asks for on the optimistic send queue, and it deserves the same deliberate treatment rather than being appended to a fix round.
- **Fix path, if taken:** an int test calling `pgCounters().release` directly against the two guards (a refund against a rolled window must be a no-op; an over-large refund must floor at zero rather than go negative), and a property that drives reserve → settle interleavings through the real counters rather than the no-op stub. The second closes the fake-vs-real divergence risk as a class, not as two cases.
- **Cross-reference:** KI-94 and KI-97 (resolved 2026-09-15 — the change that introduced `release`); KI-2026-09-05-p (the same "fixed as lines, never as a property" shape, on the optimistic queue); `docs/plans/2026-09-15-M9-01-step-quota-concurrency.md`.
- **Milestone:** unassigned. Not an M9 gate box — M9's step-ceiling box is about the ceiling holding, which it now does and is tested.
- **First noted:** 2026-09-15, in the scoped re-review of the KI-94 fix wave.
