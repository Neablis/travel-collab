### KI-2026-09-06-h — preview and production shared one database, and both production workflows wrote to a different one nobody read

- **Severity:** correctness — the highest-impact configuration defect found so far. No code was wrong; every rail was pointed at the wrong target.
- **Area:** Vercel environment variables (Neon integration), `PRODUCTION_DATABASE_URL` repo secret, `.github/workflows/{migrate-production,import-content-production}.yml`, `apps/web/scripts/vercel-build-migrate.mjs`, `docs/guidelines/environments-and-deploys.md`
- **Symptom / What happens:** two Neon projects existed with connection strings differing **only in host**, both using database `neondb` and role `neondb_owner`:
  - `spring-river-40823685` (Neon org "Vercel: neablis' projects", `managed_by: vercel`, branch **`main`**, endpoint `ep-steep-rice-afhxw55b`, us-west-2) — **what caesura.today actually read and wrote.** 30 users, 59 trips, 3,375 events.
  - `sweet-poetry-62369474` ("travel-collabe", personal Neon org, branch **`production`**, endpoint `ep-nameless-brook-ad7v04r6`, us-east-1) — **what `secrets.PRODUCTION_DATABASE_URL` pointed at.** Nothing read it.

  Three consequences, all silent:
  1. **Both production workflows wrote to the unread database.** `migrate-production` and `import-content-production` share the one secret. The 2026-09-06 content library (#153) — 148 playbook days across 19 bundles, 7 trips, the `service-ai-library` account — landed entirely in `travel-collabe`. The served database had **zero** rows with `source_bundle` set. Every run reported success, because it *was* successful; it just wrote where nobody looked.
  2. **Preview and Production shared one `DATABASE_URL`.** The Neon Vercel integration injects it scoped "Production and Preview" — one value, both scopes — from 2026-07-21. So `vercel-build-migrate.mjs`, whose only condition was `VERCEL_ENV === "preview"`, ran `drizzle-kit migrate` **against production on every preview build**. Migrations 0015-0018 reached the live database that way, never via the dispatch-gated workflow built to do it.
  3. **Preview writes landed in production.** Dev login is preview-only; production held **12 `dev-*` users owning 43 of its 59 trips**. `/api/dev/reset-demo-data` (`VERCEL_ENV=preview` + `SEED_DEMO_DATA=true`) would write demo data there too.
- **How it was found:** Mitchell was refused at the front door with `/signup?error=MISSING_INVITE_CODE` on an account he had. That was PR #150's unmigrated orphan rows (see below), but chasing it turned up `invite_codes` empty and the content library absent from the served database — neither of which was explicable until both databases were queried side by side.
- **What made it invisible for six weeks:**
  - **The branch named `production` was not production.** Someone choosing a connection string by name would pick exactly the wrong one, which is presumably what happened.
  - **The two connection strings differ only in host.** Same database name, same role. Nothing in a pasted string says which project it belongs to.
  - **The gated path was the broken one.** `migrate-production` is dispatch-only, `main`-only, and needs `migrate` typed to confirm — and it wrote to the dead database. `vercel-build-migrate.mjs` had one unreviewed condition and wrote to the live one. The care was spent on the wrong door.
  - **`environments-and-deploys.md` described a topology that had not existed since August** — a `preview` branch archived on 2026-08-28, and a `main` branch in a project the secret did not name. The doc was confidently wrong, which is worse than silent.
- **Fixed here:** only the rail. `vercel-build-migrate.mjs` now requires **`PREVIEW_DB_IS_DISPOSABLE=true`** in addition to `VERCEL_ENV=preview`, and **fails the build** without it. `VERCEL_ENV` describes where the build runs and says nothing about the connection string; the new variable is set by hand on the Preview scope only and cannot be satisfied by drift. Fail-closed follows `matchesSuperCode`'s reasoning in `server/admission.ts` — the two failure directions are not symmetric.
- **Still open (the reason this entry exists):**
  1. **`PREVIEW_DB_IS_DISPOSABLE=true` must be set on the Preview scope**, or every preview build now fails. That is the intended posture, but it is a live blocker until done.
  2. **`PRODUCTION_DATABASE_URL` must be repointed** at whichever database production actually reads, as the direct/unpooled host.
  3. **Preview needs its own database.** Until Preview's `DATABASE_URL` differs from Production's, rule 1 of the guideline is still violated; the rail only stops the migration half, not dev-login writes or demo-data seeding.
  4. **The content library still is not in the served database.** Re-run `import-content-production` — dry-run first, and **without `--prune`** on a database that has never seen a bundle.
  5. **Production's data is unreconciled**: 12 dev users, 43 preview-seeded trips, and PR #150's orphan rows (below).
  6. **How `spring-river` came to be migrated at all is not fully established.** Preview builds are the only automated path found that could have applied 0015-0018 to it, and that fits the dates — but `travel-collabe`'s `preview` branch shows compute activity until 2026-08-27, which that story does not explain. Treat as unresolved.
- **Related, and not the same bug:** PR #150 (`cd0551c`) fixed identity being keyed off Auth.js's throwaway `user.id`, but its own commit message defers the data migration — "Does NOT recover the existing orphaned rows". That migration was never written or tracked. In the served database this left **14 UUID-keyed `users` rows sharing one email**, with 1,383 events and 25 pages stranded on identities no sign-in resolves to, and any returning Google user refused as a stranger. That is the symptom that started this investigation and it needs its own entry or PR.
