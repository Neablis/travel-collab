### KI-2026-09-12-b — agent worktrees appear not to run `SessionStart`, so nothing installs dependencies or links Playwright in them

- **Severity:** reliability of local verification in subagent worktrees (no product impact; CI is unaffected and remains the authoritative e2e signal). It costs a worktree session a wrong conclusion — that the container has no usable browser — which is KI-32's symptom wearing a different cause.
- **Area:** the harness's worktree provisioning for `Agent` calls with `isolation: "worktree"` (`.claude/worktrees/agent-*`), against `.claude/hooks/session-start.sh`'s `CLAUDE_CODE_REMOTE` branch (`pnpm install` → `pnpm run setup` → `start_postgres` → `link_playwright_shell`). Related: **KI-2026-08-30-c**, which records the neighbouring fact that these worktrees are seeded from a stale `main`.
- **Symptom:** a `ki-fixer` worktree observed on 2026-09-12 had `CLAUDE_CODE_REMOTE=true` and **no `node_modules` at all** — neither `node_modules` nor `apps/web/node_modules` existed. That state is impossible if the hook's remote branch ran, because its **first** statement is `pnpm install`. Agents in these worktrees consequently run `pnpm install` by hand before they can run any check, and Playwright's browser links are never created.
- **Why it is filed now:** it was found while closing **KI-2026-09-07-b**, whose stated cause ("`SessionStart` fires before anything runs `pnpm install`") turned out to be wrong — the hook installs three lines before it links, and has since `e098d19`. The ordering was never the defect. The hook **not running at all** explains the same observed failure and was not previously written down. Closing KI-2026-09-07-b without recording this would have retired KI-32's fourth recurrence against a cause that is not the cause, and invited a fifth.
- **Scope:** establish whether `SessionStart` fires for worktree-isolated subagent sessions at all; if it does not, decide whether it should, or whether worktree provisioning should run the same install/setup/link steps itself. Note the hook is written to be safe to run repeatedly (`start_postgres` and `link_playwright_shell` are both idempotent, and `pnpm install` is a lockfile check once dependencies exist).
- **Why not fixed here:** it is harness/provisioning behaviour rather than repo code, so a worktree agent cannot fix it from inside a worktree — the same class of limit `KI-2026-08-30-c` records. The 2026-09-12 sweep had no way to change how its own agents were provisioned.
- **Second consequence, found the same day: a duplicate `@playwright/test`.** Because each worktree hand-installs, `@playwright/test` resolves to `.claude/worktrees/agent-<id>/node_modules/.pnpm/@playwright+test@1.62.1/...` there, while the main checkout holds its own copy of the **identical version** at `/home/user/travel-collab/node_modules/.pnpm/@playwright+test@1.62.1/...`. Two physical paths, two module identities — which is what raises `"Playwright Test did not expect test() to be called here"` when the runner loads one and a spec imports the other. That error was briefly mis-filed as a CLI defect (`KI-2026-09-12-c`, withdrawn the same day: every documented filter form works fine on the main checkout). So this entry costs more than a hand-run `pnpm install` — it makes the e2e lane behave differently inside a worktree than anywhere else, in a way whose error message points at the wrong thing.
- **First noted:** 2026-09-12, during the overnight KI sweep, while closing KI-2026-09-07-b.
