  2. ~~**[F-D05](../../reviews/2026-09-05-overnight-review/findings/F-D05-minimumreleaseageexclude-is-inert.md) — `minimumReleaseAgeExclude` is inert and stale.** Three exclusions were committed on 2026-08-30 to bypass a *machine-level* release-age quarantine; there is no `minimumReleaseAge` anywhere in the repo and no `.npmrc`, so in-repo the block does nothing while advertising a supply-chain control that is not configured. Either set `minimumReleaseAge: 1440` and delete the exclusions — the control for free — or delete the block so it stops implying one.~~
     **FIXED 2026-09-25, and the premise was half wrong.** The block was stale but not inert. pnpm 11 (the repo pins 11.25.0) ships `minimum-release-age: 24 * 60` as a **built-in default** (`dist/pnpm.mjs`), in "loose" mode: a too-new pick is added to `minimumReleaseAgeExclude` automatically and installed anyway (pnpm CHANGELOG 11.1.3). The finding was written against pnpm 10.28, where the default was 0. Evidence: pnpm's lockfile-verification cache (`~/.cache/pnpm/lockfile-verified.jsonl`) recorded this repo's effective policy as `"minimumReleaseAge": 1440` plus the three exclusions, with no value set anywhere in the repo. And on a scratch project with no config, `pnpm add vite@8.3.1` (published 2026-09-24T12:26Z) printed `Added 1 entry to minimumReleaseAgeExclude in pnpm-workspace.yaml … vite@8.3.1` and exited 0. That is almost certainly where the three `@ai-sdk`/`ai` exclusions came from. They were also stale: they pin `@ai-sdk/gateway@4.0.26`, `@ai-sdk/provider-utils@5.0.12` and `ai@7.0.34`, but the lockfile holds 4.0.68, 5.0.33 and 7.0.84. The fix, in `pnpm-workspace.yaml`: set `minimumReleaseAge: 1440` explicitly, delete the three stale exclusions, and add a comment. An explicit value switches pnpm to strict mode. The same scratch project with `minimumReleaseAge: 1440` failed with `[ERR_PNPM_NO_MATURE_MATCHING_VERSION] 1 version does not meet the minimumReleaseAge constraint: vite@8.3.1 was published at 2026-09-24T12:26:19.940Z, within the minimumReleaseAge cutoff`, exit 1. Proof that frozen installs cost nothing: `pnpm install --frozen-lockfile` under the new policy (cache miss, so a real re-verification) printed `✓ Lockfile passes supply-chain policies (1174 entries in 4.5s)`, exit 0, and no files were rewritten.
     - **Decision (2026-09-25 overnight sweep):** turn the control on explicitly (strict) and drop the stale exclusions. **Rejected:** *delete the block*. The protection would stay, but pnpm's loose default would silently grow the block again on the next too-new pick, so this is not a real "off" switch. **Rejected:** *leave the three exclusions*. They name versions the lockfile no longer contains, so they exempt nothing. Cost of this choice: any fresh resolution of a version less than a day old fails outside a terminal (CI, agents) and prompts inside one. **Dependabot bumps younger than a day will be held or fail to resolve**, and so will `pnpm add x@latest` right after a release. To take one on purpose, add a `name@version` line under `minimumReleaseAgeExclude`. Not verified: which pnpm version Vercel's build uses. pnpm 10.16+ applies the setting only at resolution time, and pnpm 11 already applies 1440 by default, so a frozen install behaves the same on either.
