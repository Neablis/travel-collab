### KI-2026-09-14-b — the `ai_usage` row is best-effort on the abort and error paths

- **Severity:** a lost billing row, rarely. The completed path — every turn that finishes — now awaits the write inside the request's own lifetime, so this is the tail: a turn the user abandoned, or one the provider failed partway through.
- **Milestone:** **M9, carried (assigned 2026-09-24, KI pass)** — owned by M9, not a gate box. Parked under Mitchell's 2026-09-01 rule that every open AI known issue belongs to M9; filed after that audit, so it had no owner until now. Listed in `docs/milestones/M9-ai-planning-partner.md` § *Parked 2026-09-24*.
- **Area:** `apps/web/src/server/ai/handleAskRequest.ts` (`settled`, and the recorder's `sink`), writing through `apps/web/src/server/entitlements/usage.ts`'s `recordAiUsage`.
- **What is wrong:** `settled` is awaited from `onEnd`, which the SDK awaits — so a completed turn cannot finish before both the step settlement and the `ai_usage` insert have landed. The recorder's single-writer latch also fires on **abort** and **error**, and those two do not await anything: the response is already gone or already failing. On Vercel the invocation may stop once the response closes, so an in-flight INSERT on either path can simply be dropped. M20's gate box says *"a request that fails partway still writes a row — the round-trips were still paid for"*, and on the error path that is currently true in code and eventual in practice.
- **How it came to light:** CodeRabbit on PR #174 flagged the `ai_usage` write as unawaited, which was true of **all three** paths — it was a bare `void recordAiUsage(ledger)`. Fixing the completed path (tracking it on `settled`) left the other two, and the integration test added alongside made the remaining gap visible: asserting the abort row synchronously passed when the file ran alone and failed in the full suite. The test now uses `vi.waitFor`, which is the honest shape for an eventual guarantee and is also the evidence this entry exists.
- **Why not fixed there:** the mechanism for "run this after the response is sent, and keep the invocation alive" is Next's `after()` (`next/server`, present in 16.3.3). It throws when called outside a request scope, and **every integration test in this repo drives `handleAskRequest` directly rather than through the route handler** — so adopting it means either a try/catch fallback on the one path that most needs to be reliable, or moving a large suite onto the route. Neither is a line in a review fix, and the same trade already applies to `settleAiSteps`, which has been best-effort on these two paths since ADR-033 without being written down.
- **Scope:** wrap the sink's writes in `after()` at the route-handler boundary rather than inside `handleAskRequest`, so the request scope is guaranteed and the handler stays directly callable; then drop the `vi.waitFor` in `route.int.test.ts`'s abort test back to a synchronous assertion, which is what proves the guarantee became immediate. Settle `settleAiSteps` the same way in the same pass — the two writes have the same lifetime and should not have two different guarantees.
