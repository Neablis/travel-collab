  1. ~~**[F-A02](../../reviews/2026-09-05-overnight-review/findings/F-A02-page-content-unbounded-on-write.md) — notebook title and content are unbounded on write.** `title` is `z.string().min(1)` with no `.max`; text nodes have no max; row count is unbounded. Storage abuse by an admitted editor, not an anonymous vector. Contrast `/ask`, which measures a 128 KiB cap on the raw body. This is the 2026-08-28 review's L5, still open.~~
     **FIXED 2026-09-25.** Two bounds, both on the write path only. (a) Every notebook write's body is capped at `MAX_PAGE_BODY_BYTES` = 512 KiB (`server/pages.ts`) in bytes, before it is parsed: the session routes pass `{ maxBytes }` to `readBody` (new option; 413 naming the limit), and the two `/api/v1` page routes declare `maxBodyBytes` (the public API's named-limit 400), so a token is not the way round it. `readCapped` — the chunked, cancel-on-the-way-past reader — moved from `server/public-api/route.ts` into `server/readBody.ts` so both share it. (b) `CreatePageInput.title` / `UpdatePageInput.title` are `.max(PAGE_TITLE_MAX)` = 200 (contract change: CHANGELOG entry, round-trip test in `packages/contracts/test/pages.test.ts`, `openapi.json` regenerated). `Page`, the page commands and the page events are deliberately untouched, so a page stored larger still reads and replays (asserted in the same contract test). No per-text-node cap: the byte cap already bounds every node, and `PageDoc` is shared with the events a replay parses. **Reproduction:** new `describe("a notebook write is bounded")` in `app/api/trips/[tripId]/pages/route.int.test.ts`, before the fix: `AssertionError: expected 200 to be 413` (PATCH of 512 KiB + 1), `expected 201 to be 413` (POST), `expected 201 to be 400` (a 201-character title). **Proof:** green after, with a body exactly at the cap accepted (201) and every shipped template and bundled notebook still saving; `surface.int.test.ts`'s new v1 case red with the PATCH route's `maxBodyBytes` commented out (`expected 200 to be 400`), green restored; the contract test red with `CreatePageInput`'s `.max` removed (`expected true to be false`), green restored.
  2. ~~**[F-A03](../../reviews/2026-09-05-overnight-review/findings/F-A03-sentry-example-route-ships-to-production.md) — the Sentry wizard leftovers ship.** `api/sentry-example-api/route.ts` has no `auth()` and throws on every GET; it is the only route in the tree with no product purpose and no authz check, so anyone can drive error volume into the Sentry project in a loop.   3. ~~**[F-A04](../../reviews/2026-09-05-overnight-review/findings/F-A04-member-emails-sent-to-any-viewer.md) — every member's email crosses the wire to any viewer.** `TripMemberProfile.email` is populated by `withProfiles` and served by the viewer-minimum access route; the only `.email` render anywhere is the owner-only invites list.      **FIXED 2026-09-24.** `withProfiles(members, viewerId)` now fills `email` only for the trip owner (the projection's head, `members[0]` — not the viewer's role, which a stray granted `owner` row could inflate; PR #220 review) and for the viewer's own row; everyone else — another member, or a stranger holding an invite link on the look-first view — gets `null`, which `displayNameFor` already falls through to the name or the handle.   4. ~~**[F-A05](../../reviews/2026-09-05-overnight-review/findings/F-A05-csrf-rests-on-samesite-lax-alone.md) — CSRF posture rests on Auth.js's default `SameSite=Lax` alone.** Adequate today (all mutations are non-navigation POST/PATCH/DELETE; residual is legacy-browser only), but one cookie-config change or an embedded surface needing `SameSite=None` makes every write CSRF-able and nothing would say so. This is the 2026-08-28 review's L6. Filing it here **is** the "record the decision" half of its suggested fix.~~
     **FIXED 2026-09-25 (decision recorded, attribute pinned).** The decision is in `SECURITY.md` → *Things worth knowing before reporting*: CSRF protection is `SameSite=Lax` alone, why that holds (every cookie-authenticated mutation is a non-navigation `POST`/`PATCH`/`PUT`/`DELETE`; bearer tokens and the one server action are outside it), the residual (legacy browsers), and the rule that whoever needs `SameSite=None` adds an Origin check on mutations first. The mechanical half: a new `describe` in `apps/web/src/lib/authConfig.test.ts` builds a real `NextAuth(authConfig)`, sends `GET /api/auth/session` with an undecodable session cookie so Auth.js clears it with its real options, and asserts the `Set-Cookie` carries `SameSite=Lax|Strict` — on https (`__Secure-` name) and on http. It reads the wire, not `authConfig.cookies`, so an Auth.js upgrade that moved the default is caught as well as a config override. `vitest.unit.config.ts`'s node project now inlines `next-auth` (Node's ESM loader refuses its extensionless `next/server` import; no unit test had loaded it unmocked). **Proof:** with `cookies: { sessionToken: { options: { sameSite: "none" } } }` added to `authConfig`, both cases fail — `AssertionError: expected '__Secure-authjs.session-token=; Max-A…' to match /;\s*SameSite=(Lax|Strict)(;|$)/i` (and the same for `authjs.session-token`); restored, `authConfig.test.ts` 30/30.
