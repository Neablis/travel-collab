### KI-2026-08-30-f — Our geocoder structurally cannot corroborate small independent venues, and eight of the demo trip's stops are exactly that class
- **Severity:** cleanup (no product impact — every affected stop has a correct hand-authored coordinate) — but it is the reason the geocode cross-check has never converged, and it will recur on any trip that is not built from landmarks
- **Area:** `apps/web/src/server/geocoding/locationiq.ts` (the vendor adapter), `apps/web/scripts/geocode-japan-seed.mts`, `packages/fixtures/src/japan/coordinateGaps.ts` (the record this entry explains).
- **What the 2026-08-30 live run showed.** Of 72 stops, 41 corroborated. Eight returned a definitive vendor negative — HTTP 404, `{"error":"Unable to geocode"}` — and rerunning changes nothing: Hippari Dako, Koffee Mameya, Nazuna Kyoto Gosho, Omen Kodaiji, Giro Giro Hitoshina, Ippodo Kaboku, Aisunao, Tonkatsu Maisen.
- **The pattern is structural, not random.** Every one is a small, independent, owner-operated Japanese venue — a counter-only roastery, a house-restaurant on an island of 3,000 people, the tearoom annexe of a shop. LocationIQ is OpenStreetMap-derived, and OSM's coverage of that class in Japan is thin. The same eight will fail on every rerun, forever, at any effort we spend on query shaping. **This is not a bug to fix; it is a capability we do not have.**
- **Why it matters beyond the demo fixture.** The Japan trip is hand-authored, so its coordinates are right regardless. A *user's* trip is not: the same class of venue is exactly what a well-planned trip is full of, and today the product's answer for them is ADR-007's server-side enrichment — the same vendor, the same 404. So this bounds what "we put your stops on the map" can honestly promise, and it does so invisibly.
- **Options, none taken, roughly in cost order:**
  1. **Accept and record** — what `coordinateGaps.ts` now does for the fixture. Cheap, honest, and does nothing for users.
  2. **A second provider for the gap set only.** Google Places and Foursquare both carry small commercial venues far better than OSM. Cost is per-request and the integration is a second adapter behind the existing `Geocoder` seam, which ADR-007 already isolates — so this is genuinely additive. Wants a spend decision (`quota.ts` already meters the first vendor, and KI-93 is an open hole in that metering).
  3. **A user-supplied coordinate path** — let someone drop a pin or paste a Maps link when the geocoder comes back empty. Removes the dependency entirely for the case that matters, and is the only option that helps a user whose venue no vendor carries. Largest UI surface.
  4. **Accept hand-authored coordinates as canonical for uncorroborable venues** — already the fixture's de facto position (ADR-030), never stated as policy.
- **Do not resolve this by hand-entering vendor data into `coordinateGaps.ts`.** That file records what the vendor could not do; filling it with coordinates from elsewhere would make it a second, unchecked source of truth and re-create KI-15's failure mode one layer down.
- **Raised by:** Mitchell, 2026-08-30, on seeing the live run — *"make a note that we need to figure out how to support small vendors like that that our chosen vendor cant support"*. Filed rather than actioned because options 2 and 3 are product and spend decisions, not cleanups.
