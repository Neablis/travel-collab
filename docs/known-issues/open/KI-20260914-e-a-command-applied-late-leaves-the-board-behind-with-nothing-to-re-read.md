### KI-2026-09-14-e — a command the server applies *after* you navigate leaves the board behind, and nothing ever re-reads

- **Severity:** correctness — user-visible, and the edit is NOT lost. The command is persisted; only the board is wrong, and it stays wrong until a document reload.
- **Area:** `apps/web/src/components/trip/context/TripProvider.tsx` — `load()` runs once per mount (`useEffect(() => { void load(); }, [load])`) and there is no second read. Adjacent to the optimistic sender, which the navigation unmounts.
- **What is wrong:** add a day, navigate away and back while the command is still being applied server-side, and the board comes back without the day. The return read reaches the network and is **correct at the moment it is taken** — the server genuinely has not applied the command yet — so there is nothing stale to invalidate. `TripProvider` sets state from that answer and never reads again.
- **How it came to light:** the second browser walk of PR #175 (2026-09-14), against preview `e793da8`. Reproduced by holding the command POST's **request** (not its response), so the server applies late: 2/2 failures at each of 2000ms, 3000ms and 5000ms of uplink delay, with a 0ms control on the same interception passing 2/2. Measured symptom: `before=28, on return 28, settled+15s=28, afterReload=29` — the reload is server truth, so the command landed and only the board disagreed.
- **Not what PR #175 fixed, and not caused by it.** That PR fixed a read served from a cache entry stored *before the command was sent* (`fa999e3`, the write scope). This variant's read goes to the wire. The cache is not involved: the same sequence on `main`, which has no cache and refetches on every mount, produces the same stale board for the same reason. `fa999e3`'s own commit message names the gap — *"nothing re-reads"* — and closes only the cache-hit half of it.
- **Why it is reachable without artificial delay:** what matters is time-to-apply, not round-trip. The baseline command round trip on that preview was already 2.4–2.9s.
- **Scope:** the fix is a second read, not a cache change. Options: have `TripProvider` re-read when a command it dispatched resolves after the provider remounted (requires the pending queue to survive navigation, which is `KI-005`'s territory); or reconcile from the command's own `{ detail, history }` response, which already carries post-command truth, by routing it back into whatever provider is mounted when it lands. The second is the smaller change and does not need the queue to survive.
- **Cross-reference:** `KI-005` (optimistic commands silently lost on abrupt navigation — there the command never reaches the server; here it is persisted and only the board is wrong), PR #175, ADR-046.
- **First noted:** 2026-09-14, in the second browser walk of PR #175.
