### KI-2026-09-06-a — two `PageAssistant` unit tests are red on `main`, unfiled, and the local unit lane has never been green because a second failure was masking them — RESOLVED

- **Severity:** correctness, unproven — the two tests assert that a second assistant turn ACCUMULATES rather than replacing the first, which is user-visible behaviour if genuinely broken. What is certain is the process failure: `main` is red on the unit lane and nothing recorded it.
- **Area:** `apps/web/src/components/pages/PageAssistant.test.tsx` — "accumulates a second turn instead of replacing the first" and "posts the whole conversation back on the second turn, assistant turns included"; the component under it, `apps/web/src/components/pages/PageAssistant.tsx`.
- **Symptom:** under Node 22 — CI's version, `.github/workflows/ci.yml:107,142` — `pnpm --filter web exec vitest run -c vitest.unit.config.ts` gives `Tests 2 failed | 2293 passed | 1 skipped`. The failure is a `waitFor` timeout on the second call:

  ```
  ❯ src/components/pages/PageAssistant.test.tsx:162:50
    await waitFor(() => expect(askAssistantMock).toHaveBeenCalledTimes(2))
  ```

- **It is NOT this branch, and it is NOT a flake.** Verified by checking out `origin/main` detached and running the file alone: the same two tests fail, by name. Per `CLAUDE.md` rule 2, a failure whose location *moves between runs* is a timeout and one that fails in the same place every time is a real defect — this one is in the same place every time, on two different trees, which is why it is filed rather than retried.
- **Why it went unnoticed:** the local unit lane was ALREADY red from **KI-2026-09-02-a** (Node 26 makes `window.localStorage` undefined, 12 failures in `pendingDemoClone.test.ts`). Anyone who ran the lane locally saw 14 failures, recognised the documented Node-26 ones, and had no reason to look at the count. Dropping to Node 22 removes 12 and leaves these 2 standing. **A known-red lane hid a second, unknown failure — that is the real finding here**, and it is the same species as KI-13/76 and KI-2026-09-05-s: a signal nobody could read.
- **ANSWERED 2026-09-06, same day: CI is GREEN.** PR #147's `static-and-unit` job passed in 3m33s with these two tests included, on the same tree that fails locally under Node 22. So `main` is **not** shipping red, and the severity above is downgraded accordingly — this is a **local-verification** problem, not a product defect.
  That makes it a sibling of KI-2026-09-02-a rather than a bug in `PageAssistant`: the assertion is a `waitFor` on a second mock call, which is timing-sensitive, and the local runs that failed were on a machine that had just finished an e2e lane and six parallel agents. It failed in the same *place* every time, which is why it was filed rather than retried — but it does not fail in the same *environment* every time, and that distinction is the finding. `CLAUDE.md` rule 2's "same place every time = real defect" heuristic gives the wrong answer here, because it does not separate location-stability from environment-stability.
- **What is still worth doing:** establish whether the test is load-sensitive (raise the `waitFor` timeout and see if it stops failing under load) or whether CI is masking something by being fast. Until then nothing should be changed in `PageAssistant.tsx` — no defect in it has been demonstrated.
- **Why not fixed here:** found during the 2026-09-05 KI sweep's single Tier-3 `pnpm check`, on a branch whose six merged fixes are unrelated to this component. Fixing it there would have widened a ready diff into a component nobody in the sweep touched.
- **First noted:** 2026-09-06, during the KI sweep's final verification.

- **RESOLVED 2026-09-06 — root cause found, and it was neither of the two things this entry guessed.** Not load-sensitivity and not a `PageAssistant` product defect. **The AI insert focuses the editor as its last act**, at `PageScreen.tsx:240` — `editorRef.current?.chain().focus().insertContent(...)` — and that `focus()` lands *after* the inserted text has rendered. Both tests captured the composer element once, waited on `findByText(...)` for the inserted text, then typed a second message. `userEvent.type` got two keystrokes in before the editor took focus; every remaining character, **including the `{Enter}`**, went to the editor. The turn was never submitted, and the failure surfaced as `expected "vi.fn()" to be called 2 times, but got 1 times` — which reads like a product bug and is not one.
- **How it was found:** by probing rather than guessing. Two hypotheses were tested and *falsified* first — that the composer was disabled (`disabled={asking}` at `AssistantRail.tsx:359`; it was not) and that the node was stale after a re-render (it was the same node). The decisive probe printed `document.activeElement` around the second `type`: `DIV.tiptap ProseMirror ProseMirror-focused`, with the composer holding only `"O"`.
- **Fix:** test-only. A `readyForAnotherTurn()` helper waits for the focus steal to happen (`document.activeElement` is `contenteditable` — the semantic attribute, not the `.ProseMirror` class, which the test-quality wall would rightly object to), then clicks the composer and waits for focus to come back. **No product file changed.**
- **Proof:** both tests seen red for their real reasons after the fix, by breaking what they guard — dropping assistant turns from the posted history (`useAskThread.ts:131`) gives `expected [ …(2) ] to deeply equal [ …(3) ]`, and swapping `insertContent` for `setContent` in `PageScreen.tsx` gives `Unable to find an element with the text: Bring a raincoat`. Three consecutive green runs before that, so the fix is deterministic rather than a widened timeout. Full unit lane under Node 22: **166 files, 2295 passed, 0 failed** — green for the first time.
- **Why CI was green and local was red:** the race is decided by how quickly the machine gets from render to `focus()`. It is a genuine defect of the test, not a flake, and it is worth recording that **`CLAUDE.md` rule 2's "same place every time = a real defect" heuristic gave the right verdict here for the wrong reason** — the location was stable, but so was the environment; what varied was only the machine. The rule separates defects from timeouts, and does not separate either from an environment-sensitive defect.
- **Left as an open question, deliberately not fixed:** *should* an AI insert steal focus from the composer at all? A user typing a follow-up while a turn lands would lose the same keystrokes this test did. The `.focus()` is load-bearing for `insertContent` (it needs a selection to insert at), so removing it is not a one-liner and is a product decision, not a cleanup. Filed as **KI-2026-09-06-b**.
