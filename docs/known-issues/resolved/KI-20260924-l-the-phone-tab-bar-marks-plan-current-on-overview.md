### KI-2026-09-24-l — opening a trip on a phone lands on Overview while the tab bar marks Plan as current — RESOLVED

- **Severity:** correctness of navigation state, small — the tab bar lies about where you are.
- **Area:** the phone tab bar (`aria-current="page"` logic) and the trip's default view on a phone; SPEC §10.
- **Symptom / What happens:** measured 2026-09-24 at 390px: a trip opens on the Overview document, but the tab bar marks **Plan** `aria-current=page`. The Overview itself is the desktop notebook document inside a padded card (8,560px tall), which reads but is not the designed phone companion.
- **Why not fixed here:** needs the phone's default view confirmed (Overview or Plan) before choosing which half to change.
- **Cross-reference:** screenshot `d-overview-mid-390.png` from the 2026-09-24 check; KI-2026-09-24-i.
- **First noted:** 2026-09-24, mobile check.
- **Fix (2026-09-25):** `activePhoneTab` in `apps/web/src/components/nav/PhoneTabBar.tsx` now lights a trip tab only when that tab's own view is on screen: `Map` lights Map, `Plan` lights Plan, and Overview, Calendar and an unknown view light nothing. The old code returned `view === "Map" ? "map" : "plan"`, which lit Plan for every non-Map view. That was written on the reading that §10's two phone views stand for all four desktop ones, and it became a lie once §24 made a bare trip URL land on Overview. The SSR `PhoneTabBarFallback`, which cannot read the query, lit Plan by the same guess and now lights no trip tab. The invariant is that `aria-current="page"` sits on the tab of the view on screen, or on none.
- **Reproduction (before the fix):** a new case in `PhoneTabBar.test.tsx` renders the bar at `/trips/t1` (no view param) and asserts no tab is current. Against the unchanged source it failed with `AssertionError: expected 'Plan' to be null`. `TripBoardScreen` renders whatever `resolveView` returns with no phone override, so that URL shows Overview.
- **Proof:** the updated test file was run against the original `PhoneTabBar.tsx` and gave 5 red: `/trips/t1`, `?view=Overview` and `?view=Calendar` each failed with `expected 'Plan' to be null`, plus the new Overview case and the fallback case (`/trips/t1?view=Plan` rendered through `PhoneTabBarFallback`). With the fix restored, 30/30 were green. Three old rows (`/trips/t1`, `?view=Overview` and `?view=Calendar` → Plan) and the fallback's "Plan is current" assertion encoded the bug, so they now expect no current tab. Checks: `pnpm --filter web exec vitest run -c vitest.unit.config.ts src/components/nav/PhoneTabBar.test.tsx`, `pnpm --filter web typecheck` and `pnpm --filter web lint`, all green. The e2e specs that assert Plan is current (`responsive.spec.ts:665`, `m16-mobile-assistant.spec.ts:479`) open `?view=Plan`, which is unaffected.
- **Decision (2026-09-25 overnight sweep):** kept Overview as the landing view and changed the tab bar. SPEC §10 says the phone has "two views, not four", but it predates §24 and never names a phone default. §24 says "Entering a trip lands on Overview", with no surface exception. Since the spec is silent on a phone default, the landing stays. Rejected: (a) a phone-only default of Plan, which would need a `useIsPhone`-dependent `resolveView`, so the URL would render differently by width, and §24 names no such exception; (b) lighting Notebook on Overview (§25: Overview "IS a notebook page"), because the Notebook tab links to `/pages`, a different screen, so that would be the same lie again; (c) keeping Plan lit for Overview as "the phone's catch-all", which is the reported bug. Overview therefore has no current tab on a phone.
- **Not addressed here:** the Symptom's second sentence, that the phone Overview is the desktop notebook document in a padded card (8,560px tall) rather than a designed phone companion. That is presentation, not tab-bar state. It was reported to the sweep as a candidate for its own entry.
