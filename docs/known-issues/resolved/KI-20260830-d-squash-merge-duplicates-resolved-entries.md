### KI-2026-08-30-d — A squash-merged PR makes the next branch's `git mv` reappear as a duplicate, in both `open/` and `resolved/`, with no conflict — RESOLVED
- **Severity:** correctness of this register (an entry listed as open AND resolved at once) — and it is a limitation of KI-95's own fix, found the same day, on the first stacked pair
- **Area:** `docs/known-issues/` (the directory-as-status scheme), `.claude/commands/ki-sweep.md` step 6b, and this repo's squash-merge habit.
- **What happens, measured on PR #94 → #95:** KI-95 made resolving an issue a `git mv` from `open/` to `resolved/`. That is conflict-free between *sibling* branches, which is the property it was built for and which held. It is **not** robust to the base being **squash-merged** underneath a stacked branch. #94 landed as a single squashed commit (`cad4273`), so none of its original commits are ancestors of `main`. When `main` was merged into #95, git had no rename to follow: it saw `main` adding four files under `open/` that the branch did not have there, and kept them — while the branch's `resolved/` copies stayed. Result: **KI-78, KI-89, KI-91 and KI-96 present in both directories at once**, the `open/` copy being the pre-fix text and the `resolved/` copy carrying the proof line.
- **`git merge` reported no conflict.** That is the part worth remembering. A same-file edit collision announces itself; this does not. The tree is simply wrong afterwards, and `ls docs/known-issues/open/` — which the README declares to be the index — lists four issues that are fixed. Caught here only because the merge output printed four `create mode` lines for files that should not have been created.
- **Not a reason to go back.** The old single-file layout would have produced a genuine conflict at both anchors for the same pair, which is worse and is what KI-95 measured at 10 resolutions per four-branch sweep. This is a narrower failure with a narrower fix.
- **Fix path, cheapest first:**
  1. **Merge, don't squash, a sweep's base PR** when another branch is stacked on it. The rename is then a real ancestor and git follows it. Zero code.
  2. **A guard**, since (1) depends on remembering: a check that fails when any basename appears in more than one of `open/`, `resolved/`, `dormant/`. It is a five-line script and belongs beside `check-lint-wall.mjs` in `pnpm lint`, which is where this repo already puts structural walls. That would have failed this merge instead of shipping it.
  3. Have `/ki-sweep` step 6b say the integration branch must be brought up to date **before** the base merges, not after.
- **Fix (2) is the one to take**, because it catches the whole class rather than this instance, and because the register is now read by `ls` — a wrong listing is the failure mode the structure trades for conflict-freedom.
- **Seen again 2026-09-11, on PR #162 → the stacked P6 branch — and it presented as something else entirely.** The title of this entry predicts duplicated known-issue entries. That is **not** what happened. `#162` was squash-merged while `claude/ai-stream-envelope-contracts` was stacked on it; merging `main` into the stacked branch produced **twelve `add/add` and content conflicts on source files** — `assistant/admission.ts`, `deps.ts`, `grants.ts`, `ledger.ts`, `prompt.ts`, `registry.ts`, `tools/planning.ts`, `tools/read.ts`, `handleAskRequest.ts`, `writeTools.ts`, a route test and the design spec — because git sees `main` *adding* every file the stacked branch also has. Meanwhile the `open/` ∩ `resolved/` check this entry is named for came back **clean**.
  - **So the failure mode scales with how much code the squashed base carried, not with how many KI entries it moved.** A four-entry sweep produces four silent duplicates; a 73-file refactor produces a merge nobody can resolve by hand. The duplicate case is the *mild* one, and naming the entry after it undersells the hazard.
  - **The remedy when it has already happened** (fix path 1 prevents it; this recovers from it): do not merge. A squash preserves the **tree** and loses only the ancestry — verified here, `git diff <old-branch-head> origin/main` was empty — so replay the stacked branch's own contribution on top of the new `main` instead. Concretely: `git checkout -B <stacked> origin/main && git read-tree -u --reset <stacked-old-head>`, then commit. The result is one clean commit and zero conflicts.
  - **One trap in that recovery, hit on the first attempt.** The stacked branch's tree is only as new as the last time its base was merged in. Anything committed to the base *after* that point is absent, and `read-tree --reset` will **delete it without saying so** — here, `KI-2026-09-11-d`, filed on the base an hour after the stacked branch last merged it. It showed up as a lone `D` in `git status` and was restored from `main`.
  - **`git status` is not the check. Compare file SETS.** The advice here used to be "read `git status` before committing a replay; the deletions are where the damage is", and #163 proved that insufficient. A file the replayed tree is *missing* shows as a `D` and gets caught. A file it *reverts* — an edit made to the base after the branch last merged it — shows as an ordinary modification to a file the branch legitimately touches, and reads as the branch's own work. **The docstrings on eight files — 75 lines of them, `git show 1bd9c64 --stat` — were lost that way, and a review bot found them, not this recipe.** The check that does work: take the files the branch's own commits touched, `git log --name-only --format="" --no-merges <old-base-head>..<old-head>`, and compare that set against the replayed branch's, `git diff --name-only origin/main`. Treat every extra file as suspect until explained, and run it **on the replay commit itself**, before anything is stacked on top — every later commit adds legitimate extras and blurs the signal. Measured on #163: **20 versus 28** at the replay commit, and all eight extras were under `apps/web/src/server/assistant/**` — pure reversion, a directory that PR never touched. (By the time it was caught the branch had two more commits, so the same comparison read 20 versus 30.)
- **Found by:** the 2026-08-30 sweep, bringing `main` into the batch branch after #94 was squash-merged. The duplicates were removed by hand in that same merge commit.
- **Cross-reference:** KI-95 (resolved — the structure this refines), `.claude/commands/ki-sweep.md` step 6b, `docs/known-issues/README.md` (the "no index file" rule that makes `ls` load-bearing).
- **First noted:** 2026-08-30.
- **Fix (2026-09-25):** fix paths (2) and (3). **(2)** is in `scripts/check-ki-filenames.mjs`, which already runs in root `pnpm lint` and already walks all three directories, so it goes there and no new script is needed. It now records every entry's basename per directory **before** any grandfathering, and fails when one basename is in more than one of `open/`, `resolved/`, `dormant/`: `<file> is in open/ AND resolved/ — one entry, two statuses …`. The existing shared-id check (added 2026-09-24) now counts distinct basenames, not paths. It used to catch an ordinary duplicate only by accident, and then gave the wrong remedy, "give the newer one the next free letter", which would turn a stale copy into a fake second entry. **(3)** `.claude/commands/ki-sweep.md` step 6b now says: bring a stacked branch up to date **before** its base merges, merge the base without squashing, run the wall after the merge, and replay rather than merge if the base was already squashed.
- **Proof:** Reproduced in a scratch copy of the register at `cdb3582`. With `KI-20260830-eslint-src-misses-app-root-files.md` (a grandfathered filename) and `KI-20260906-c-imported-content-carries-no-coordinates.md` (a grandfathered shared id) each copied from `resolved/` into `open/`, the wall printed `ki filename wall OK (260 entries scanned, 6 grandfathered)`, exit 0. Both entries were listed as open and resolved at once. A plain duplicate (`KI-095-…`) failed only as `KI-95 is used by 2 entries — give the newer one the next free letter`. After the fix the same scratch register fails, exit 1, with all three reported as `… is in open/ AND resolved/`. The regression tests are in `scripts/__tests__/check-ki-filenames.test.mjs`: "fails when one entry sits in two status directories, grandfathered or not" and "reports a two-directory duplicate once, not also as a shared id". Both went red when the basename record was commented out (`actual: 0, expected: 1`). The second went red again, on `doesNotMatch /next free letter/`, when the distinct-basename count was reverted to counting paths. Restored: 10/10 green. Checks: `node --test scripts/__tests__/check-ki-filenames.test.mjs` 10/10, `node scripts/check-ki-filenames.mjs` OK on the real register, `node scripts/check-ki-citations.mjs` OK.
- **Decision (2026-09-25 overnight sweep):** closed as RESOLVED, not narrowed, even though the wall does not cover the 2026-09-11 form of this hazard, where a squashed base causes add/add conflicts on source files. That form is loud: git reports the conflicts, so nothing ships silently. It already has a recovery recipe above, and step 6b now points to it. Fix (1), merge without squashing, is prevention by habit, and this entry already says habit alone is not enough. The wall is the part a tool enforces. Rejected alternatives: a separate `check-ki-duplicates.mjs` script, because it would be a second walk of the same three directories and one more item in the lint chain; and matching duplicates by id rather than basename, because the grandfathered ids and filenames are exactly the cases that approach cannot see.
