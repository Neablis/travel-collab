### KI-55 — A unit queued after a KI-42 retention predicts over a base that skips the retained work — RESOLVED
- **Severity (as filed):** correctness-cosmetic (the optimistic *preview* can show a trip no send will produce; **no work is lost** — every retained unit is still queued, still counted by `unsentCount`, and still sent in order)
- **Area:** `apps/web/src/components/trip/context/optimistic.ts` (`enqueue`, `baseDetail`)
- **Symptom (as filed):** after `confirmHead` retains units it can no longer predict (KI-42), those units carry `predictedDetail: null` and `baseDetail` scans past them to the last unit that *has* a prediction. `enqueue` predicts a newly queued unit against that base — so the new prediction, and therefore `activeDetail`, omits the retained work even though it is still queued and will still be sent. `confirmHead`'s own comment states the opposite guarantee ("predicting a later one against a base that skips an earlier one would show the user a trip that no send is ever going to produce"); that guarantee covers only the units `confirmHead` itself re-predicts, not ones enqueued afterwards.
- **Found by:** CodeRabbit's review of PR #73 (the KI sweep that fixed KI-42), 2026-08-28. Verified against the code and **pinned by a characterization test** — `optimistic.test.ts`, "predicts a newly queued unit over a base that skips the retained ones (KI-55)" — so a change to this behavior is a visible test change rather than a silent one. (That test is what this fix rewrote; it no longer exists under that name. See Proof.)
- **Why it was recorded rather than fixed (as filed):** the recommended fix (make a null-prediction unit a barrier, so newly queued units are also retained unpredicted) has a real cost — the user's *next* edit would visibly do nothing on screen until the queue became predictable again. The current behavior is at least self-consistent: the user can only act on what is rendered, what is rendered is already `baseDetail`, so the new prediction matches the screen they clicked. Which trade-off is right is a product call about the optimistic layer, not a mechanical fix — the same class of decision `tripDetailFactory`'s `conflicts: []` was left as.
- **A third option, if neither is wanted:** surface the retained-but-invisible units explicitly (the count is already in `sync.unsent`), so the preview's incompleteness is stated rather than inferred.
- **How it is reached:** requires a concurrent write that invalidates a queued unit's prediction mid-flight, *and* the user making further edits before the queue drains. Rare in single-player; Invariant 6 makes it normal in Phase 2.
- **Reproduced before fixing**, as a reducer test in `optimistic.test.ts` ("never previews a later unit's work while omitting an earlier queued unit's"). The queue drains sequentially and in order, so every trip the server can hold while it drains is the work of a *prefix* of the queue. Using KI-42's own setup — `u1 = AddDay d-a`, `u2 = AddActivity on d-a`, `u3 = AddDay d-c`, head confirmed with an authoritative outcome that does not contain `d-a` — then queuing `u4 = AddDay d-d` and asking which of the queue's days the preview shows:
  ```
  FAIL  src/components/trip/context/optimistic.test.ts > confirmHead retains queued units
        that no longer predict (KI-42) > never previews a later unit's work while omitting
        an earlier queued unit's (KI-55)
  AssertionError: expected [ 'd-d' ] to deeply equal [ 'd-c' ]

  - Expected
  + Received

    [
  -   "d-c",
  +   "d-d",
    ]
  ```
  `['d-d']` is not a prefix of the send order `['d-c', 'd-d']`: the board rendered `u4`'s day while omitting `u3`'s, which is still queued ahead of it and still going to be sent first. No send ever produces that trip.
- **Cause:** unpredicted units are a strict *suffix* of `pending` — `confirmHead` establishes that (once a unit fails to re-predict, everything behind it is retained unpredicted too) and `baseDetail`'s backwards scan is only correct because of it. `enqueue` broke the invariant: it predicted unconditionally, appending a *predicted* unit behind unpredicted ones, and `baseDetail` then returned that unit's detail — a base computed over a trip missing real, still-queued work. Each further edit predicted over that, so the divergence compounded.
- **Fix (2026-09-02):** `enqueue` now preserves the invariant. It still runs `predictBatch` against `baseDetail` — so an impossible command is still rejected with the predictor's own code, and the unit is still *described* — but when the queue already holds a unit with `predictedDetail: null`, the predicted detail is discarded and the new unit is queued unpredicted. Every rendered preview is therefore a prefix of the send order. This is the entry's own "recommended fix" (the barrier), and its stated cost — the board stops moving under the user's edits while the queue is unpredictable — is real, bounded by the queue draining, and partly answered by the third option already being in place: the unit is counted by `unsentCount` and named in `activeHistory` as a pending row, exactly like the retained units ahead of it, so a board that stops moving is not a queue that has gone silent. `confirmHead` is unaffected: while its loop is still predicting, `acc.pending` holds no nulls, so its internal `enqueue` call takes the normal path; once a re-prediction fails it appends unpredicted units directly, without going through `enqueue`.
- **Deliberately NOT done:** no new alert, banner or "your edit is queued but not shown" copy, and no change to `EnqueueResult` — the edit is accepted (`ok: true`), not refused, so nothing about the dispatch path in `TripProvider.tsx` changes. Refusing the enqueue instead was considered and rejected: while a `failure` gates the sender the queue can stay unpredictable until the user retries, and locking editing for that whole window is worse than a board that lags. `baseDetail`'s backwards scan is unchanged — under the restored invariant it is correct — and now documents the invariant it depends on. **No file outside `optimistic.ts` and its test needed to change**, so this does not touch KI-5's or KI-90's territory in `TripProvider.tsx`.
- **Proof:** the reproduction above now passes. Regression tests — 6 in `optimistic.test.ts` under the KI-42 describe: the reproduction itself (the preview is a prefix of the send order); the rewritten characterization test, which used to assert the *inverse* and passed (that was the bug, written down) and now pins the unit being queued unpredicted with `activeDetail` equal to the authoritative trip; the barrier holding for the whole tail rather than just the first unit past it (two edits, still nothing predicted); the unit still carrying a description and a pending history row; an impossible command still rejected with `activity-not-found` while the queue is unpredictable; and the barrier lifting on its own once the queue drains. Mutation-proved: restoring `predictedDetail: prediction.detail` turns **3 of the 6** red (the other three assert the parts the barrier deliberately does *not* change — description, rejection, and recovery — and pass either way, which is what they are for).

There is still no way to *abandon* a unit the server will never accept except by reloading, the same gap KI-36 recorded.
