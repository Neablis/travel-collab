### KI-2026-09-05-l — kept days carry no version and `SavedStop` has no defaults, so the first required-field addition hides every existing Playbook — RESOLVED

- **Severity:** correctness risk (recoverable — rows survive — but the recovery is an operator writing a backfill after users report their library is empty)
- **Area:** `packages/contracts/src/saved.ts:23-32` (`SavedStop`: `kind`, `tags`, `anchors`, `cost` all required, no `.default()`); `apps/web/src/server/savedDays.ts:80-88` (`fromRow` drop-and-log), `:234-238`; `server/db/schema.ts:234` (`jsonb` with a compile-time `$type` only); `server/playbooks.ts:230-244` (`toDiscoverDay` — the second copy of the same parse)
- **Symptom / What happens:** KI-71's fix made an unreadable row fail *closed*, which is right, but there is no migration mechanism for this jsonb value at all — unlike `PageDoc` (a derived `v` plus a migration chain) and event payloads (`.default()` on every post-v1 field). Add one required `SavedStop` field — a second time zone, a money-model change, any ADR-040 follow-on that lands *inside* a stop — and every existing saved day silently disappears from its owner's library and from Discover.
- **Alongside it ([F-F05](../../reviews/2026-09-05-overnight-review/findings/F-F05-saved-day-row-parse-duplicated.md)):** that parse exists **twice**, with identical log strings, in `savedDays.ts:81-88,99-106` and `playbooks.ts:230-244`. A third parsed column, a changed message, or the `v` wrapper below has to land in both — so the single `parseSavedDayColumns(row)` helper is the natural home for the fix and should land with it.
- **Why not fixed here:** found by a read-only review; no code was changed by it. Suggested fix: adopt the event-payload rule for `SavedStop` in the contract file's header (every field added after today carries `.default()`), and add `v` to the stored value **now**, while there is one version — a `{ v: 1, stops: [...] }` wrapper parsed in `fromRow` with a one-shot migration on read for v-less rows. Write it into ADR-040's consequences before its migration lands; ADR-040 is still `Status: Draft` and unbuilt, which is exactly the window in which this is cheap.
- **Cross-reference:** [F-C04](../../reviews/2026-09-05-overnight-review/findings/F-C04-savedstop-has-no-version-or-defaults.md) (MEDIUM), [F-F05](../../reviews/2026-09-05-overnight-review/findings/F-F05-saved-day-row-parse-duplicated.md) (LOW); resolved KI-71 (the fail-closed read boundary this builds on); ADR-040; KI-2026-09-05-j (the same "non-additive change has nowhere to land" theme, for events).
- **Narrowed 2026-09-19 by M23 (ADR-048), NOT resolved.** Two of the three halves this entry asks for are now real: `SavedStop`'s header carries the rule that *every field added to it from now on carries `.default()`*, and `dayIndex` is its first adopter — so the next field added additively can no longer hide a library by accident. F-F05's single `parseSavedDayColumns(row)` helper also exists now and both read sites go through it, which was the other half of the blast radius. **What is still missing is the part that matters for a NON-additive change:** there is no `{ v, stops }` wrapper and no migration chain, so a required field, a money-model change or any ADR-040 follow-on landing inside a stop still has nowhere to go. ADR-048's rejected-alternatives section says why the wrapper was deliberately not built in that milestone — it would have converted an additive change into a versioned read before any of M23 could start — and that the first genuinely non-additive `SavedStop` change is what should pay for it. Keep this entry open until then.
- **First noted:** 2026-09-05, overnight review streams C + F.
- **Resolved 2026-09-25 (overnight KI sweep).** M23 had already written the `.default()` rule into `SavedStop`'s header and built F-F05's shared parse. What was left was that the rule was prose that nothing checked. `packages/contracts/test/fixtures/savedStopV0.ts` is now a **frozen** golden of the oldest stops ever stored: `SavedStop` at `cccbac8`, before `dayIndex`, with each nested schema (`TimeWindow`, `Location`, `Anchor`, `Money`) at its shape in that commit. It has a barest-legal stop, a stop with every nullable field populated and all four anchor kinds, and a fully geocoded location. `packages/contracts/test/saved.test.ts` adds two tests. One parses the golden through `SavedStop.array()`, the parse `parseSavedDayColumns` runs for both read sites. The other names any top-level field added since v0 that is not optional or defaulted. The `SavedStop` header now names the guard and records the decision below. This was a comment-only change to `saved.ts` with no schema change, so there is no CHANGELOG entry.
- **Proof, red then green.** *Reproduction.* A scratch edit added `secondTimeZone: z.string()` to `SavedStop`, and a scratch int test inserted a pre-M23 row and read it back with `listSavedDays`. The row vanished: `AssertionError: expected [] to deeply equal [ 'Old day' ]`. The same test was green before the edit. *No existing guard.* With the scratch field also added to the test's shared `stop` literal, which is what an author naturally does, the contracts suite's only red was the ActivityView field-parity test (`1 failed | 409 passed`), and the author fixes that by listing the field. No test failed because old rows had stopped parsing. *New guard, red.* With the same scratch edit, the golden test failed with `invalid_type … "path": [0, "secondTimeZone"] … "Required"` and the per-field test with `expected [ 'secondTimeZone' ] to deeply equal []`. A nested scratch edit (`placeId: z.string()` on `Location`) also failed the golden test (`"path": [..., "placeId"]`). *Green.* Changing the scratch field to `z.string().default("UTC")` turned both new tests green. That proves the rule's remedy satisfies the guard. All scratch edits were reverted. Checks run: `pnpm --filter @tc/contracts exec vitest run` and the full `pnpm check`, because the change touches `packages/contracts/src` (invariant 5).
- **Decision (2026-09-25 overnight sweep):** no `version`/`{ v, stops }` wrapper on kept days. This entry's harm is that an additive change *silently* empties libraries, and the guard now turns that into a red contract test before merge. The remedy is a `.default()`, which fully covers every additive change. A non-additive change (a rename, a type change, a money-model change inside a stop) cannot be expressed with a default, so it fails the guard too, and that is the moment to build the wrapper and a migration on read. ADR-048's rejected-alternatives section already assigns that cost to the first such change, and this decision keeps that assignment. Rejected: (a) adding `v: 1` now with an upcaster for v-less rows. That builds a migration chain with nothing to migrate, needs a data backfill or a permanent v-less branch, and puts the stored-shape change into production data. It also overlaps KI-2026-09-05-j's "non-additive change has nowhere to land" territory for events. (b) Relaxing the read boundary to salvage rows that fail to parse. That would render fragments whose shape nothing validated, which undoes KI-71's fail-closed read.
