### KI-2026-09-14-e — a command the server applies *after* you navigate leaves the board behind, and nothing ever re-reads — RESOLVED

- **Severity:** correctness — user-visible, and the edit is NOT lost. The command is persisted; only the board is wrong, and it stays wrong until a document reload.
- **Area:** `apps/web/src/components/trip/context/TripProvider.tsx` — `load()` runs once per mount (`useEffect(() => { void load(); }, [load])`) and there is no second read. Adjacent to the optimistic sender, which the navigation unmounts.
- **What is wrong:** add a day, navigate away and back while the command is still being applied server-side, and the board comes back without the day. The return read reaches the network and is **correct at the moment it is taken** — the server genuinely has not applied the command yet — so there is nothing stale to invalidate. `TripProvider` sets state from that answer and never reads again.
- **How it came to light:** the second browser walk of PR #175 (2026-09-14), against preview `e793da8`. Reproduced by holding the command POST's **request** (not its response), so the server applies late: 2/2 failures at each of 2000ms, 3000ms and 5000ms of uplink delay, with a 0ms control on the same interception passing 2/2. Measured symptom: `before=28, on return 28, settled+15s=28, afterReload=29` — the reload is server truth, so the command landed and only the board disagreed.
- **Not what PR #175 fixed, and not caused by it.** That PR fixed a read served from a cache entry stored *before the command was sent* (`fa999e3`, the write scope). This variant's read goes to the wire. The cache is not involved: the same sequence on `main`, which has no cache and refetches on every mount, produces the same stale board for the same reason. `fa999e3`'s own commit message names the gap — *"nothing re-reads"* — and closes only the cache-hit half of it.
- **Why it is reachable without artificial delay:** what matters is time-to-apply, not round-trip. The baseline command round trip on that preview was already 2.4–2.9s.
- **Scope:** the fix is a second read, not a cache change. Options: have `TripProvider` re-read when a command it dispatched resolves after the provider remounted (requires the pending queue to survive navigation, which is `KI-005`'s territory); or reconcile from the command's own `{ detail, history }` response, which already carries post-command truth, by routing it back into whatever provider is mounted when it lands. The second is the smaller change and does not need the queue to survive.
- **Cross-reference:** `KI-005` (optimistic commands silently lost on abrupt navigation — there the command never reaches the server; here it is persisted and only the board is wrong), PR #175, ADR-046.
- **First noted:** 2026-09-14, in the second browser walk of PR #175.
- **Reproduced:** `TripProvider.lateWrite.test.tsx`, which drives the REAL `sendTripCommand`/`sendTripCommandBatch` with only `fetch` held: on a solo trip, add `d-a` (POST held) and `d-b`, unmount (KI-5's flush sends `d-b`, held), remount (the return read gets `d1`), then let the server apply both and release the POSTs. Before the fix: `Expected: "d1,d-a,d-b" / Received: "d1"`. A multi-member trip converges through `useTripBroadcast`'s 2s timer, and any trip on a focus or visibility change; a solo trip navigated in-app had neither, which is the case the entry measured.
- **Fix:** `queryCache.ts` gains `writesSettled(prefix)`: `null` when no write scope overlapping `prefix` is open, otherwise a promise that resolves when the last one closes (`endWrite`) or the cache is cleared. It uses the `beginWrite`/`endWrite` scope every trip write already opens, so it covers the old board's in-flight head, KI-5's unmount flush, and any other write to the trip. `TripProvider`'s mount effect asks it once, before `load()`; if a write was outstanding it waits for `load()` to set its state, then for the write to settle, then runs `onRemoteChange` (invalidate, read detail and history, `adoptOutcome`). The re-read goes after `load` so the answer it corrects cannot overtake it. It is skipped if the provider has unmounted.
- **Proof:** the reproduction is green. Red with the `onRemoteChange` call in the mount effect commented out: the same `Received: "d1"`. Three `writesSettled` cases in `queryCache.test.ts` and the "no re-read when nothing is outstanding" case in the new file each went red for their reason (resolving on the first of two open scopes, `expected Promise{…} to be null`, a 2000ms timeout with the clear's resolve removed, `expected "vi.fn()" to be called 1 times, but got 2 times`) and green once restored. Checks: `pnpm exec vitest run -c vitest.unit.config.ts src/lib/queryCache.test.ts src/components/trip/context/` gave 9 files and 172 tests passed. `pnpm --filter web typecheck` and eslint on the four touched files were clean.
- **Decision (2026-09-25 overnight sweep):** re-read on mount when a write to the trip was outstanding at mount, using the query cache's existing write scope as the signal. Rejected: (a) sending the late command's `{ detail, history }` response to whichever provider is mounted, which the entry preferred. It would need a registry of live providers, and adopting a response wholesale can go backwards if another write lands between it and the mounted board's own read. A re-read after the write settles is always at least as new. (b) Re-reading on every mount, which adds a request per navigation to fix a case that only happens with a write in flight. (c) Keeping the queue alive across navigation (KI-5's territory, and bigger). (d) Timer-polling solo trips, which ADR-049 Decision 2 declines on cost. This touches `queryCache.ts`, which the entry's Scope said the fix would not. That line meant caching was not the cause, and it still isn't: no caching behaviour changed. The write scope just gains a way to be waited on.
- **Resolved:** 2026-09-25.
