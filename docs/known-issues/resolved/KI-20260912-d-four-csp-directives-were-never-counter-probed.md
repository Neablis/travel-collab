### KI-2026-09-12-d — four CSP surfaces were never exercised, and KI-66's close carried them out of `open/` with it — RESOLVED

- **Severity:** correctness — unverified security claims, not a known defect. Nothing is observed to be broken; the point is that four directives have only ever been reasoned about.
- **Area:** `apps/web/next.config.ts` (the `headers()` CSP) and `apps/web/next.config.test.ts`. The dev-mode branch (`'unsafe-eval'`, `va.vercel-scripts.com`), `form-action` against Google OAuth's 302, the `frame-src` / `frame-ancestors` / `object-src` / `base-uri` group, and Vercel's `/_vercel/insights/script.js` + `/_vercel/speed-insights/script.js` under `script-src 'self'`.
- **Symptom:** none observable. Each of these is a directive whose *blocking* behaviour has never been demonstrated by a browser refusing something. KI-66's 2026-08-28/29 walk proved enforcement was live with a deliberate `connect-src` control probe — `Refused to connect to 'https://example.com/probe'` — and that probe is exactly what these four lack. "No violations appeared" is not evidence for a directive nothing ever tried to violate.
- **Why this is filed separately:** KI-66 was closed as ` — DOWNGRADED` on 2026-09-12 because its headline claim (`script-src` keeps `'unsafe-inline'`) is a recorded architectural trade-off rather than a fixable defect — the App Router streams RSC through inline `<script>self.__next_f.push(...)</script>` on every page, and the supported alternative is a per-request middleware nonce that opts the whole app out of static rendering. That close is correct on its own terms, but KI-66's body was also the only record of these four gaps, and moving it to `resolved/` would have retired them silently. They are carried here verbatim in substance so the close stays honest.
- **Scope:** a counter-probe per directive against a local production build, in the shape KI-66's `connect-src` probe already established: attempt the violation, capture the `Refused to …` console line, record it. The Vercel insights scripts additionally need to be *seen loading* in an environment where they are enabled, which no walk has done.
- **Why not fixed here:** the 2026-09-12 KI sweep could not run it. `pnpm --filter web build` fails in the container without `DATABASE_URL` (`Error: DATABASE_URL is not set`, while collecting `/api/health/ai-mode` page data), so no production build could be served to a browser, and standing up Postgres was outside that sweep's one-KI blast radius. No fresh browser proof was fabricated to paper over it.

- **RESOLVED 2026-09-24 — all four surfaces counter-probed; no directive was wrong, one comment was.** A `pnpm --filter web build` succeeded with `DATABASE_URL` passed on the command line (Postgres on :5433). That build was served by `next start` (with `VERCEL=1`, so the insights components mount, and placeholder `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET`, so the Google provider registers), and the dev branch by `next dev --turbopack`. Both were walked in Playwright's Chromium 141.0.7390.37, capturing `securitypolicyviolation` events and console output. Off-box origins (`example.com`, `accounts.google.com`, `attacker.test`) were stubbed with `context.route`, so every refusal below is the browser's CSP decision, not a network failure. The served production policy: `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://tiles.openfreemap.org; font-src 'self' data:; connect-src 'self' https://tiles.openfreemap.org; worker-src 'self' blob:; frame-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none'`. KI-66's own control still holds: `Refused to connect to 'https://example.com/probe' because it violates the following Content Security Policy directive: "connect-src 'self' https://tiles.openfreemap.org".`

  1. **Dev-mode branch.** Production, eval from an inline script in the served document: `EvalError: Refused to evaluate a string as JavaScript because 'unsafe-eval' is not an allowed source of script in the following Content Security Policy directive: "script-src 'self' 'unsafe-inline'".` (`new Function` got the same). Off-origin script: `Refused to load the script 'https://va.vercel-scripts.com/v1/script.debug.js' because it violates the following Content Security Policy directive: "script-src 'self' 'unsafe-inline'".` Non-self socket: `Refused to connect to 'ws://ws-probe.invalid/x' because it violates … "connect-src 'self' https://tiles.openfreemap.org".` Against `next dev` the same three probes ran with zero violations: eval ran, the va.vercel-scripts.com script loaded and executed, and the WebSocket connected. **Trap for the next prober:** eval injected through Playwright's `page.addScriptTag({content})` ran even in production, with no violation. That is a Playwright injection artifact, not the policy. Only eval from a script inside the served HTML is a valid probe.
  2. **`form-action` against the Google OAuth hand-off.** The app's real "Continue with Google" button reached `https://accounts.google.com/o/oauth2/v2/auth?…` with **zero violations**. Counter-probe: `Refused to send form data to 'https://example.com/post' because it violates the following Content Security Policy directive: "form-action 'self'".` **The config comment was wrong, and it is now corrected.** It said the hand-off "is a 302 redirect, which form-action does not govern". Chromium does govern form redirects: a *native* form POST to `/api/auth/signin/google`, which 302s to Google, was refused with `Refused to send form data to 'http://localhost:3917/api/auth/signin/google' because it violates … "form-action 'self'".` The app is unaffected because `signIn("google")` is a fetch followed by a `window.location` assignment, not a form submission. The directive stays `'self'`.
  3. **`frame-src` / `frame-ancestors` / `object-src` / `base-uri`.** `Refused to frame 'https://example.com/' because it violates … "frame-src 'none'".` and the same refusal for a same-origin `/signin` iframe. From a cross-origin parent page: `Refused to frame 'http://localhost:3917/' because an ancestor violates the following Content Security Policy directive: "frame-ancestors 'none'".` The same refusal appeared with `X-Frame-Options` stripped from the framed response, so the CSP alone blocks the frame. With both headers stripped, the frame rendered the sign-in button (control). `Refused to load plugin data from 'http://localhost:3917/favicon.ico' because it violates … "object-src 'none'".` (and the same for an `<embed>`). `Refused to set the document's base URI to 'https://example.com/' because it violates … "base-uri 'none'".` In that last probe, `document.baseURI` stayed on our origin.
  4. **Vercel insights under `script-src 'self'`.** With `VERCEL=1` (the layout's real gate), the page emitted `<script src="/_vercel/insights/script.js">` and `<script src="/_vercel/speed-insights/script.js">`. Both returned 200 and executed (their marker globals were set), with zero violations. Only Vercel's edge serves the real bodies, and the egress proxy refuses `va.vercel-scripts.com`, so the bodies were stubbed at those exact same-origin paths. What is proven is the CSP's decision about those URLs. The vendor code's own follow-on beacons (same-origin `/_vercel/*` per the packages) remain unobserved. A preview walk (`walk:preview`) is where those would show up.
