### KI-78 — The geocode script reports "no results" as a retryable vendor error, on nine stops, every run — RESOLVED
- **Severity:** cleanup (a misleading label in a one-off script's report; no product impact)
- **Area:** `apps/web/scripts/geocode-japan-seed.mts` (`resolveJob`'s `catch`, and the `lookup-failed` reporting block)
- **Symptom:** LocationIQ answers a zero-result query with **HTTP 404**, not an empty list. `createLocationIQGeocoder` throws on it, `resolveJob` catches it as `reason: "lookup-failed"`, and the report prints it under `Lookup failed (rate limit or vendor error — rerun to retry)`. Nine stops hit this on every run — Hippari Dako, Koffee Mameya, Nazuna Kyoto Gosho, Omen Kodaiji, Giro Giro Hitoshina, Ippodo Kaboku, Aisunao, Zentis Osaka and Tonkatsu Maisen — and none of them is a transient failure. Rerunning changes nothing.
- **Why it is worth fixing:** the script's whole design point is that a miss is *reported and left missing* rather than guessed (its own method comment, constraint 5). It gets that right; it then files the honest misses under a heading that tells the next reader to rerun. The distinction the report is trying to draw — "the vendor failed us" versus "the vendor has no such place" — is real and currently collapsed, and a genuine rate-limit would be invisible among the nine standing 404s.
- **One of the nine is a symptom of another bug, not of this one:** `d14-s1-breakfast-at-the-hotel` queries `"Zentis Osaka, Kita, Tokyo, Japan"` — a real Osaka hotel with Tokyo in the string, because the day's destination city is folded into the query. That is KI-59, and it is the clearest independent evidence of it: the query is unanswerable because the data is wrong.
- **Fix path:** have the vendor adapter distinguish 404 from other failures, or have the script inspect the error, and add a fourth outcome (`no-results`) alongside `no-candidate-in-box` / `name-mismatch` / `lookup-failed`. Touching `locationiq.ts` makes this a change to a shared seam rather than a script edit, so it wants its own scoped step.
- **Reproduced first, offline, at zero vendor quota (2026-08-30).** Two steps, both executed, neither touching the network. (a) The real adapter, with `globalThis.fetch` stubbed to LocationIQ's actual zero-result answer (`404`, body `{"error":"Unable to geocode"}`): `createLocationIQGeocoder(...).forward(...)` → `THREW: Error: geocode failed: 404`. (b) The script's real `resolveJob` (a byte-identical copy with only `await main()` swapped for an export) driven with a stub geocoder throwing each of those:
  ```
  zero results  -> { ids: [ 'd04-s3-lunch' ], reason: 'lookup-failed', detail: 'Error: geocode failed: 404' }
  rate limited  -> { ids: [ 'd04-s3-lunch' ], reason: 'lookup-failed', detail: 'Error: geocode failed: 429' }
  ```
  A definitive "the vendor has no such place" and a transient rate limit come out of the `catch` as the same outcome, which `main()` then prints under `Lookup failed (rate limit or vendor error — rerun to retry)`.
- **Cause:** `resolveJob`'s `catch` classified *every* rejection as `lookup-failed`. The adapter turns every non-2xx into `Error("geocode failed: <status>")`, so the status — the one thing separating "definitively no" from "we failed" — was discarded at the only place that could read it.
- **Fix (2026-08-30), entirely inside `apps/web/scripts/geocode-japan-seed.mts`:** a `vendorErrorStatus(err)` helper reads the status off the adapter's own anchored throw (returning `undefined` for anything else, so a network error or parse failure keeps the conservative `lookup-failed`), and the `catch` classifies a `404` as a new fourth outcome, `no-results`. The report gained its own section — `No result from the vendor (LocationIQ 404 — it has no such place; rerunning changes nothing)` — listed with the definitive misses, and the summary line counts it separately, so the retryable heading now means what it says. `locationiq.ts` and the `Geocoder` seam are untouched: giving the adapter a typed error would move every caller, and the entry's own fix path allows either.
- **Proven.** The reproduction is now the committed regression test, `apps/web/scripts/geocode-japan-seed.test.ts` (7 tests, green; reverting just the classification line makes exactly the 404 case fail with `expected 'lookup-failed' to be 'no-results'`, so it is not vacuous). End to end, the script itself run with every LocationIQ call stubbed to a 404: `Unresolved: 72 stops (69 no vendor result, 0 no candidate in box, 0 in box but wrong venue, 0 lookup failed)` under the new heading — previously all 69 would have read `lookup failed`. Check subset (`minimal-check-subset`; every changed file maps to `web`, none to `packages/contracts`): `pnpm --filter web typecheck`, `pnpm --filter web lint`, `pnpm --filter web exec vitest run -c vitest.unit.config.ts scripts/geocode-japan-seed.test.ts` — all green. No integration or e2e lane was run.
- **Two supporting changes outside the `catch`.** The script now runs `main()` only when it is the invoked command (`process.argv[1]`, not `import.meta.main` — that is newer than the repo's Node floor and undefined under Vitest) and exports `resolveJob`; without that, importing the module ran the whole 70-lookup pass, which is why this classification had no test. `apps/web/vitest.unit.config.ts`'s node project names the new file, the same way it already names `next.config.test.ts` and `sentry.shared.test.ts` for living outside `src/`; `vitest list` before and after differs by exactly that one added file.
- **Still open, deliberately untouched:** the nine stops remain unresolved — this entry was always about the *label*, not about finding them. `d14-s1-breakfast-at-the-hotel`'s unanswerable `"Zentis Osaka, Kita, Tokyo, Japan"` query is still KI-59. KI-77's three (Gonpachi, Tenryū-ji, Ginkaku-ji) are a different set — they are `name-mismatch`, not 404 — and `geocodeNameMatch.ts` was not opened.
