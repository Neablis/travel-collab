### KI-2026-09-05-p — the optimistic send queue has produced six known issues and two review findings, all fixed as lines; it has no property test over interleavings — RESOLVED

- **Severity:** reliability of verification (no defect of its own — the two live symptoms are KI-5 and KI-90; what is missing is the guard that would stop the seventh)
- **Area:** `apps/web/src/components/trip/context/optimistic.ts` (216 lines), `TripProvider.tsx:315,322`, `optimistic.test.ts` (**zero** uses of `fast-check`, while ten other test files use it), `TripProvider.test.tsx:719-735` (covers only the same-tick KI-70 half)
- **Symptom / What happens:** KI-5, 36, 42, 55, 70, 90 and the 2026-08-28 review's §1.1 and §1.4 are one sentence — "an accepted unit vanished with no failure record". Each was fixed as a line (KI-70's ref read, KI-42's retention) and the next window opened beside it; KI-90 is literally the same line again, after the `await`. Every case in `optimistic.test.ts` is an example the author had already imagined, so the suite cannot find the next one.
- **Why not fixed here:** found by a read-only review; no code was changed by it. It is filed separately from KI-5 and KI-90 because it is not either symptom — it is the missing guard, in the same shape as KI-2026-09-02-e (a code path with no coverage at all).
- **Suggested fix:** one `fast-check` property over a model of the queue — for any interleaving of `enqueue` / `confirmHead` / `failHead` / history-reconcile, every accepted unit is either confirmed, retained in `pending`, or present in `failure`. It would have caught KI-42, 55, 70 and 90 at once, and it forces the one product decision KI-90 defers: gate edits during a history command, or re-predict the queue on top of the reconciled state. Add a `witness` floor per `docs/guidelines/testing.md`.
- **What it will not reach:** KI-5's own trigger (abrupt navigation before the queue drains) is outside the model — it needs a `pagehide`/`keepalive` mitigation, and the review confirmed no `beforeunload`/`pagehide`/`keepalive` exists anywhere in `apps/web/src`.
- **Cross-reference:** [F-E02](../../reviews/2026-09-05-overnight-review/findings/F-E02-optimistic-queue-needs-interleaving-property.md) (MEDIUM, CONFIRMED); KI-5 and KI-90 (the two open symptoms); resolved KI-36, 42, 55, 70; `docs/guidelines/testing.md`.
- **First noted:** 2026-09-05, overnight review stream E.
- **Resolved 2026-09-24 — the guard, added; `optimistic.ts` was not changed.** One `fast-check` property in `apps/web/src/components/trip/context/optimistic.test.ts` ("the optimistic queue loses nothing under any interleaving") drives the reducers exactly as `TripProvider` does — `enqueue`, the head send accepted (`confirmHead`), refused by the server or dropped in transit (`failHead`), the server's no-op path (`confirmHead` against the existing confirmed state), the manual retry (`clearFailure`), another client editing the server, and a poll or history-command reconcile (`adoptOutcome`) — against a model server that decides with the same `decideTripCommand` (`predictBatch`). After every step it asserts: the queue is exactly the accepted units not yet confirmed, in order; `failure` is present iff a refusal has not been retried; unpredicted units are a strict suffix (KI-55); `confirmed` is the last authoritative outcome; and `activeDetail` is the predicted prefix replayed over it. 200 runs of up to 30 steps, ~0.5s. Four witnesses with floors at half the observed minimum over eight runs (steps 1400, retention 12, reconcile-over-queue 37, server refusal 7). **Proven by reintroducing the historical defects one at a time** — each went red with a shrunk counterexample on the matching invariant, and green on restore: KI-42 (`predictable = false` → `break`, dropping units that no longer predict: `expected [] to deeply equal [ 'u2' ]` after edit/edit/remote RemoveActivity/send); KI-55 (store the prediction behind a retained null: the suffix assertion fails after edit/remote RemoveDay/reconcile/edit/send); KI-90 (`adoptOutcome` as `{ confirmed: outcome, pending: [] }`: `expected [] to deeply equal [ 'u1' ]` after edit/reconcile); KI-36 (`failHead` discarding the queue: same, after edit/drop); and `adoptOutcome` dropping a recorded failure (the failure assertion, after edit/drop/reconcile). No new defect was found. The product decision this entry said the property would force was already made by M13 link 3 (`adoptOutcome` re-predicts rather than gating); the property now pins it. KI-5's own trigger (navigation before the queue drains) remains outside any reducer, as stated above, and stays with KI-5.
