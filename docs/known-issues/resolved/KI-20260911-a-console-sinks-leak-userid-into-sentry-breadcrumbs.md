### KI-2026-09-11-a — the AI console sinks put a `userId` into Sentry breadcrumbs, and two of the three pass only by timing — RESOLVED

- **Severity:** correctness (privacy). Not a live leak today; two of three sinks are latent and one was live for the length of one commit.
- **Area:** `apps/web/src/server/ai/askAnalytics.ts` (`logAskAnalytics`), `apps/web/src/server/ai/handleAskRequest.ts` (`defaultApplySink`), `apps/web/instrumentation.ts` / `sentry.shared.ts` (where the general fix belongs)
- **Symptom:** Sentry's `Console` integration is on by default and copies `console.info` arguments into the breadcrumb trail of whatever transaction is open. `ai.ask`, `ai.proposal.apply` and (as of M9 Phase 0 P3) `ai.grant` all `console.info` a record containing `userId`. A breadcrumb attached to a captured transaction is sent to Sentry, so an actor id reaches telemetry on a path nobody declared.
- **How it was found:** P3 (`a8784ef`) wrote the new `ai.grant` line from *inside* the request transaction, and `ask/telemetry.int.test.ts` failed immediately — `expected '[[{"sdk":…' not to contain 'ask-telemetry-owner'`. It failed in the same place every run, which is the tell for a real defect rather than a timeout (CLAUDE.md rule 2; `docs/known-issues/` was grepped first and held nothing). Fixed there by forking the isolation scope around the sink.
- **Why the other two are latent rather than fixed:** `ai.ask` is written *after* the transaction is captured, and the telemetry suite additionally injects a no-op sink, so neither reaches a live breadcrumb today. **Both pass by accident of ordering, not by design** — any change that moves the write earlier, or that captures later, makes either one leak. That is the whole reason this is filed: the property they rely on is invisible and nothing asserts it.
- **Fix path:** `beforeBreadcrumb` in `sentry.shared.ts`, dropping or scrubbing `console` breadcrumbs whose message names one of the `ai.*` events. **Note what does not work:** P3 tried exactly this first and the telemetry suite still failed, because that suite initialises Sentry with **default** options deliberately — so a `sentry.shared.ts` fix is invisible to it. Whoever takes this needs either a second test that exercises the configured client, or to keep the scope fork as the belt beside it.
- **Cross-reference:** [F-A07](../../reviews/2026-09-05-overnight-review/findings/F-A07-bearer-tokens-reach-sentry-unscrubbed.md) — the same class, one layer up: share/invite bearer tokens reach Sentry with no `beforeSend` anywhere and tracing at 100%. **These should be fixed together**; a single `beforeSend`/`beforeBreadcrumb` pass closes both, and doing them separately means writing the same hook twice. ADR-032 (Sentry telemetry), ADR-043 (M9 Phase 0).
- **First noted:** 2026-09-11, by M9 Phase 0 P3.
- **Resolved:** 2026-09-12. Fixed at the boundary, per the "Fix path" above: `sentry.shared.ts` gained `scrubBreadcrumb`, wired as `beforeBreadcrumb` in `sharedSentryOptions` in place of the plain `scrubSentryPayload` it used before. It drops (not scrubs) any `category: "console"` breadcrumb whose message starts with `ai.` — matching the shared naming convention of every sink named in this entry (`ai.ask`, `ai.ask.failed`, `ai.proposal.apply`, `ai.grant`) rather than listing them, so a future sink following the same convention is covered without an edit here. No call site (`logAskAnalytics`, `defaultApplySink`, `logAiGrant`) was touched — the boundary fix covers all three regardless of write order relative to the transaction, which is what closes the "passes only by timing" half of this entry as well as the live leak. `logAiGrant`'s `withIsolationScope` fork is left in place as the belt the "Fix path" note anticipated needing.
  Reproduced first against the real client (`sharedSentryOptions`, a capturing transport, `defaultApplySink`'s exact `console.info(record.event, record)` shape): the breadcrumb's `data.arguments` and `message` carried the live `userId` straight into a sent transaction envelope, confirming the leak is real in production config, not just in a hand-built event.
  Proof: `apps/web/sentry.shared.test.ts`'s `"what actually reaches the Sentry transport"` suite was extended with the exact shapes of all four `console.info`/`console.error` lines the three sinks write (ids generated at runtime via `randomUUID()`, not literals, so the SDK's `ContextLines` integration can't reintroduce a false failure by reading them out of the test's own source near the thrown exception) plus one control breadcrumb. Reverting `beforeBreadcrumb` to plain `scrubSentryPayload` reproduces the failure verbatim: `AssertionError: expected '[[{"sdk":...' not to contain '<generated-uuid>'`, only that one test failing (74 pass / 1 fail) — restoring the fix makes it green (75/75) with no other regression. Checked: `pnpm --filter web typecheck`, `pnpm --filter web lint`, `pnpm --filter web exec vitest run -c vitest.unit.config.ts sentry.shared.test.ts` (75 passed).
