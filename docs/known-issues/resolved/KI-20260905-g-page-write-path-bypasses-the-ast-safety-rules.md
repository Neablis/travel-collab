### KI-2026-09-05-g — the pages write path stores the *parsed* document and checks no widget name, so an unknown node is entombed and the `attribute` allow-list is a browser convention — RESOLVED

- **Severity:** correctness (a stored document is permanently altered by a write, and a documented safety rule is unenforced on the server)
- **Area:** `apps/web/src/app/api/trips/[tripId]/pages/route.ts:23` and `pages/[pageId]/route.ts:20` (both persist `body.data.content` — the Zod *output*, not the received bytes); `apps/web/src/server/pages.ts:97`; `packages/contracts/src/pageDoc.ts:43-44` (`MacroNode.attrs` is `name: z.string().min(1)`, `params: z.record(z.unknown())`), `:118-131` (`KNOWN_NODE_TYPES` excludes `unknown`), `:152-158` (`tagUnknownNode`), `:346` (`v` defaults to 1 with no ceiling), `:571-572` (`serializePageNode` unwraps `unknown` — used by the browser, not the server); the registry walk that *would* check name and params, `walkForError` in `server/ai/pageTools.ts:178-207`, has one caller and it is on the AI path only
- **Symptom / What happens:** two defects at one insertion point.
  1. **Unknown nodes are entombed ([F-B09](../../reviews/2026-09-05-overnight-review/findings/F-B09-storing-parsed-doc-entombs-unknown-nodes.md)).** PATCH a doc containing `{type:"futureNode",foo:1}` through a server that does not know it: stored as `{"type":"unknown","raw":{"type":"futureNode","foo":1}}`; re-read wraps it **again**; `collectPageDocNodeTypes` never reports `futureNode` again. So during a rolling deploy — a newer browser build autosaving through an older server instance — the new node is permanently reclassified and the page opens read-only for everyone. ADR-038 decision 3 was designed for exactly this window; it holds in the browser and is defeated on the server. Reproduced with a node probe.
  2. **Any widget name and any params are accepted ([F-B01](../../reviews/2026-09-05-overnight-review/findings/F-B01-server-accepts-any-widget-name-and-params.md)).** `PATCH {…{type:"macro",attrs:{name:"attribute",params:{field:"account.email"}}}}` is 200 and persisted; so are `cost{person:"x"}` and `nope.nope{}`. ADR-039 decision 6 describes the `attribute` allow-list as what "stops it becoming a field browser"; today that is enforced only in the browser. ADR-037 decision 4 ("no way to put a widget into a document that skips validation") holds for every *insert* path and is bypassed by the *write* path.
- **Why not fixed here:** found by a read-only review; no code was changed by it. Both want the same edit in the same two routes: parse → refuse `v > CURRENT_PAGE_DOC_VERSION` → registry-check via a lifted `walkForError` → store `serializePageDoc(migratePageDoc(parsed))`. Do them together or the second one re-opens the file. Half a day; it is item 1 of the review's executive summary.
- **Cross-reference:** [F-B09](../../reviews/2026-09-05-overnight-review/findings/F-B09-storing-parsed-doc-entombs-unknown-nodes.md) and [F-B01](../../reviews/2026-09-05-overnight-review/findings/F-B01-server-accepts-any-widget-name-and-params.md) (both MEDIUM, CONFIRMED); [F-C05](../../reviews/2026-09-05-overnight-review/findings/F-C05-superseded-by-F-B09.md) (the `v` half, folded in); ADR-037 decision 4, ADR-038 decision 3, ADR-039 decision 6; proposed widget rule 11 in `../../reviews/2026-09-05-overnight-review/README.md` §B.
- **Fix (2026-09-24):** the fix point moved since this entry was written. The routes no longer write rows; every page write, both BFF routes and both `/api/v1` routes, goes through `executePageCommand` (`apps/web/src/server/pageCommands.ts`), so the check and the serialisation live there.
  1. **Widget check.** `walkForError` was lifted from `server/ai/pageTools.ts` into `@tc/pages` as `findWidgetError` (`packages/pages/src/writeCheck.ts`). It judges each `macro` node with `insertWidget` rather than a copy of its rules, so the save path now refuses what the insert path refuses: an unknown name, bad params (including `attribute`'s allow-list), and a filter the widget does not select by. `cost{person:"x"}` from F-B01 passes a bare `params.safeParse` because the schema strips unknown keys, so the insert door was the only check that caught it. `checkPageDocForWrite` (`server/pages.ts`) runs `migratePageDoc`, which refuses `v > CURRENT_PAGE_DOC_VERSION`, and then `findWidgetError`. `executePageCommand` calls it on every `CreatePage`/`EditPage` that carries content and answers `invalid-page`, which the routes already map to 400 (BFF `{error}`, v1 `invalid-request`). `validateComposedPage` uses the same function.
  2. **Canonical storage.** The entombing came from two parses stacked on each other. Each route parsed the body with `PageDoc`, then passed the parse output to `executePageCommand`, which parsed it again, and `applyPageEvents` parsed a third time before writing the row. Every parse wrapped an unknown node once more. A single PATCH stored `futureNode` three levels deep. The routes now pass `serializePageDoc(parsed)` (the wire form, which the executor's docstring now requires). The executor stores the migrated document through `serializePageDoc` in the event payload (`storedPageEvent`) and in the projection row (`storedContent`), so the log and the table hold the same canonical bytes and a rebuild writes the same row.
  - **Proof.** New tests in `apps/web/src/app/api/trips/[tripId]/pages/route.int.test.ts` (describe "the write path stores the canonical document and checks every widget") failed first on unfixed code: `expected { raw: { raw: { …(2) }, …(1) }, …(1) } to deeply equal { type: 'futureNode', foo: 1 }` (PATCH and POST), `expected 1 to be 2` (v-less body not stamped), and `expected 200 to be 400` (future `v`, `nope.nope`, `attribute{field:"account.email"}`, `city.rows{kind:"booked"}`). After the fix: 42/42. Each half was broken again on purpose and went red for its own reason: the check disabled (4 red), serialisation dropped from the executor (2 red), the BFF PATCH route passing the parse output (1 red), migration skipped (1 red). The same file creates every shipped document through POST, and all return 201: `DEFAULT_TEMPLATES`, `TEMPLATE_LIBRARY`, and all 7 notebooks in `content/notebooks/built-in-notebooks.json`. `apps/web/src/server/public-api/surface.int.test.ts` covers v1 POST+PATCH, going red when either v1 route is reverted. `packages/pages/src/writeCheck.test.ts` (14) covers the walker and every shipped template.
