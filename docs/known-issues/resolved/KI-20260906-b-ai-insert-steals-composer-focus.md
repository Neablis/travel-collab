### KI-2026-09-06-b — an AI insert steals focus from the assistant composer, so a follow-up typed while the turn lands loses its keystrokes — RESOLVED

- **Severity:** correctness (user-visible input loss), unquantified — nobody has measured how often a real user types into the composer in the window between an insert rendering and the editor taking focus.
- **Area:** `apps/web/src/components/pages/PageScreen.tsx:240` — `editorRef.current?.chain().focus().insertContent(event.content.content as never).run()`, the `page-inserts` handler; `apps/web/src/components/assistant/AssistantRail.tsx:357-365` (the composer that loses focus).
- **Symptom:** the editor's `.focus()` fires as the last act of applying an insert, *after* the inserted text has rendered. Any keystroke entered into the assistant composer after that render but before the focus call stays in the composer; every keystroke after it goes to the **editor document instead** — silently, including `Enter`, so the follow-up is never submitted and the characters are appended to the page the user was reading.
- **How it is known to be real:** it is exactly what made two `PageAssistant` tests fail (**KI-2026-09-06-a**, resolved). The probe there recorded `document.activeElement` as `DIV.tiptap ProseMirror ProseMirror-focused` mid-type, with the composer holding `"O"` of `"One more thing"` — i.e. thirteen characters and an `Enter` went into the document. A test is not a user, but the mechanism is the product's, not the test's.
- **Why it is not simply "remove the `.focus()`":** the `focus()` is load-bearing. `insertContent` inserts at the current selection, and without focusing the editor first there is no selection to insert at — so removing it changes where content lands, or whether it lands at all. Options worth weighing: restore focus to whatever held it before the insert; only focus when the editor already had focus when the turn started; or insert at an explicit position rather than at the selection.
- **Cross-reference:** **KI-2026-09-06-a** (the test failure this was found through, with the full probe transcript); **KI-2026-09-05-a**, the other open entry about this editor's selection behaviour.
- **First noted:** 2026-09-06, while root-causing KI-2026-09-06-a.

- **RESOLVED 2026-09-07 — the insert no longer TAKES the caret; it only keeps it.** `PageScreen.tsx`'s `page-inserts` handler now builds the chain and includes `focus()` only when `editor.isFocused` is already true: `const insert = editor.chain(); if (editor.isFocused) insert.focus(); insert.insertContent(…).run();`.
- **Reproduced first, on Node v22.22.2 — CI's version, not the Node 26 of the original probe.** The file was green before the change (`Tests 10 passed`, so the sibling KI-2026-09-05-ab's "believed green on 22" holds here). A probe test typed a follow-up with `userEvent.keyboard` — no click, because a user who never stopped typing never clicks — after waiting for the first insert's autosave, and printed:
  ```
  PROBE activeElement after insert: DIV tiptap ProseMirror ProseMirror-focused
  PROBE askAssistant calls: 1
  PROBE composer value: ""
  PROBE last autosaved doc: {"v":2,"type":"doc","content":[…,{"type":"paragraph","content":[{"type":"text","text":"One more thing"}]},…]}
  AssertionError: expected "vi.fn()" to be called 2 times, but got 1 times
  ```
  The whole follow-up — not just its tail — was typed into the page and **autosaved to the server**, the composer was left empty, and the turn was never asked.
- **The mechanism, from the library source rather than inference:** `@tiptap/core` 2.27.2's `focus` command (`dist/index.js:1886`) schedules `view.focus()` inside a `requestAnimationFrame`, so the steal lands a frame *after* the inserted text renders — mid-word for anyone typing.
- **Why this option, and why placement is provably unchanged.** The entry's premise above — "without focusing the editor first there is no selection to insert at" — is not true of this version: `focus()` with no position calls `resolveFocusPosition(doc, null)`, which returns `null`, falls back to `editor.state.selection`, finds the selection identical and never calls `tr.setSelection`. Its only effect is that scheduled frame, and a ProseMirror state always carries a selection whether or not the view holds DOM focus. So `insertContent` lands at exactly the same position either way — confirmed by comparing the autosaved doc JSON before and after the fix, which is byte-identical for the first insert. **Nothing about where content lands, or whether it lands, changed**, so no product decision was needed. Click-to-insert and drop (`insertAtCursor`, `PageEditor.tsx`) are untouched: a click in a popover *should* return the caret to the editor.
- **Regression test:** `PageAssistant.test.tsx` — "keeps a follow-up typed while an insert lands in the composer, not in the page". It deliberately does not use `readyForAnotherTurn`, whose click is exactly what hides this. Seen red for its own reason by restoring the unconditional `focus()`: `AssertionError: expected "vi.fn()" to be called 2 times, but got 1 times`, with `One more thing` visible in the printed ProseMirror document.
- **Proof:** `pnpm exec vitest run -c vitest.unit.config.ts` over the eight unit files that render `PageScreen` — `Test Files 8 passed (8) / Tests 129 passed (129)`; `pnpm --filter web typecheck` and `pnpm --filter web lint` both clean. No e2e spec exercises an insert (`m7-solo-delight.spec.ts` only opens the rail).
