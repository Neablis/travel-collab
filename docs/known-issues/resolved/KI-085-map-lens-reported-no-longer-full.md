### KI-85 — The Map lens reported as "no longer full height", not reproduced — RESOLVED, not reproducible
- **Severity:** cosmetic — and **unconfirmed**; this entry exists so the report is not lost, not because a defect is established
- **Area:** `apps/web/src/components/lenses/MapLens.tsx`, `.map-lens` / `.map-lens-canvas` in `apps/web/src/app/globals.css`
- **Symptom as reported:** Mitchell, on PR #89's preview (2026-08-29), with a screenshot: the map does not fill the height it used to. Seen on his own trip at `?lens=Map`, in a **3440×1271** window.
- **What was checked, and what it rules out.** The report arrived on a PR that changed `DayChips`, which sits directly above the map, so the obvious suspect was a taller header squeezing a flex-sized lens. Measured both ways on the same page and viewport — with that change checked out, and with the previous version:
  ```
  pre-change   header 153px   map lens 630px   top offset 288px
  post-change  header 153px   map lens 630px   top offset 288px
  ```
  Not a pixel moved. PR #89's diff also contains no change to `MapLens.tsx`, to `globals.css`, or to any container above the lens. On `/demo?lens=Map` at 1200×900 the map ran to the bottom edge with the MapLibre attribution bar on it.
- **Why it is still filed.** Three things differ between that check and the report, any of which could carry it: a 3440px-wide window versus 1200px (a much wider aspect than anything tested), `/demo` renders a banner above the board that a real trip does not, so the offsets above the lens differ, and the report is against a Vercel preview rather than a local build. None of those were eliminated.
- **What would settle it:** open `/demo?lens=Map` at ~3440×1271. Full height there means it is specific to a real trip's header and this is a live defect; short there means it is width-dependent and reproducible without an account. Either way it is **not** PR #89's — that much is measured — so it belongs to whatever change did it, or to `main` as it stands.
- **Cross-reference:** KI-49 (the Map lens's tiles have never been confirmed to paint — a different and still-open claim about the same lens); KI-2026-09-06-g (the same canvas's inline height, resolved separately by swapping `100dvh` for `100svh` to close a mobile scroll-growth loop — unrelated mechanism, doesn't touch this report's repro, see below).
- **First noted:** 2026-08-29 (PR #89 preview review).
- **Resolution (2026-09-12): closed as not reproducible, per this entry's own settling test, run twice.** Ran the exact check the entry names — `/demo?lens=Map` at 3440×1271 — locally (`pnpm --filter web dev`, Playwright/Chromium, viewport 3440×1271). The canvas ran to the exact bottom of the viewport (`canvasRect.bottom === 1271 === window.innerHeight`, `document.documentElement.scrollHeight === 1271`, i.e. zero page overflow either way): full height, not short.
  Per the entry's own decision rule that alone leaves open "specific to a real trip's header" rather than settling it, since `/demo` draws `FrontDoorHeader` + a banner above the shared `TripBoardScreen`, not the authenticated app's real `AppHeader` (`(app)/layout.tsx`) a real trip uses. So the second, decisive half: signed in via dev login, used "Make this trip mine" to clone the demo trip into a fresh account (`POST /api/trips/:id/duplicate` under the hood), and loaded the **real, owned trip** at `/trips/<id>?lens=Map`, same 3440×1271 viewport. The measured top offset differed from `/demo`'s, as expected (251.98px vs 289.67px) — confirming the two headers really are different heights, the one variable the entry flagged and never eliminated — but the canvas still ran to the exact bottom of the viewport (`canvasRect.bottom === 1271`, `docHeight === 1271`). Screenshot confirmed the same visually: rail, day list and canvas all reach the window's bottom edge with no strip of page under them (tiles render blank per KI-49 — this container's egress proxy blocks `tiles.openfreemap.org`, confirmed by the console's 403/`ERR_CONNECTION_RESET` on the style/tile requests — which is expected and unrelated to layout height).
  **Why this holds regardless of header height, and so why width and header shape were both red herrings:** the canvas's height is not a fraction of the viewport or a flex share of it — it's `calc(100svh - <measured top>px - var(--rack-height, 0px) - var(--phone-tab-bar-height, 0px))`, where `<measured top>` comes from `canvasRef`'s own `getBoundingClientRect()` (re-run via a `ResizeObserver` on `document.body` and on `window`'s `resize`). That construction is self-correcting: whatever sits above the canvas, and at whatever width, the canvas's bottom edge is `100svh` (the actual small-viewport height) minus two variables that are genuinely `0px` at desktop widths (`--phone-tab-bar-height` is `md:hidden`; `--rack-height` reports `0px` with no unscheduled rack open) — i.e. it always lands exactly on the window's bottom edge once `canvasTop` has been measured at all. Confirmed the reverse is detectable and not a measurement artefact: temporarily hardcoding the canvas height to `70vh` (the pre-fix value the code's own comment names as the old, broken behaviour) reproduced a real, measurable shortfall at the same viewport (`canvasRect.bottom === 1179.36` against a `1271` viewport) with the same script — so the check is capable of catching the reported symptom, and did not do so against the real code at either header.
  Also checked, since no width breakpoint anywhere in `globals.css` sits above 1180px: nothing in the CSS or in `MapLens.tsx` treats ≥1180px specially, so there is no mechanism by which 3440px would differ in kind from the 1200px and 1180px widths already checked by this entry and its neighbours.
  **What this does not clear, honestly:** the report was against a Vercel preview build, not a local `pnpm dev`; that variable the entry flagged is still untested; a build-only or preview-infrastructure-specific cause (e.g. a stale asset, a race unique to preview's cold start) cannot be ruled out by this session, which had no way to reach a preview deployment. No regression test was added: the mechanism above is a live-DOM/CSS `calc()` result that jsdom does not lay out, so a unit test could only assert the height *string* (already covered by `MapLens.test.tsx`'s `svh`-not-`dvh` test) — it cannot assert that the string resolves to the window's actual bottom edge without a real browser, and a Playwright e2e for this would need the very preview-vs-local gap this session could not close to mean anything beyond what was just verified once, live.
  **Left untouched:** no code change was made — nothing to fix, since nothing reproduced. `KI-2026-09-06-g` (the `dvh`→`svh` swap already merged in ahead of this session) does not interact with this report's mechanism: `svh` and `dvh` render identically on a desktop browser with no dynamic toolbar, so that change neither caused nor cured this one.
