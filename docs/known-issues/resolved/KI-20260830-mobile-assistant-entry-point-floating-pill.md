### KI-2026-08-30 — The mobile assistant's entry point is a floating pill launcher, which SPEC §13.5 rules out outright — RESOLVED
- **Severity:** cosmetic — but it is a *stated spec violation* rather than an accident, which is why it is filed rather than left in a fixed entry's footnote.
- **Area:** `apps/web/src/components/assistant/AssistantRail.tsx` (the launcher), `apps/web/src/app/globals.css` (`.assistant-rail`), `SPEC.md` §9/§10/§13.5.
- **What is wrong:** below 768px the rail itself is now correct — KI-84 made it a full-screen `position: fixed` surface, walked in a browser at 411×852 and 375px. The way you *open* it is not. It is still a pill that floats over the plan, and `SPEC.md` §13.5 forbids exactly that, in terms: *"Nothing floats over data. No floating action button."*
- **This was off-spec before KI-84's fix and is off-spec after it.** KI-84 changed what happens once the rail opens; it did not touch the launcher, and said so. Nothing regressed here — the violation is unchanged and pre-existing.
- **Why not fixed here:** redesigning the mobile entry point is a design decision, not a defect fix. It needs §10's "mobile is retrieval, not planning" framing plus a genuine phone surface, and neither exists yet. SPEC's two other assistant presentations — the 56px bubble and the 364×476 floating card (§9) — are still M16-deferred per Mitchell's 2026-08-25 call, and are the more likely long-term answer to the launcher question than anything bolted onto a full-screen rail.
- **Why it is its own entry:** it was the reason KI-84 sat in `## Open` marked "MOSTLY RESOLVED" while the defect it was actually filed for was fixed and proven. A closed defect held open by an unrelated design question is invisible work on both counts — the fix looks unfinished and the design question looks like a footnote.
- **Cross-reference:** KI-84 (resolved — the rail fix this was carved out of), `docs/milestones/M16-assistant-read-agent.md` ("Deferred, and owned by this milestone so it stays routed"), `SPEC.md` §9/§10/§13.5.
- **First noted:** 2026-08-29, inside KI-84. Split into its own entry 2026-08-30.
- **Reproduced (2026-09-02), before touching anything.** Chromium at 402×874 against a local dev server, a `threeDayTrip` on the Day columns lens, assistant closed, reloaded at the phone width so any load-time device gate re-ran. The launcher measured `position: fixed; right: 24px; bottom: 63.19px; z-index: 40`, 114.53×40.30, box at x=263 y=770 — a filled-brand pill sitting on top of the day columns in the viewport's bottom-right corner, which is the corner a stop card's cost is right-aligned into. Same measurement at 411×852 (the `phone` Playwright project's own viewport): `position: "fixed"`, height 40.30.
- **Cause.** Not the rail. The launcher is rendered by `TripBoardScreen.tsx` — *not* `AssistantRail.tsx`, which this entry's **Area** line names; the rail only ever renders the open state — as a `position: fixed` element mounted outside the plan's flex row, with `right-6 z-40` and a measured `bottom` offset, unconditionally at every width. Nothing gated it on the breakpoint the rest of the phone treatment already uses.
- **The fix (2026-09-02).** The launcher keeps the design's minimized pill at `>=768px` and stops floating below it. Below 768px it is a full-width, 44px-floor (§13.1) button in normal flow, mounted as the last child of `.trip-board-content` — §13.5's own remedy for a FAB, "adding sits at the end of the day, as on desktop". It is mounted *inside* that div rather than after the flex row so the existing `padding-bottom: calc(24px + var(--rack-height))` reservation — which exists to keep content clear of the `position: fixed` unscheduled rack — does for the launcher exactly the job it already does for the day columns; placed after the row it would have landed underneath the rack's bar. `md:min-h-0` releases the phone's 44px floor above the breakpoint so the docked pill keeps its exact 40.297px height. One CSS rule moved with it: `.assistant-launcher .map-lens-canvas .maplibregl-ctrl-bottom-right`'s 158px reservation is now scoped to `@media (min-width: 768px)` — that padding exists only to keep MapLibre's attribution out from under the fixed pill, and below 768px there is no fixed pill, so unscoped it reserved 158px of a 402px canvas for nothing and wrapped the attribution onto three lines (the same "gap in front of nothing" the rule's own /demo note describes). Same 768px `.assistant-rail`, `.unscheduled-rack`, `useIsPhone` and TripHeader's `hidden md:block` already draw. Files: `apps/web/src/components/board/TripBoardScreen.tsx`, `apps/web/src/app/globals.css` (that one selector), `apps/web/e2e/m16-mobile-assistant.spec.ts`.
- **Proven.** Same reproduction re-run after the change, at 402×874 and at 411×852: `position: "static"`, 44px tall, in flow at the end of the plan column, `right: auto`, `z-index: auto` — nothing floats over data. Desktop is byte-identical to before: at 1280×800 and at 1100×800 (the `narrow` project's width, and KI-46's range) the pill still measures `fixed`, `right: 24px`, `bottom: 63.19px`, `z-index: 40`, 114.531×40.297 — the same numbers taken before the change. Map lens re-walked at both widths: attribution padding is `0px` at 402px and `158px` at 1280px. Checks (`minimal-check-subset`, all files map to `web`, no `packages/contracts` change): `pnpm --filter web typecheck` clean; `pnpm --filter web lint` clean (one pre-existing unrelated warning in `ui/dialog.tsx`); `pnpm --filter web exec eslint e2e/m16-mobile-assistant.spec.ts` clean, run explicitly because `lint` is `eslint src` and misses `e2e/`; `node scripts/check-color-wall.mjs` OK (463 files, no new colour — the change adds no literal); `pnpm --filter web exec vitest run -c vitest.unit.config.ts src/components/board/TripBoardScreen.test.tsx` 50/50 passed.
- **Regression test.** `e2e/m16-mobile-assistant.spec.ts` gains "the launcher does not float over the plan: SPEC §13.5 allows no phone FAB", in the existing `phone` (411×852) project — the layer this repo already uses for breakpoint behaviour (KI-19), since jsdom loads no stylesheet and could only assert a class string. It asserts the launcher is neither `fixed` nor `absolute`, clears 44px, and still opens the rail. The three KI-84 tests beside it would all pass with the pill restored: they click a button named "Assistant" and never ask where it is. Proven red-first by reverting the fix and re-measuring at the spec's own 411×852 — `position: "fixed"`, height `40.297` — which fails both assertions; restored, both pass. That red/green was measured with a standalone Playwright script against a dev server, not the `test:e2e:ci-like` runner, which was deliberately not run: several KI fixers were working in parallel and a full lane run reproduces exactly the contention KI-13 documents. The assertion was verified at the identical viewport the spec's project uses, but the spec file itself has not been executed by the Playwright runner.
- **Two costs worth stating.** (1) On a long lens the in-flow launcher is now at the end of a scroll rather than always on screen — on Timeline at 402px it sits at y≈2011, and on the full-bleed Map lens it is just below the fold. That is the trade §13.5 makes on purpose ("adding sits at the end of the day"), not an oversight. (2) The two other §9 presentations (56px bubble, 364×476 floating card) remain M16-deferred, so this does not pre-empt the long-term answer to the launcher question — it removes the spec violation from the presentation that ships today.
- **Not resolved as "remove the launcher on a phone",** which the design file would also support (its `surface: phone` has no assistant entry point at all): it would have contradicted Mitchell's own 2026-08-29 direction that the mobile assistant be "a full page experience" rather than gone, and it would have required deleting three passing tests.
- **Resolved:** 2026-09-02.
