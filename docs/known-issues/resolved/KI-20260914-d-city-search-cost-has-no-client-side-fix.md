### KI-2026-09-14-d — `/api/cities` runs an unindexed aggregate on every settled keystroke, and the client cannot cache its way out — RESOLVED

- **Severity:** cost / latency — not a correctness defect. The endpoint is correct; it is just the most expensive read per call in the app, and it is called from a typeahead.
- **Area:** `apps/web/src/server/cities.ts:46` (`searchCities`), reached from `apps/web/src/app/api/cities/route.ts` and `apps/web/src/components/playbooks/CitySearch.tsx:75` (250ms debounce, no memo).
- **What is wrong:** every settled query runs `select city, count(*) from saved_days, unnest(cities) as city where visibility = 'public' and deleted_at is null and city ilike $prefix group by city` — an `unnest` over every published saved day, with a prefix match no ordinary index serves. Backspacing through "Kyoto" and retyping it asks the same question again, and the index it aggregates changes only when someone publishes or unpublishes a day.
- **How it came to light:** PR #175 (the ADR-046 read cache) shipped a client-side memo and a `Cache-Control: private, max-age=300` header for exactly this. The memo broke `e2e/m11b-playbooks.spec.ts:339` — *"city search shows all four states against the real endpoint"* — at line 374: step 4 routes `/api/cities` to abort and refills the city string step 1 already searched, so the cached answer meant **no request was made and the failure state never rendered**. Reproduced locally under `test:e2e:ci-like`, same line as CI.
- **Why not fixed there — and the general lesson:** **on this endpoint, saving the request and keeping the failure state reachable are mutually exclusive.** A cache that saves the request cannot fail; a stale-while-revalidate cache keeps the state and saves nothing, which was the whole point. The four states are a milestone exit gate, so the cache came out rather than the gate being bent. The `Cache-Control` header was removed with it even though the e2e passed with the header alone: that pass is an artifact of Playwright's `page.route` intercepting ahead of the browser's HTTP cache, and a real user under `max-age=300` has the same staleness the memo had. Shipping a behaviour whose safety rests on a test blind spot is worse than shipping neither.
- **Scope:** the saving belongs on the **server**, where the request still happens and every client-observable state survives. Options, cheapest first: memoize `searchCities` per process with a short TTL; add an `ETag` + `max-age=0, must-revalidate` so a repeat is a 304 rather than a re-aggregate; or materialise a `city -> published day count` projection maintained on publish/unpublish (the invariant-2 "projections are disposable" shape) and index it. The third is the real fix and the only one that removes the aggregate rather than hiding it.
- **Cross-reference:** ADR-046 (Consequences names this), PR #175, `apps/web/src/lib/queryCache.ts`'s header comment ("There is deliberately no window for search").
- **First noted:** 2026-09-14, while driving PR #175 to green.
- **Fix (2026-09-25):** a per-process memo in front of the aggregate, on the server (`apps/web/src/server/cities.ts`). `searchCities` holds each query's answer for 30 s, keyed on the query exactly as typed and capped at 500 entries (oldest out first). Callers get copies of the rows. A rejected aggregate is dropped, so the next request goes back to the database. `forgetCitySearches()` clears the memo and runs after every in-process write that can change the index: `setSavedDayVisibility` (publish/unpublish), `editPlaybook` when it changes visibility, `actOnReport` hide-day/restore-day (after the commit, not inside the transaction) and the two dev seed routes. `deleteSavedDay` doesn't need it because it refuses a public day. The request still reaches the server every time, so all four states of the search box, including failure, are still reachable. The memo also serves `/api/places` and `/api/v1/cities`, which call `searchCities`.
- **Reproduction (before the fix):** a new int case, *"answers a repeated query without re-running the aggregate"*, spies on `db.execute` and searches the same city twice: `AssertionError: expected "execute" to be called 1 times, but got 2 times` (`cities/route.int.test.ts:176`).
- **Proof:** that case is now green. A second new case, *"does not remember a failed search"*, rejects the first `db.execute` and expects the retry to get the answer. Break-and-restore: dropping the failure eviction, the `forgetCitySearches()` in `setSavedDayVisibility` and the one in `actOnReport` turned 4 cases red, each for its own reason: `Error: connection dropped`; the unpublish case, `expected [ { city: 'Kyotoish…', …(1) } ] to deeply equal []`; the publish case, `expected [] to deeply equal [ { city: 'Kyotoish…', …(1) } ]`; and reports' hide-day, `expected [ { city: 'Repmod…', days: 1 } ] to deeply equal []`. With the code restored, 23/23 passed. Checks: `node scripts/with-test-db.mjs vitest run` on the cities, places, reports, saved-days/[savedDayId], playbooks and public-api collections int files (6 files / 68 tests green), `pnpm --filter web typecheck`, `pnpm --filter web lint`, and `pnpm --filter web test:e2e:ci-like e2e/m11b-playbooks.spec.ts` (4 passed, including *"city search shows all four states against the real endpoint"*).
- **Decision (2026-09-25 overnight sweep):** option 1, the short-TTL server memo. **Rejected: option 3, a materialised `city -> published count` table.** `saved_days` has seven writers: owner publish/edit, moderation, the moderation carry on rewrites, two dev seed routes, and `scripts/import-content-production.ts`, which runs in another process. The repo has no triggers to hang maintenance on, so the table would need hand-maintenance in each writer or the repo's first trigger. It would also add a migration to the M14 queue that production hasn't run yet. `saved_days` is Community CRUD, not a log-sourced planning projection, so invariant 2 doesn't cover it and nothing guaranteed it could be rebuilt. **Rejected: option 2, `ETag`/304.** The server has to know the answer to produce the tag, so a 304 still pays for the aggregate unless a cheap version stamp exists, and none does. **The freshness cost, accepted:** the instance that handles a publish, unpublish or hide clears its memo and is fresh at once. Another serverless instance, or a production import, can show a count up to 30 s old. A day can be counted for up to 30 s after it stops being public, but a city that never had a public day never appears. If that window matters, option 3 is still the fix that removes the aggregate.
