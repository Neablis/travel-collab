### KI-2026-09-24-v — nobody has checked whether the Sentry build plugin contacts Sentry during the build that e2e serves — RESOLVED

- **Severity:** process, and low. This is build-time traffic, not test traffic.
- **Area:** `withSentryConfig` in `apps/web/next.config.ts`; the `pnpm build` inside `test:e2e:ci-like` and in the CI build step.
- **Symptom / what happens:** the e2e build now sets `NEXT_PUBLIC_SENTRY_DSN=""`, so the served app sends no events: no built chunk carries the ingest DSN (now checked on every e2e build by `pnpm --filter web check:build-sentry`, in `ci.yml` and `test:e2e:ci-like`), and a request-logging probe saw no `/monitoring` tunnel POSTs (2026-09-24). The Sentry webpack/Next plugin itself may still phone home at build time (release creation, source-map upload when `SENTRY_AUTH_TOKEN` is set, or its own telemetry). Nobody measured this.
- **Why not fixed here:** it was outside the e2e change. Checking it needs a build with egress observed, and without `SENTRY_AUTH_TOKEN` the upload path should already be a no-op.
- **What to do:** run one `pnpm build` with the token unset and network logging on. If the plugin makes a request, set its `telemetry: false` / skip-upload options for non-deploy builds.
- **First noted:** 2026-09-24, the no-third-party-in-tests change.
- **Resolved 2026-09-25 (overnight KI sweep).** It did. The plugin's own telemetry (`telemetry`, on by default in `@sentry/bundler-plugin-core` 5.3.0, where `normalizeUserOptions` has `telemetry: userOptions.telemetry ?? true`) starts a Sentry client with Sentry's DSN (`o1.ingest.sentry.io/6690737`). During `runAfterProductionCompile` it sends a session and an "execution" span to that DSN. **Reproduction:** `NEXT_PUBLIC_SENTRY_DSN='' pnpm --filter web build`, with `SENTRY_AUTH_TOKEN` and `CI` unset, `HTTPS_PROXY`/`HTTP_PROXY` pointed at a local logging proxy that refuses `*sentry*`, all under `strace -f --seccomp-bpf -e trace=connect`. The proxy saw only `fonts.googleapis.com` and `fonts.gstatic.com`. strace showed the `next build` process itself doing `connect(70, {sa_family=AF_INET, sin_port=htons(443), sin_addr=inet_addr("34.160.81.0")}) = -1 EINPROGRESS`, twice, after a DNS lookup to 8.8.8.8. `getent ahostsv4 o1.ingest.sentry.io` gives `34.160.81.0`. So the telemetry goes **around** the proxy, which is why a proxy log alone would have said "nothing". No other Sentry host was contacted: `sentry.io` (`34.111.148.117`, `34.8.226.60`), the API that release creation and source-map upload would use, got no connect. Without a token both already skip themselves.
- **Fix:** `telemetry: false` in `withSentryConfig`'s options (`apps/web/next.config.ts`), with a comment giving the evidence.
- **Proof:** a controlled A/B on the same warm `.next/cache`, with `DATABASE_URL` set as in `ci.yml`, and both builds exit 0. With the line commented out, strace again shows two `connect(… sin_port=htons(443), sin_addr=inet_addr("34.160.81.0"))`. With it in place, the only `connect()` in the whole build is one loopback IPC socket (`127.0.0.1:45747`). There is no DNS lookup and no connection to any Sentry address. `runAfterProductionCompile` ran in both builds. Regression guard: `next.config.test.ts`, *"the Sentry build plugin › is configured with its own telemetry off"*. It wraps the real `withSentryConfig` in a `vi.doMock` spy and asserts that the options it received carry `telemetry: false`. With the line commented out it fails: `AssertionError: expected undefined to be false // Object.is equality`. Restored, it passes 44/44. **Checks:** `pnpm --filter web typecheck` (exit 0), `pnpm --filter web lint` (exit 0), `pnpm --filter web exec vitest run -c vitest.unit.config.ts next.config.test.ts` (44/44).
- **Decision (2026-09-25 overnight sweep):** telemetry is off on **every** build, Vercel deploys included, not only on non-deploy builds. The data goes to Sentry's own project about their plugin, is worth nothing to this app, and tags each build with our org slug. Rejected: gating on `VERCEL`/`SENTRY_AUTH_TOKEN`, which adds an environment branch for no benefit and leaves deploy builds making a request nobody reads. Rejected: `sourcemaps.disable` or `release.create: false` on non-deploy builds. Both already skip themselves when there is no auth token (the plugin logs "No auth token provided. Will not …"), and the observed build contacted no Sentry API host, so a second switch would add configuration without changing behaviour. The unconditional choice is reversible by deleting one line.
