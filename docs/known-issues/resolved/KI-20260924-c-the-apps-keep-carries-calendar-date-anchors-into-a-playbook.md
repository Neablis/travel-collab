### KI-2026-09-24-c — keeping days in the app carries calendar-date anchors into the Playbook — RESOLVED

- **Severity:** product correctness, low. The anchor is kept, not lost; it is
  just meaningless (and conflict-raising) in any other trip.
- **Area:** `apps/web/src/server/savedDays.ts` (`captureDays` / `storeSavedDay`
  as the app's keep calls them), `withoutDateAnchors`.
- **Symptom:** a Playbook kept through the app keeps a stop's `dateRange`
  anchor, so applying it to a trip in another month raises an anchor conflict on
  that stop. The same capture over `POST /v1/playbooks` strips the anchor and
  returns a `date-anchor-removed` warning (ADR-050 decision 8), so the two paths
  disagree.
- **Why not fixed here:** stripping in the app changes a shipped UI behaviour
  and wants the Keep dialog to say so (the API says so in its warnings; the app
  has nowhere to show one yet). A design decision, not a one-liner.
- **Cross-reference:** ADR-050 decision 8.
- **First noted:** 2026-09-24, Playbooks API pass A.
- **Fix (2026-09-25):** `saveDay` (`apps/web/src/server/savedDays.ts`) takes `dateAnchors: "keep" | "strip"`. With `"strip"` it runs the same `withoutDateAnchors` step `POST /v1/playbooks` runs, between `captureDays` and `storeSavedDay`. The app's route (`apps/web/src/app/api/saved-days/route.ts`) passes `"strip"`. The default stays `"keep"` because `POST /v1/library` (`public-api/library.ts` `keepDays`) also calls `saveDay`, and `/v1` behaviour is out of scope here. `KeepDayDialog` now says, before the button acts, which selected stops will lose a calendar-date anchor (`droppedDatesNote`, `data-testid="keep-day-dropped-dates"`). Weekday, time-of-day and holiday anchors are kept and not mentioned. The dialog restates the server's rule (`kind === "dateRange"`) because `savedDays.ts` is server-only; the server is what decides. ADR-050 decision 8 carries a one-paragraph amendment saying the gap is closed.
- **Reproduction (before the fix):** a new case in `apps/web/src/app/api/saved-days/route.int.test.ts` keeps a day whose stop has a `dateRange` and a `dayOfWeek` anchor through `POST /api/saved-days`. It failed with `AssertionError: expected [ { kind: 'dateRange', …(2) }, …(1) ] to deeply equal [ { kind: 'dayOfWeek', …(1) } ]`, and the diff showed `"from": "2027-05-03", "kind": "dateRange", "to": "2027-05-05"` surviving into the saved day.
- **Proof:** that case now passes (11/11 in the file). A new `KeepDayDialog.test.tsx` case pins the one-stop and several-stop wording and checks that a weekday-only stop gets no note. Red-then-green on each: with the route passing `"keep"`, the int case went red with the same assertion as the reproduction. With the dialog filtering on `dayOfWeek`, the unit case went red with `Expected: "…the date anchor on "Flea market" won't be kept." Received: "…the date anchor on "Temple" won't be kept."`. Both were restored and went green. Checks: `pnpm --filter web typecheck`, `pnpm --filter web lint`, unit `KeepDayDialog`/`KeepDayFlag`/`TripHeader` (57/57), and int `src/app/api/saved-days/**`, `savedDays{,.sequence,.stops}.int.test.ts`, `public-api/playbooks.int.test.ts`, `public-api/collections.int.test.ts` (9 files, 121/121).
- **Decision (2026-09-25 overnight sweep):** the dialog states the loss before the keep, not after it: *"A Playbook has no dates, so the date anchor on "X" won't be kept."* / *"…so the date anchors on N stops won't be kept: "X", "Y"."*. This follows the dialog's existing "say it before it happens" rule (M23 link 4, §35.7). The route response stays `{ savedDay }` with no new fields. Rejected: returning a `warnings` list from `POST /api/saved-days` and showing it after the keep. The dialog closes on success and hands off to the pennant's "Kept" choreography, so there is no success state to put it in, and telling the user after the keep is less honest than telling them before. Also rejected: making `"strip"` the default in `saveDay`, which would silently change `POST /v1/library`.
