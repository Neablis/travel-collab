### KI-2026-09-05-r — `getTripDetail` returns the stored doc unparsed, typed by a Drizzle cast, and six callers take it raw — RESOLVED, it parses at the source and the cast is now labelled as one

- **Severity:** correctness (latent — no defect today; the type is a lie that every new caller inherits)
- **Area:** `apps/web/src/server/projections.ts:61-64` (`return rows[0]?.doc ?? null`); `server/db/schema.ts:94` (`.$type<TripDetail>()` — the compile-time cast that makes the type true without a parse); raw callers `cloneTrip.ts:139,143,152`, `access/shares.ts:142`, `access/invites.ts:193,197,244`, `api/trips/[tripId]/members/[userId]/route.ts:39`; `access/trip-access.ts:92` (the one place KI-74 fixed, downstream, with `safeParse` + logged issues)
- **Symptom / What happens:** none today, and that is why this is LOW — the review **downgraded** it from PLAUSIBLE to "latent trap, no defect". Every raw caller reads only day-one, non-defaulted fields (`status`, `members`, `name`), and clone re-reads activities from events, so no reproduction exists. What is wrong is structural: KI-53, 71, 73, 74, 88 and 92 are one class — "a value crossed a boundary typed but not parsed" — and KI-74 fixed the *seam* while leaving the *source* returning the lie, so the next caller starts wrong by default.
- **Why not fixed here:** found by a read-only review; no code was changed by it. It is filed because the class it belongs to has six entries and this is the remaining source of it.
- **Suggested fix:** make `getTripDetail` return `TripDetail.parse(doc)` and delete the parse at the seam — or rename it `readRawTripDoc(): unknown` so the type stops lying and each caller parses. Either way, comment `schema.ts:94` that `$type` is a cast, not a guarantee.
- **Reproduced before fixing:** the entry says "no reproduction exists", and for a *user-facing* symptom that stands — every raw caller reads day-one fields only. What is reproducible is the crossing itself, and two tests written against `getTripDetail` before any code changed both failed against the unmodified function. A trip whose stored doc was aged back to pre-M18 (no `kind`, no `tags`, no `forkedFrom` key): `AssertionError: expected undefined to be 'planned'` — the contract's `.default()`s exist only inside a parse. And a stored doc with `members: []`, which `TripDetail`'s `.min(1)` forbids outright and no default can repair: `AssertionError: promise resolved "{ …(17) }" instead of rejecting` — a document satisfying none of `TripDetail` handed back under `Promise<TripDetail | null>`, with no error anywhere.
- **Fix (2026-09-07):** the first of the two suggested options — parse at the source. `getTripDetail` now `safeParse`s the row and returns `parsed.data`; on failure it logs `{ tripId, issues }` and throws. Throwing rather than returning `null` because `null` is that function's word for "no such trip" and a malformed row is not a missing trip; logging the `tripId` because the throw does not carry it and the id is what makes the row findable (the reason KI-74 logged it at the seam). The second option — renaming to `readRawTripDoc(): unknown` — was rejected: it renames a function with ~90 call sites across 20+ files, far outside this entry's Area, and it makes all seven callers repeat the parse, which is the "every caller must remember" shape that produced this six-entry class in the first place. `db/schema.ts` now carries the comment the entry asks for, stated for every `$type` in the file, with the rule that follows from it: reading `trip_details.doc` anywhere other than through `getTripDetail` re-opens the hole.
- **One deviation from the suggested fix, deliberate:** the seam's `safeParse` in `access/trip-access.ts` was NOT deleted. It is no longer what makes a legacy row safe, but it is not redundant — the value it parses is `{ ...projected, members }`, where `members` is `effectiveMembers(...)`, whose granted half is built in `access/members.ts` as `{ userId: r.userId, role: r.role as TripRole }` off a `text` column. That cast is unchecked, so a `trip_memberships` row carrying a role no `TripRole` names reaches the read boundary through this parse and nowhere else; deleting it would drop that guard and the deliberate logged-500 `malformed-trip` channel with it. Both doc comments were rewritten to say what the parse now guards, so the next reader does not re-derive it. (The stray-role cast itself is a separate instance of this class and was left alone.)
- **Proof:** the two tests above, in `apps/web/src/server/projections.int.test.ts`, now pass — `Test Files 1 passed (1) / Tests 3 passed (3)`, with the new `trip_details doc failed TripDetail parse { tripId: …, issues: [ { code: 'too_small', minimum: 1, … } ] }` on stderr showing the refusal is the parse's and not an incidental throw. Non-vacuous by construction: both were written first and quoted failing above. Check subset per the `minimal-check-subset` skill — all four changed files map to `web`, and because the change is to a projection several suites rebuild, the skill's own rule escalates the test half to the whole integration lane: `pnpm --filter web typecheck` (clean), `pnpm --filter web lint` (clean), `pnpm --filter web exec vitest run -c vitest.unit.config.ts src/server/access/members.test.ts` (12 passed), `pnpm --filter web test:int` (**40 files, 471 tests, all passed**) — which is what proves the parse did not break `cloneTrip`, `shares`, `invites`, the member-removal route or `requireTripAccess`.
