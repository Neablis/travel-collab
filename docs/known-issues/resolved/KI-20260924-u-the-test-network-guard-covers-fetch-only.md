### KI-2026-09-24-u — the unit and integration network guard blocks `fetch` only; `http`/`https`, XHR, `sendBeacon` and WebSocket can still reach a third party — RESOLVED

- **Severity:** process. There's no known leak today. This is a gap in the backstop behind the "no automated test talks to a real third party" policy (Mitchell, 2026-09-24).
- **Area:** `apps/web/src/test-support/networkGuard.ts`, installed by `networkGuard.setup.ts`, which both lanes run (`vitest.config.ts` names it; `apps/web/vitest.setup.ts` imports it).
- **Symptom / what happens:** the guard rejects any `fetch` to a non-localhost host that MSW doesn't answer. Node `http.request`/`https.request`, `XMLHttpRequest`, `navigator.sendBeacon` and `WebSocket` aren't intercepted. A future dependency that uses one of them would reach the real service silently.
- **Why it matters more than it looks:** the integration lane loads `apps/web/.env.local`, which on a developer machine carries real `LOCATIONIQ_API_KEY`, `AI_GATEWAY_API_KEY` and `STRIPE_SECRET_KEY` values. The guard is the only thing between an unstubbed call and the vendor.
- **Why not fixed here:** checked 2026-09-24. Nothing that tests import uses those transports; every third-party client in `src/server` goes through `fetch`. Sentry's node transport is the exception, and it is closed by the DSN instead: `networkGuard.setup.ts` forces `NEXT_PUBLIC_SENTRY_DSN` to `""` in both lanes, overriding a value `.env.local` may set, and `networkGuard.int.test.ts` asserts it. Covering them is cheap only if something starts to need it.
- **The e2e lane is covered differently:** Chromium launches with `--host-resolver-rules` that fail every non-app host, and route interception answers the map host (`apps/web/playwright.config.ts`, `e2e/fixtures/mapTiles.ts`).
- **Cross-reference:** `docs/guidelines/testing.md`, `docs/guidelines/third-party-services-on-a-preview.md`.
- **First noted:** 2026-09-24, the no-third-party-in-tests change.
- **Fix (2026-09-25):** a second layer beneath the `fetch` guard. `installNetworkGuard()` now also patches `net.Socket.prototype.connect` (`installSocketGuard`, `apps/web/src/test-support/networkGuard.ts`), the call that `net.connect`, `tls.connect` and undici all end in. That covers Node `http`/`https` `request`/`get`, jsdom's `XMLHttpRequest`, and `WebSocket` in both environments. A connect to a host `isLocalHostname` doesn't accept is destroyed with the same `blockedRequestMessage` (naming `host:port`) before any DNS lookup, and the message is also written to `console.error`, because XHR (bare `error`) and WebSocket (1006 close) never show it to the caller. Unix sockets and every local host connect as before. It is the socket, not `http.request`, because MSW's `ClientRequestInterceptor` wraps `http.request` in a Proxy that calls through for every request, handled or not, using `MockHttpSocket`s. A guard at `http.request` would refuse requests MSW was about to answer. `MockHttpSocket` overrides `connect`, so only a passthrough reaches the patched method. `sendBeacon` needed nothing: neither Node 24 nor jsdom 29 defines it, and a test pins that absence.
- **Reproduction (before the fix):** an `http.get` to host `third-party.invalid` with a `lookup` that resolves it to a stub server on 127.0.0.1 returned `"reached"` and the server counted 1 hit. `https.get("https://third-party.invalid/…")` failed only on `getaddrinfo ENOTFOUND third-party.invalid`, which means it went to DNS and would have connected.
- **Proof:** new cases in `networkGuard.test.ts` (node: `http.get` with the loopback `lookup`, `https.request` + `https.get`, `WebSocket`, local still answered, MSW-handled `https.get` still stubbed while an unhandled one is refused, `connectTarget` overloads including http's `path: null`), a new `networkGuard.jsdom.test.ts` (XHR, WebSocket, no `sendBeacon`), and an `https` case in `networkGuard.int.test.ts`. With `installSocketGuard()` commented out, 6 unit cases and the int case went red, e.g. `expected 'reached' to be 'error: Blocked network request to third-party.invalid:45635: …'` and `expected 'getaddrinfo ENOTFOUND third-party.invalid' to be 'Blocked network request to third-party.invalid:443: …'`. Restored, 14/14 + 3/3 green. Checks: `pnpm --filter web typecheck`, `pnpm --filter web lint`, the whole unit lane (289 files / 3984 tests), and the whole integration lane (83 files / 1050 tests, Postgres on localhost unaffected). Both lanes were run in full because the setup file every test loads changed. Neither lane logged a single `Blocked network request` outside the guard's own tests.
- **Decision (2026-09-25 overnight sweep):** guard at `net.Socket#connect` rather than wrapping `http.request`/`https.request`/`XMLHttpRequest`/`WebSocket` one by one. Per-API wrappers were rejected: the `http` wrapper breaks MSW (above), and per-global wrappers miss any library that opens its own sockets. Log the refusal to `console.error` as well as failing the socket. The alternative, a test-only "blocked connections" registry, was rejected as extra surface for the same observable. Kept the empty Sentry DSN: the socket guard would refuse Sentry's post, but Sentry would still try and report the failure mid-test.
- **Still not covered (by design, in the module header):** worker threads and child processes get their own unpatched `net`. That includes jsdom's synchronous XHR. A request through a local HTTP proxy connects to the proxy, which is local, but Node only does that under `NODE_USE_ENV_PROXY`, which neither lane sets.
