### KI-2026-09-15-b — the phone Notebook insert spec intermittently finds the widget bound to "All days" — RESOLVED

- **Severity:** test reliability — one e2e spec, phone lane. No evidence yet of a product defect; the same walk passes on the next run with no change.
- **Milestone:** **M14, carried (assigned 2026-09-24, KI pass)** — owned by M14 (the notebook/widget builder), not a gate box. Listed in `docs/milestones/M14-rich-layer.md` § *Parked 2026-09-24*.
- **Area:** `apps/web/e2e/m14-mobile-notebook.spec.ts:94` — *"insert is one sheet with a bind step, and the widget lands already pointed"*. The assertion is `expect(widget-settings button /: dates/).not.toHaveText("All days")`.
- **What is wrong:** the inserted widget is expected to land bound to the day chosen in the sheet's bind step, and sometimes lands on the default `All days` instead. The failure is an assertion, not a timeout, and it names the same locator every time.
- **How it came to light:** three consecutive `pnpm --filter web test:e2e:ci-like` runs on `claude/keen-darwin-qkkq41` (2026-09-15, M21 Phase 3/4). Run A: failed on the first attempt AND on Playwright's retry. Run B: passed. Run C: failed once, passed on retry — reported as `1 flaky`. So it is intermittent rather than broken, and intermittent in a way that survives one retry.
- **Why not fixed there:** it is **not this branch's code**. M21 touches billing, the account sheet, a new `plans` route and the operator console; `git diff <base>...HEAD` contains no file under `components/pages/**`, no widget module and no notebook route. Fixing an M14 widget-binding defect inside an M21 branch would widen a PR past what it is reviewed for, which is the same reason `KI-2026-09-14-f` was filed rather than folded into PR #175.
- **Read this before calling it environmental** (CLAUDE.md rule 2, which is why this entry exists at all): the location does NOT move between runs, so it is not the timeout signature. Either the bind step's write races the widget's first render, or the sheet closes before the chosen day is committed and the widget falls back to its default. Both are real and both are cheap to reproduce once somebody runs the spec in a loop.
- **Scope:** run `pnpm --filter web test:e2e --project=phone m14-mobile-notebook.spec.ts` in a loop until it reproduces, then look at whether the insert command carries the day or the widget re-reads it after mount. If it is a race in the product rather than in the spec, it is a real defect on the phone surface and this entry should be re-severitied.
- **Cross-reference:** SPEC §19, `docs/milestones/M14-*`, the three runs above.
- **First noted:** 2026-09-15, running the e2e lane for M21 Phase 3.
- **Resolved:** 2026-09-24. **Both a spec race and a small product defect, and the insert→bind flow itself is correct.** The bound day always reached the editor and the insert's own PATCH: an instrumented run logged `"name":"cost","params":{"dates":{"from":"2026-10-05","through":"2026-10-05"}}` in the insert's save. Every failure was at `:154`, the check *after* `page.reload()`; the in-memory check at `:143` never failed. **The mechanism:** `PageEditor`'s mode effect called `editor.setEditable(editable)`. TipTap 2.27.2's `setEditable(editable, emitUpdate = true)` emits `update`, `onUpdate` is `onChange`, and `onChange` autosaves. So clicking *Edit page* queued an 800 ms save of the **unchanged** document. When that save was sent before *Insert it* and answered after it, `waitForPageSaved` (which accepted *any* page PATCH) took it for the insert's save. The failing runs' only pre-reload PATCH carried the seeded, unbound `cost` first (`"params":{}},{"type":"text","text":" · budget left — "`). The reload then unmounted `PageScreen`, whose cleanup cancels the debounced save, so the bound widget never reached the server. **Fix:** `setEditable(editable, false)` in `apps/web/src/components/pages/editor/PageEditor.tsx`, so a mode flip is no longer a write. Also, the spec's `waitForPageSaved` takes a `carrying` predicate, and the insert waits for the PATCH whose first `cost` macro has `dates`. No sleeps, raised timeouts, retries or skips. **Proof** (production build, `CI=true pnpm test:e2e --project=phone m14-mobile-notebook.spec.ts -g "lands already pointed" --repeat-each=20 --retries=0`): before, **6 failed / 15 passed** (`Expected: not "All days"` / `Received: "All days"`, all at `:154`), and 3/20 on a second run. Spec fix alone against the old build: 21 passed. Product fix alone with the original spec: 21 passed. Both: 21 passed. Whole file `--repeat-each=20` under three busy-loop processes (load average ~12.5 on 4 cores): **121 passed**. Regression test: `PageEditor.test.tsx` › *does not report a change when only the mode flips*. It was red before the fix (`expected "vi.fn()" to not be called at all, but actually been called 2 times`) and is green after.
