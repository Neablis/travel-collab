### KI-2026-09-19-d — the Keep-a-day dialog does not focus its name field, so "accept it and press Enter" has never worked — RESOLVED

- **Severity:** papercut (the feature works; one documented shortcut does not, and two comments claim it does)
- **Area:** `apps/web/src/components/trip/KeepDayDialog.tsx` (the `Name` input has no `autoFocus`), `apps/web/src/components/ui/dialog.tsx` (Radix focuses the first tabbable node in `DialogContent`, which is the header's `<RadixDialog.Close>`)
- **Symptom:** opening the dialog and pressing Enter without clicking anything **closes it and saves nothing** — the keypress reaches the focused Close button. Typing in the name field first and pressing Enter does save; `submitOnEnter` is wired correctly and is not the problem. Measured on the PR #192 preview: `focus after open: {"tag":"BUTTON","aria":"Close"}`, then `Enter` → `dialog count: 0`, nothing written.
- **PRE-EXISTING, and checked rather than assumed:** `git show origin/main:apps/web/src/components/trip/KeepDayDialog.tsx` has the same absent `autoFocus` and the same claim. **M23 did not cause this** and its multi-day picker does not change it.
- **Why it is worth an entry:** two places assert the behaviour that does not happen. `KeepDayDialog.tsx`'s own header says *"This dialog opens with the name already filled in and the field focused, so the whole interaction is 'accept it and press Enter'"* — added when the Enter handler was built (Mitchell, 2026-09-01) — and `docs/milestones/M23-multi-day-playbooks.md`'s 2026-09-19 note repeated it as *"still accept-and-Enter"* while describing the new picker. Both claims are corrected in #192; the defect itself is not fixed there, because focusing the field is a change to a shipped dialog's behaviour that M23 has no business making on the way past.
- **Suggested fix:** `autoFocus` on the name `Input`, or Radix's `onOpenAutoFocus` pointed at it. Worth checking the same pattern in the other dialogs that pair a prefilled field with `submitOnEnter` before fixing this one alone.
- **First noted:** 2026-09-19, walking PR #192's preview.
- **Resolved:** 2026-09-24. `autoFocus` on the name `Input` in `KeepDayDialog.tsx`. Radix's `FocusScope` only falls back to the first tabbable node (the header's Close button) when nothing inside `DialogContent` already has focus. React applies `autoFocus` at commit, before that mount effect runs, so the field wins and the shared `ui/dialog.tsx` stays unchanged. The field's comment, which described this defect, now states the behaviour and why it holds. Of the other `submitOnEnter` sites the entry suggested checking, `NewTripWizard.tsx`'s is an in-body draft field, not a prefilled field that opens focused. So it is not the same pattern, and it was left alone.
  Reproduced first, in `KeepDayDialog.test.tsx`: the new test `"opens with the name field focused, so a bare Enter keeps the day"` renders the dialog and presses Enter with no click. Its first version asserted the focus target directly and failed with `AssertionError: expected <button type="button" …(2)>…(1)</button> to be <input …(4)></input>`, and the received node was `aria-label="Close"`, which matches the preview measurement. That assertion read `document.activeElement`, which the test-quality wall bans (`testing-library/no-node-access`). So the committed test states focus through what the keypress reaches instead. With `autoFocus={false}` it fails `expected "vi.fn()" to be called with arguments: [ { name: 'Day 3 of Kyoto', …(2) } ]` / `Number of calls: 0`, and with the fix restored it is green.
