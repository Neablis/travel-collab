# F-B09 — The pages routes store the *parsed* document, not the received bytes, so an unknown node from a newer client is permanently reclassified as `unknown` on write — the rolling-deploy case ADR-038 decision 3 promised to survive

- **Stream:** B Notebook (found by the verifier while checking B09; merges the original B09 `v`-default point and F-C05) · **Severity:** MEDIUM · **Confidence:** CONFIRMED (reproduced with a node probe against `packages/contracts/src/pageDoc.ts`)
- **Area:** `apps/web/src/app/api/trips/[tripId]/pages/[pageId]/route.ts:20` and `pages/route.ts:23` (persist `body.data.content` — the Zod *output*); `packages/contracts/src/pageDoc.ts:152-158` (`PageInlineNode`/`PageNode` preprocess with `tagUnknownNode`, so an unrecognised node arrives as `{type:"futureNode"}` and parses to `{type:"unknown", raw:{type:"futureNode"}}`), `:118-131` (`KNOWN_NODE_TYPES` does not include `unknown`, so on the next read the stored wrapper is wrapped **again**), `:571-572` (`serializePageNode` unwraps `unknown` → `raw`, which is what the browser uses and the server does not); `:346` (`v` defaults to 1 with no ceiling; v-less bodies are stored as `v: 1` — `route.int.test.ts:69,103`); ADR-038:246-250 (decision 3: "carrying the original JSON verbatim … serialise back out byte-identical").
- **What is wrong:** reproduction: PATCH `{content:{…, content:[{type:"paragraph"…},{type:"futureNode",foo:1}]}}` through a server that does not know `futureNode`. Stored: `{"type":"unknown","raw":{"type":"futureNode","foo":1}}`. Re-read: `{"type":"unknown","raw":{"type":"unknown","raw":{…}}}`; `collectPageDocNodeTypes` reports `['paragraph','text','unknown']`, never `futureNode`. So during a rolling deploy — a newer browser build autosaving through an older server instance — the new node is entombed: the newer build never sees its own type again and the page opens read-only for everyone. ADR-038 designed decision 3 for exactly this window; it holds in the browser (`serializePageNode`) and is defeated on the server. No test covers it (`route.int.test.ts` has no unknown node; `storedPageDoc.test.ts:54` is client-side).
- **Suggested fix:** on both write routes, after parsing: refuse `v > CURRENT_PAGE_DOC_VERSION` (400), then store `serializePageDoc(migratePageDoc(parsed))` — serialisation unwraps `unknown` back to its raw JSON and stamps `v`, so rows converge to the current version and unknown nodes survive verbatim. Same insertion point as F-B01's registry check; do them together.
- **Scope of the fix:** `server/pages.ts` (or the two routes), `route.int.test.ts`. No contract change unless the write schema gains a `v` ceiling refine (then CHANGELOG). Check subset: pages route int tests + `page-doc.test.ts`.
- **Test that should exist:** PATCH a document containing `{type:"futureNode",foo:1}` → GET returns exactly `{type:"futureNode",foo:1}` at that position (byte-identical), and `collectPageDocNodeTypes` on the stored row reports `futureNode`; PATCH with `v: CURRENT+1` → 400; PATCH a v1 body → stored `v` is CURRENT. Break by reverting to storing `body.data.content`.
- **Cross-reference:** ADR-038 decisions 2 and 3, F-B01, F-C05 (superseded by this file — its `v` points are folded in here).
- **Do not:** make the read path strict; "fix" by adding `unknown` to `KNOWN_NODE_TYPES` (that hides the problem and breaks the vocabulary guard).
