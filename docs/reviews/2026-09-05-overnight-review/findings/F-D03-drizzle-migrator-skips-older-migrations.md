# F-D03 — Drizzle's migrator applies only entries newer than the last applied row, so two migration PRs in flight can silently skip one — on the shared preview branch and in production

- **Stream:** D Infra · **Severity:** MEDIUM (raised: the verifier showed the production path is exposed too) · **Confidence:** CONFIRMED mechanism (verified in the SDK); no observed skip yet
- **Area:** `node_modules/.pnpm/drizzle-orm@0.45.2*/node_modules/drizzle-orm/pg-core/dialect.cjs:64` (`if (!lastDbMigration || Number(lastDbMigration.created_at) < migration.folderMillis)` — a migration whose journal `when` is older than the newest applied row is never applied); `migrator.cjs:55` (`folderMillis: journalEntry.when`); `drizzle-kit@0.28.1` delegates `migrate` to the installed drizzle-orm migrator, so this is what both `pnpm db:migrate` and `migrate-production.yml` run; `apps/web/scripts/vercel-build-migrate.mjs:9-10` (every preview build migrates the one shared Neon `preview` branch; `docs/guidelines/environments-and-deploys.md:55,75-79`); `apps/web/drizzle/meta/_journal.json` (16 entries, `when` strictly increasing today). Precedent for two migration PRs in a day: #99 (19:51) and #100 (20:49) on 2026-08-30, journal 0011–0013 within ~97 minutes.
- **What is wrong:** **Preview:** PR A's build applies its migration (`when = T_A`) to the shared branch; PR B, generated earlier (`T_B < T_A`) and lacking A, builds next — B's migration is skipped and B's preview 500s on exactly the feature under review, which reads as a code bug. **Production:** if PR B (later `when`) merges and is dispatched before PR A (earlier `when`) merges, A's migration is silently skipped in production; `drizzle-kit migrate` prints success. Nothing in CI checks journal shape (F-C07), and nothing compares the journal against what production has applied (F-C03).
- **Suggested fix:** (a) `scripts/check-migration-journal.mjs` in root `lint` (F-C07), **asserting the newest entry's `when` exceeds `origin/main`'s newest `when`**, not merely that the PR's journal is internally increasing — that is the check that catches the production case. (b) Per-preview Neon branch via the Neon–Vercel integration (a platform setting plus env wiring), or a documented "reset the preview branch when two migration PRs are in flight" at `environments-and-deploys.md:75-83`. (c) A line in the migration section of AGENTS.md: rebase and regenerate a migration whose `when` is older than one already on `main`.
- **Scope of the fix:** one script + test + `package.json`, one guideline, one AGENTS.md line; Neon setting is out-of-repo. Check subset: `node --test scripts/__tests__`, `pnpm lint`.
- **Test that should exist:** `scripts/__tests__/check-migration-journal.test.mjs` with a fixture whose newest `when` is older than a fake "main" — goes red.
- **Cross-reference:** KI-2026-08-30-e (the same isolation principle applied locally but not to previews), ADR-004, F-C03, F-C07.
- **Do not:** have the preview build `db:reset` the branch — it destroys data reviewers are mid-walk on.
