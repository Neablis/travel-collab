# F-G02 — Live AI enrichment accepts a wrong venue inside the right bounding box, renames the stop after it, and reports it `verified`; the identity check written for exactly this has no caller on the request path

- **Stream:** G Broken functionality (answers F-F12's open question) · **Severity:** MEDIUM (a sub-finding of open KI-015 — the new part is that the fix now exists off the shelf and is unwired) · **Confidence:** CONFIRMED mechanism (full path read; the three vendor instances are recorded in the seed history; not exercised against the live vendor from this session, which would cost API spend)
- **Area:** `apps/web/src/server/ai/geocodeEnrichment.ts:157-199` (`resolveOne`): `:171-178` builds `found` with `name: match.canonicalName` — the model's own name is *replaced*; `:183-193` accept on `distanceKm ≤ 50` (trusted hint) or `withinBox` (trip region, 150 km margin) only; `:12-16` states the rule "never relocate, only refine". `apps/web/src/server/ai/geocodeNameMatch.ts:1-10` (header: "A per-city bounding box only rejects a wrong-CITY match. It has no way to reject a wrong-VENUE match that lands inside the right city: Kegon Falls → Urami Falls, Zentis Osaka → Hotels Inn Osaka, Shin-Osaka Station → Shinagawa Station. All three passed the box"), `:206-219` `placeNameVerdict`. Callers of `placeNameVerdict`: only `apps/web/scripts/geocode-japan-seed.mts:135,362`; zero in `src/`.
- **What is wrong:** `forward(name, { limit: 1, viewbox })` returns the vendor's best guess *inside the box*. Any venue within range passes; the stop's `location.name` is overwritten with the wrong venue's display name, coordinates move to the wrong venue, the outcome is `verified` (so no user notice — `hasUnverifiedLocations` excludes it), and per KI-015 a `verified` pin widens `tripRegionOf` permanently. The seed pipeline hit exactly this three times with the same vendor and got the fix (KI-039/058/077); the request path never did. KI-015 does record the mode in general terms ("a guess that happens to agree with a fuzzy string match is still reported as verified"; the canonical-name-replaces-model-name rule). What it does not record is that a name-identity predicate now exists — `placeNameVerdict`, built 2026-08-28 under resolved KI-039, whose `:33` cross-references KI-015 as "same family, different call site" — and was never wired into this call site.
- **Reproduction (unit):** fake `Geocoder.forward` returning `{ canonicalName: "Urami Falls, Nikkō", lat/lng 8 km from the hint }` for `AddActivity{ location: { name: "Kegon Falls", lat, lng } }` → `enrichCommandLocations` yields `report.verified = ["Kegon Falls"]` and `command.location.name === "Urami Falls, Nikkō"`.
- **Suggested fix:** in `resolveOne`, after geometry passes: `const verdict = placeNameVerdict(name, match.canonicalName)`; `"mismatch"` → `{ location: fallback, outcome: "unverified" }`; `"not-comparable"` (the Japan local-script case, KI-077) → accept coordinates but keep the model's `name` rather than renaming, still verified-by-box. This resolves F-F12 to "stays under `server/ai` and gains a caller".
- **Scope of the fix:** `geocodeEnrichment.ts` + `geocodeEnrichment.test.ts`; no contract change. Check subset: `pnpm --filter web test -- geocodeEnrichment geocodeNameMatch`.
- **Test that should exist:** the reproduction above, red first (today: `verified` and renamed).
- **Cross-reference:** KI-015 (append the unwired-predicate note; this is its fix path), KI-039, KI-058, KI-077, F-F12.
- **Do not:** move `geocodeNameMatch.ts` out of `server/ai/` (F-F12's other option) before this decision is taken.
