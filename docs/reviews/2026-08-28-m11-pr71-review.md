# Review of PR #71 — M11: sharing, invites, saved days, trip cloning

Reviewed at `a109eb7` (the merge), diff scope `6d8b76e..a109eb7` (193 files,
+12,917/−911). Four parallel review agents (access-layer security, contracts &
domain, server logic, UI & tests); every finding below is anchored to file:line
and was verified against the tree. **CONFIRMED** = full code path traced;
**PLAUSIBLE** = mechanism verified, trigger not fully proven.

**Overall verdict:** this is a well-built change. The access architecture is
sound where it matters most — token generation, the exhaustive per-command role
map, per-sub-command batch authorization, clone going through the command
pipeline rather than raw event copies, pinned shares resolved through one gate.
The PR body's verification section is honest (including retracting a false
browser-walk claim). What follows is what four adversarial passes found anyway:
one operational blocker, one real access-control hole, one confirmed 500, and a
set of smaller items.

## 1. HIGH — revoke/accept race leaves a permanent, irrevocable membership

**CONFIRMED independently by two agents.**
`apps/web/src/server/access/invites.ts:99-118` (`revokeInvite`).

Under READ COMMITTED: revoke's plain `SELECT` sees `status='pending',
acceptedBy=null` → skips `revokeMembership`; a concurrent accept claims the
token, inserts the membership, commits; revoke's blind
`UPDATE ... SET status='revoked'` (no status predicate) then applies over the
new row version. Result: invite shows "Revoked", membership row lives. It is
**unrecoverable through the API**: re-revoking early-returns at `:108`
(`status === "revoked"` → ok), `revokeInvite` is the only caller of
`revokeMembership`, and there is no remove-member endpoint. A recipient who
suspects revocation can script accepts and keep editor access permanently.
The module's own docstring invariant ("a revoked invite can never leave a live
membership behind") fails in exactly the lock-them-out scenario it exists for.

**Fix (small):** do the guarded write first —
`UPDATE trip_invites SET status='revoked', ... WHERE id=$1 AND status <> 'revoked'
RETURNING accepted_by` (RETURNING reflects the post-lock row, so a concurrent
accept's `acceptedBy` is visible), then delete the membership when the
*returned* `accepted_by` is non-null. Also make the already-revoked branch
re-assert membership deletion instead of early-returning, so a retry heals any
leak. Consider a remove-member endpoint as the general recovery path.

## 2. MEDIUM — "Keep this day" 500s on pre-M18 trips and leaves an invalid row

**CONFIRMED.** `apps/web/src/server/access/trip-access.ts:33-43` returns
`getTripDetail()`'s **raw** `trip_details.doc` (unparsed) typed as
`TripDetail`; `POST /api/saved-days` hands it to `stopsForDay`
(`lib/savedStops.ts:37-42`), which copies `activity.kind`/`tags` verbatim. For
a doc written before M18 both are `undefined`; `SavedStop.kind`/`tags` are
required with no default, so the route's final `SavedDay.parse` throws —
**after** `db.insert(savedDays)` committed (no transaction). User gets a 500
plus an orphaned, contract-violating library row. The PR fixed this exact
class for the trip GET route (Mitchell's "500 loading any trip" report) but
missed the third consumer it created itself.

**Fix:** `TripDetail.parse` once inside `requireTripAccess` so `access.detail`
actually is what its type claims — that also defuses the standing trap for
every future consumer (finding 2b). Minimum fix: `?? "planned"` / `?? []` in
`stopsForDay`, mirroring `hydrate`.

## 3. HIGH (carried) — the send-queue wedge from the project review is still live, side by side with the fix pattern

**CONFIRMED.** All ~14 new M11 apiClient helpers (`apiClient.ts:243-420`)
correctly wrap fetch+parse in try/catch returning `{ok:false, status:0}`. The
nine pre-existing helpers the optimistic queue actually depends on —
`sendTripCommand` (:100), `sendTripCommandBatch` (:117), `fetchTripDetail`
(:64), the history/AI/duplicate/reset helpers — remain unwrapped, and the
sender effect (`TripProvider.tsx:159-164`) still resets `inFlight` after an
unprotected `await`. A rejected fetch (offline, DNS, or a `TripDetail.parse`
throw on a 200) still wedges the queue permanently: "Saving…" forever, no
failHead, no retry, silent loss on navigation
(docs/reviews/2026-08-28-project-review.md §1.1). One mechanical try/catch
pass over the nine old helpers finishes what the new code already does.

## 4. MEDIUM — saved-day insertion is a new silent-loss trigger on the one queue

**CONFIRMED.** `SavedDaysDialog.insert()` (`SavedDaysDialog.tsx:68-79`) calls
`insertSavedDay` then `onInserted(result.value)`; `AddSavedDayButton.tsx:40`
passes `applyOutcome` as `onInserted`; `applyOutcome`
(`TripProvider.tsx:279-285`) sets `pending: []` with **no pending gate**. Drag
a card, then insert a saved day: queued-but-unsent edits are silently
discarded from UI and server, and a KI-36-retained failure queue is wiped
without its retry ever being offered. History commands guard exactly this
(`if (pending) return`, `TripProvider.tsx:248`); this path and the original
assistant-ask instance (project review §1.4, still unchanged at
`TripBoardScreen.tsx:298-309`) do not. That makes six known silent-loss
triggers on one queue — none of the two open ones filed in
`docs/known-issues.md`, which is the repo's own rule for known-unfixed.

**Fix:** gate both paths on `pending` (disable the affordance while unsent
work exists) or merge into `pending` instead of clearing.

## 5. LOW-MEDIUM — the board surface is not viewer-gated

**CONFIRMED.** `TripHeader`, `SettingsSheet`, `ShareButton`,
`AddSavedDayButton` and the history controls are thoroughly `readOnly`-gated;
but `TripBoardScreen.tsx:54` never reads `readOnly`, and `Board`,
`TimelineLens`, `CalendarLens`, `UnscheduledRack`, `EndOfTrip`'s "Add a day",
and `ActivityEditorSheet` (takes `dispatch` ungated) have no viewer awareness.
A viewer can drag a card (it moves and snaps back — the exact UX
`TripProvider.tsx:199-203`'s comment claims to prevent), open the editor, and
edit fields; every attempt is refused at dispatch with "You have view-only
access" — graceful, but the affordances are live-looking, and the e2e viewer
test asserts only the badge (`m11-invites.spec.ts:152`). Edge (PLAUSIBLE): if
`fetchTripAccess` fails for a real viewer, `myRole` stays null, the whole UI
is live, and every send 403s into a retained queue whose retry can never
succeed.

## 6. MEDIUM (operational) — `GET /api/trips` now scans every trip plus N+1 membership queries

**CONFIRMED.** `api/trips/route.ts:10-28`: `listTripSummaries()` loads every
trip on the instance, filters in JS, then runs one `effectiveMembers` query
per surviving trip in a `Promise.all`. This was flagged as latent in the
project review (L3); M11 made it worse *and measurable* — the PR's own KI-28
recurrence note attributes widened e2e flake windows to per-request access
overhead. Fix: membership predicate in the query (join `trip_memberships` +
owner) and one batched `inArray` membership fetch.

## 7. Security notes on the new access layer

- **MEDIUM — dev login is now a cross-tenant impersonation surface.**
  Post-M11, on any deployment with `AUTH_DEV_LOGIN=true` and a shared DB,
  anyone can sign in as an existing `dev-*` user and inherit their
  memberships, or accept any invite as anyone. The flag still has no
  environment guard (unlike `reset-demo-data`'s `VERCEL_ENV` gate — project
  review M1, still open), and **no test asserts the gate**:
  `authConfig.test.ts` exercises `devLoginIdentity` thoroughly but never that
  the Credentials provider is absent when `AUTH_DEV_LOGIN` is unset (~10
  lines with the file's existing resetModules pattern). Also: the hardcoded
  fallback `DEV_EMAIL_BASE` (`authConfig.ts:36`) checks a personal email into
  the repo.
- **LOW — revoked/spent invite tokens still disclose metadata.**
  `previewInvite` (`invites.ts:131-158`) never gates on `status`: a revoked
  token returns `tripName`, `role`, `invitedByName` forever. Return the
  unknown-token shape for non-pending tokens.
- **LOW — member emails are served to every member, including link-joined
  viewers.** `withProfiles` (`members.ts:135-149`) via viewer-min
  `GET /access`; invites are bearer links with email-as-label (ADR-026), so
  forwarding a viewer link transitively shares all members' Google emails.
  Consistent with the ADRs — flag as a deliberate product decision, or serve
  `email` only to owners.
- **LOW — 403/404 split is a trip-existence oracle** contradicting its own
  comment (`trip-access.ts:33-42`). UUIDs make it near-useless to a prober;
  fix the comment or return 404 to strangers.
- **LOW — amplification, no limits.** Clone replays the full source per call,
  invite/share creation is uncapped, and `GET /api/trips`' full scan makes
  the growth everyone's problem (see 6). Same limiter the project review
  wants for the AI endpoint (H1) covers clone/invite/share creation.
- **Accepted-risk notes:** tokens are stored plaintext so owners can re-copy
  (ADR choice — a DB read yields live invite tokens); tokens travel in URL
  paths (platform access logs); `/s/[token]` renders no external resources
  today, but the first external link added to that page will leak share
  tokens via Referer — add `Referrer-Policy: no-referrer` on `(front)/s/**`
  preemptively (the headers() block from project review M2 is still absent
  entirely). Share pages serve notes, coordinates, budget, and cost totals —
  the fields most likely to hold things a sharer didn't mean to publish;
  conscious product decision.

## 8. Smaller server findings

- **Clone compensation** (`cloneTrip.ts:103-111`): if the compensating
  `DeleteTrip` throws, its error replaces the root cause; in the `!batched.ok`
  branch its result is ignored, so a failed compensation leaves a silent
  "(copy)" husk. Wrap it, log it, surface the original error.
- **`duplicateTrip` non-atomic head read** (`cloneTrip.ts:126-140`): detail
  and head are two reads, so `forkedFrom.atSeq` can name a point one off from
  the state actually copied. `createShare` already does this right in-tx.
- **Accept's trip-deleted check is outside the transaction**
  (`invites.ts:178-181`) — harmless downstream, noting only.
- **`saved_days.stops` jsonb is trusted forever against a moving contract**
  (`savedDays.ts:80-86`, returns rows unparsed): the next required field on
  `SavedStop` turns old rows into opaque 400s. Sibling of KI-53; file it.
- **Design decisions living only in comments:** a clone lands as one batch,
  so a single Undo strips the entire cloned trip (intentional under ADR-005,
  covered nowhere); any editor's Undo unwinds another editor's latest batch
  (reasoned in the `MINIMUM_ROLE` comment, absent from the milestone doc).
  Both deserve a line in the M11 milestone file.
- **Doc drift:** `TripShare`'s comment says "the owner's view" but the routes
  deliberately serve it at editor minimum; `cloneFrom` violates
  `diffTripStates`' "members never differ" documented precondition (harmless
  today — diff never reads members — but nothing pins it).
